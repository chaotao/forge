# forge · L3 模块设计 —— `inbox`

> 层级：**L3**。上游 = **L2 概要架构与模块划分**（`02-architecture.md`）。
> 本文件写 `inbox` 的**核心设计**；**实现以 `forge/inbox.py` 为准**。

---

## 1. 职责与边界

**模块**：`inbox` —— **念头捕获与交接**（L2 §3.1）。它是**用例层**的**数据型**角色（**不是**数据访问层，L2 §3.1）。

**一句话**：`inbox` 管**项目里那些「现在不做、但别忘」的念头** —— 记下、待着、**攒成够格的主题**、最后**交接出去**或**丢弃**。

|         | 内容                                                                                                                                                                |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **做什么** | ① **捕获**：`Item`（`text` / `tags?` / `source?` / `note?` / `created` / `status` / `target?`）<br />② **整理 · 合并**：把 N 条零散 `open` 攒成 1 条主题（`merge`，§2.4）<br />③ **交接**：`open → handed / dropped`，**一步完成**，且留一条**去向**<br />④ 读**经 `store`**                                                                                        |
| **不做**  | ① **不判**"这条重不重要 / 该不该做 / **哪几条该合**" —— 判断归 agent（L1 约定 **B**）<br />② ★ **不跟踪完成** —— 它**不是任务列表**（任务归 `plan`，§8）<br />③ **不自行落盘**（经 `store`；`.forge/` 归它独占，L2 §2.2 **W3**）<br />④ **不建**到 `plan` / `aiwf` 的**外键**（L1 **E1**，§7）<br />⑤ **不承载** L2 §2.3① 的 `ad hoc 事项`（悬空项，§8）<br />⑥ 无优先级 / 排序 / 提醒 / 截止日（§8） |

### 1.1 它回答三个问题

| 问题              | 靠什么答                                          |
| --------------- | -------------------------------------------- |
| **还悬着什么**（现在不做、但别忘的） | `inbox list` —— 未处理条目（一行一条：`id` / 内容 / 标签 / 日期） |
| **这些零散念头能不能攒成一件事** | `inbox list --full`（看全文）→ agent 判断 → `inbox merge`（§2.3 场景 C） |
| **那条念头最后去哪了**   | `inbox show <id>`（单条）+ `inbox list --all`（含已归档标题行） |

### 1.2 边界（与谁无关）

| 对象          | 关系                                                                                                |
| ----------- | ------------------------------------------------------------------------------------------------- |
| `store`     | **经它读写**（L2 §4.2 边 6）—— `inbox` **不碰文件**                                                            |
| `plan`      | **零依赖**（L2 §4.2 **写路径零依赖**；**§4.2.1** 读面原则 —— 本模块**不引用**其它模块的读面）。★ 交接**去向**是一段**文本**，可以提一句"已建 `login.T7`"，但**不是外键、不校验**（§7） |
| `observer`  | **不依赖** —— 外部运行状态归它                                                                               |
| `scaffold`  | **不依赖** —— 它立骨架 + 登记受管                                                                             |
| `workbench` | **只被读、不反向依赖** —— `workbench` 经本模块的**公开读面**读（L2 §4.2 边 **7b** · **§4.2.1**）；★「未处理的 inbox 条目」是它答"**哪些需要我介入**"的信号源之一（**由它聚合**，L1 **D2**） |
| `aiwf`      | **不感知 · 不挂钩**（L0 §4.1）                                                                            |
| 项目业务内容      | **本轮零产物** —— `inbox` 只写 `.forge/inbox.json`（`store` 代写），不往项目里落任何文件                                     |

## 2. agent 使用视角（L1 约定 **H6**）

> **本节为什么排在这里**：L1 约定 **H1** 已定「**首要使用方是 agent**」—— 对外表面先按 agent 的易用性设计。
> 故本文件把「**agent 怎么用**」提到模型之前（H5：**按完整流程设计，不按单命令设计**）。

### 2.1 五条使用纪律

| # | 纪律                                                                                            | 依据                            |
| - | --------------------------------------------------------------------------------------------- | ----------------------------- |
| 1 | **归属先分流** —— 属于**当前在推的计划** → 走 `forge plan add <计划>.<任务>`；**只有不属于任何计划、或现在不做**的，才进 inbox | L1 **B**（判断归 agent）+ 本模块定位   |
| 2 | **一次意图 = 一次调用**（H3）—— 记一条是 `add`、攒一组是 `merge`、送走一条是 `hand` / `drop`，**不由 agent 拼两步**                              | L1 **H3**                     |
| 3 | **不直读原始文件**（H4）—— `.forge/inbox.json` 是**引擎的存储**，agent 只看 `list` / `show` 的**过滤视图**            | L1 **H4**                     |
| 4 | **判定归 agent，引擎只存**（L1 **B**）—— "这条还值不值得留""该交给谁"**"哪几条该合"**是 agent（或主人）的判断，写入即落盘                                 | L1 **B**                      |
| 5 | ★ **合并时机固定在两个节点** —— ① **人明确要求**（"看看还欠什么" / "整理下 inbox"）② **「提升为需求」之前**（T2 前置）。**不在 `add` 时合** | L1 **H3 / H5** + §2.3 场景 C |

> ⚠ 纪律 1 的现实风险：agent 图省事，把**本该建 task** 的活记进 inbox（拖延）。**这条只能靠 skill 明说约束**（§10）—— 不靠"必填参数逼问"（捕获那刻根本答不出）。
> ⚠ 纪律 3 的现实风险与 `06-plan` §2.1 同源：`.forge/*.json` 是仓库里的**普通文件**，agent **天然会直接 `Read` 它**。
> ★ **为什么"不在 `add` 时合"**：`add` 那一刻 agent 只顾着这一条、**没有全局视角** → 判断质量最低；而 `add` 是**最高频**动作 → 错的代价被放大。合并是**批量动作**，本该一次看全、一次判断（H3 / H4）—— 见 §2.3 场景 C。

### 2.2 地址规则

```
INB-003          ← 一条念头 —— 项目内唯一
```

- **条目标识 = 顺序 id**（`INB-003`）—— **不是 slug**：念头没有天然短名（它往往只是一句话），而 **id 必须递增、不复用**（§3.3）—— 否则 `去向` 里写的旧 id 会指错条目（L1 **D1**）。
- **无嵌套**：inbox 是**项目级平铺**的一层，**没有** `<计划>.<任务>` 那样的二级地址（与 `plan` 的有意对比，§7）。
- ★ **合并产物也是普通条目**：用同一个递增 id 空间（`INB-NNN`），**不另立地址形态**；它与"没合过的念头"在视图上**不区分**（§8）。

### 2.3 完整流程（三个场景）

**场景 A · 记下**（开发中冒出个念头）

| 步 | agent 做什么                           | **一次调用**                                     | 拿到什么                              |
| - | --------------------------------- | ------------------------------------------ | --------------------------------- |
| 0 | ★ **先判归属**（纪律 1）                   | ——                                         | 属当前计划 → 走 `forge plan add`；否则 → 下一步 |
| 1 | **记下**                            | `forge inbox add "登录页的报错文案要统一"`              | `id` = `INB-004` + 日期              |
| 2 | （可选）带标签 / 出处 / 补充                 | `forge inbox add "…" --tag 体验 --source login --note "…"` | 同上            |

**场景 B · 交接**（主人说"看看还欠什么"／流程收口时 —— 挑条目定去向）

| 步 | agent 做什么                | **一次调用**                                          | 拿到什么（H4：只要该场景需要的）                |
| - | ------------------------ | ----------------------------------------------- | -------------------------------- |
| 0 | **看还悬着什么**               | `forge inbox list`                              | 未处理条目：`id` / 内容（截断一行）/ 标签 / 日期   |
| 1 | **挑一条看全**                | `forge inbox show INB-004`                      | 单条全文 + 出处 + 备注 + 状态 + 去向          |
| 2 | ★ **按去向分组呈交**（不按标签分组）    | ——（agent 自己组织）                                 | 纳入某计划 / 留给以后 / 丢弃 —— **等主人选定**    |
| 3 | **交接出去**                 | `forge inbox hand INB-004 --to "纳入 login 计划"`    | 状态 `→ handed` + 去向（从活页移出）        |
| 4 | **或 丢弃**                 | `forge inbox drop INB-002 --to "与既有方案重复"`       | 状态 `→ dropped` + 去向（从活页移出）       |
| 5 | **回看**（含已归档）             | `forge inbox list --all`                        | 未处理条目 + 已归档条目（**标题行**）            |

**场景 C · 整理 · 合并**（"整理下 inbox"／**准备提升为需求之前**）

| 步 | agent 做什么                     | **一次调用**                                     | 拿到什么                                |
| - | ---------------------------- | ------------------------------------------ | ---------------------------------- |
| 0 | **看全部（全文）**                  | `forge inbox list --full`                  | 所有 `open` 条目 + `text` **全文**（不给 `note`） |
| 1 | ★ **判断**：哪几条是**一件事** → 合成一句表述 | ——（agent 自己组织）                             | 待合并的 id 组 + 新表述                    |
| 2 | **合并**                       | `forge inbox merge INB-001 INB-004 --text "…"` | 新 `id`（如 `INB-005`）+ 源 2 条 → 已归档（`handed`） |
| 3 | （可选）重复下一组                    | ——                                         | ——                                 |
| 4 | **回看**                       | `forge inbox list`                         | 剩下的零散条目                            |
| 5 | **接着往上走**（若有 plan）           | ——（入口层组合：`inbox` + `plan`，§9 **T2**）       | 把够格的主题**提升为需求**（本轮不做）              |

> ★ **本能力只交接、不代做**（依据 **L1 E1**：`inbox` 与 `plan` 零依赖，`inbox` **不能**替 `plan` 建任务）。
> 「把念头**提升为任务 / 需求**」= **入口层组合**两个用例的动作（不算 `inbox` 的动作）—— 本轮**不做**，登记 §9 **T2**。
> ★ **宁少合、不合错**：合并判断没把握时，**宁可留着**（继续独立）—— 合错了源虽可查（`list --all`），但**没有撤销动作**（§9 **T8**）。
> ★ **合并只让条目"够格"，不让它"变成需求"** —— 「需求」在 forge 里 = `plan` 的**计划 / 任务**，`inbox` 不生产它（§7）。

### 2.4 命令总表

**写（5 个动词 / 3 个捷径）** —— 一个意图一个动词：

| 写动词                                                        | 用途                                       | 强制               |
| ---------------------------------------------------------- | ---------------------------------------- | ---------------- |
| `inbox add <内容> [--tag <t>]… [--source <s>] [--note <n>]`    | **记一条**                                  | **内容**             |
| `inbox merge <id> <id> [<id>…] --text <表述> [--tag]… [--source] [--note]` | ★ **整理**：把 N 条攒成 1 条主题（§2.3 场景 C） | **源 ≥ 2 且全 `open`** · **`--text`** |
| `inbox set <id> [--text][--tag]…[--source][--note]`          | **兜底** —— 改笔误 / 补标签 / 改出处（**不动状态**）        | 至少给一项            |
| `inbox hand <id> --to <去向>`                                 | **交接出去**（`→ handed`）                     | **`--to` 必填**     |
| `inbox drop <id> --to <去向>`                                 | **丢弃**（`→ dropped`）                      | **`--to` 必填**     |

> `add` 建、`set` 改，`merge` 攒，`hand` / `drop` 是**语义捷径**（各映射到一次"改 `status` + 写 `target`"）。
> **为什么 `merge` 是独立动词而不是让 agent 自己 `add` + `hand` 拼**（H3：一次动作 = 一次调用）：拼法要 `add`（拿新 id）再 N 次 `hand`（引用新 id）→ **多次调用、非原子**；独立动词 = **一次调用、一次写**。
> **为什么 `merge` 的 `--text` 必填**：整合表述是 **agent 的判断产物**（L1 **B**：语义不归引擎）—— 引擎**不能**替它拼原文（拼出来的是"堆"不是"主题"）。
> **为什么是两个捷径而不是一个 `resolve --status`**（H2：能强制就强制）：两个动词各自**只有一个结果**，agent 不需要知道 `status` 的取值集合；也要不了"两种写法语义却不同"的坑。
> **为什么 `hand` / `drop` 都要 `--to`**：它问的是「**这东西最后落哪了**」—— 是**已经发生的事实**，答得出来；与"预见性辩护"（如"为何现在不做"）不是一类。

**读（2 个视图 · `list` 带 `--full` 变体）** —— 都不吐 `inbox.json` 原始文件；默认**结构化文本**、另给 `--json`：

| 读视图                      | 返回                                       | 过滤器              | **默认体量**                        |
| ------------------------ | ---------------------------------------- | ---------------- | ------------------------------- |
| `inbox list`             | **未处理条目**：`id` / 内容（截断）/ 标签 / 日期        | `--tag <t>`      | **全量**（未处理条目 = "我还欠着的"，截断会漏）      |
| `inbox list --full`      | ★ **整理专用**：未处理条目 + **`text` 全文**（仍不给 `note`） | 同上 | 全量（整理要**一次看全**才能判断哪几条是一件事）      |
| `inbox list --all`       | 未处理条目 + **已归档条目（标题行）**                    | 同上               | 同上；**归档只给标题行**（不给正文 —— H4）         |
| `inbox show <id>`        | **单条全文**：内容 + 标签 / 出处 / 备注 + 状态 + 去向      | —                | **全量**（单条，有界）                    |

> **为什么归档默认不列**：已归档随项目寿命**无界增长**；默认列它**会炸 token**（H4）。
> **为什么 `list` 默认给全量**：未处理条目 = 主人"**还欠着的事**"，是 `inbox` 存在的意义 —— 截断 = 漏掉"别忘"的那条。
> ★ **为什么 `--full` 单独一档**：`list` 的一行摘要**不够**支撑"哪几条是一件事"的判断；但把 `note` 也给出去又**超需**（H4：只给该场景需要的）→ `--full` = **全文、不含 note**，只在**场景 C** 用。
> **输出契约**：默认渲染**结构化文本**；加 `--json` 输出**同一过滤视图**（**非原文**，过滤与默认体量规则照旧生效）。与 `06-plan` §2.4 的口径**一致**（H2：表面一致）。

### 2.5 token 纪律（视图分工，H4）

| 视图                | 带正文？           | 默认体量 | 为什么                          |
| ----------------- | -------------- | ---- | ---------------------------- |
| `inbox list`      | ❌ 只一行（截断）      | 全量   | 要"一眼扫完还欠什么"（H4）              |
| `inbox list --full` | ✅ `text` 全文（无 `note`） | 全量   | 整理判断**要读全**，但又不要 `note`（H4） |
| `inbox list --all`| ❌ 归档只标题行       | 全量   | 归档无界增长 → 不给正文                |
| `inbox show <id>` | ✅ 全文 | 全量   | 单条，有界；看全才能定去向                |

**两条规则**：

1. **正文分三档**：`list` 一行摘要 · `--full` `text` 全文 · `show` 含 `note` 的全文 —— **够用即止**（H4）。
2. **默认体量贴合各自的界** —— 有界（单条）给全量；无界的部分（归档）**只给标题行**。

## 3. 模型

依 **L1 约定 C**（模型先行）。落盘形态 = 语言中立的 JSON Schema（`forge/schemas/inbox.schema.json`，§5）。

### 3.1 条目集合（`kind` `inbox` · snapshot）

```
Inbox {
  version: int             # schema 版本（变更须显式动作，C4）
  items:   [Item]
}

Item {
  id:      string          # 项目内唯一 · 递增不复用（`INB-NNN`）
  text:    string          # 一句话：是什么念头（必填）
  status:  string          # open | handed | dropped
  created: string          # ISO 8601（捕获日期）
  tags:    [string]?       # 自由标签（不封闭词表）
  source:  string?         # 出处：哪个计划 / 哪次对话 —— 纯文本，不校验
  note:    string?         # 补充说明
  target:  string?         # 去向（仅 handed / dropped 有）：交给谁 / 纳入哪 / 为何丢弃
}
```

**`text` 与 `note` 的分工**：`text` = **可扫的一行**（`list` 视图只渲染它）—— 所以它必须短；`note` = **只有 `show` 才看到的详情**（`list` 不带）。与 `plan` 的 `title` / `goal` 同一分工思路。

**为什么没有 `updated`**：条目唯一会变的就是 `status` + `target`，一次交接即终结 —— 单独的"最后修改时间"没有读者（A1）。`created` 有读者（"这条放了多久"）。

★ **合并（§2.4 `merge`）零模型改动** —— 它只用**已有字段**：
- **产物** = 一条普通 `Item`（新 `id`、`status=open`、`text` = agent 给的整合表述）
- **源** = 改 `status → handed` + 写 `target="并入 <新id>"`
- **不新增 `mergedInto` / `mergedFrom` / `group` 字段**（§3.3 / §8）

### 3.2 词表（§4）

**只有一张封闭词表** = `Item.status`。`tags` **有意不封闭**。

### 3.3 四个"没有"是刻意的

不为"以后可能需要"预留结构（L1 **A1**）：

| 没写进去                    | 为什么                                                                                                  |
| ----------------------- | ---------------------------------------------------------------------------------------------------- |
| **`priority` / 排序字段**   | 单人在推进自己的事，优先级是**读的时候的判断**（靠 `plan` 的进展 + 主人的取舍），不是记录的属性 → 落盘即第二个事实源（L1 **D2**）                   |
| **`due` / 提醒**          | `inbox` 治"**记住不丢**"，不治"**到点提醒**"；到期是任务/日程的事（L1 **A1**）                                                 |
| **`Item.history`（轨迹）**  | 一条念头的生命周期只有 `add → 合入 / hand / drop`（**最多一个状态变更**）→ 轨迹是**噪音**（对比 `plan_log`：任务会反复被打回）。**也正因此不另立 `inbox_log`**（§5） |
| ★ **`mergedInto` / `mergedFrom`** | 合并的**溯源已在数据里**：源条目的 `target` 写着"并入 `INB-XXX`" → **反查即可**（L1 **D2**：派生不落盘）。加字段 = 存第二份事实源 |

**`id` 递增不复用的理由**：`target` 里写的去向常引用别的 id（如"并入 `INB-007`"）—— **复用 id 会让旧引用指错条目**（L1 **D1**：一份数据一个权威来源，引用必须稳定）。

## 4. 词表

**一张封闭词表**（由 schema 枚举约束，L1 **C3**：校验只到结构层）——取值用**英文 token**（与 `store` 的 `stage` · `plan` 的 `status` 同风格；**渲染层出中文**）。

| 实体     | 字段       | 取值                                 | 说明                                                                   |
| ------ | -------- | ---------------------------------- | -------------------------------------------------------------------- |
| `Item` | `status` | `open` · `handed` · `dropped`      | 对应 L2 §2.1 的**未处理 / 已交接 / 丢弃**；★ **没有"进行中 / 已完成"** —— 它不是任务（§8） |
| `Item` | `tags`   | **不封闭**（自由文本，可多个）                  | ★ **有意**：要灵活，放弃可聚合；将来要聚合再走 §9 **T4**                                 |

★ **合并不改词表** —— 源走**既有的 `handed`**（它本就是"交出去了"，去处是另一条条目）。**不为合并另立状态**（如 `merged`）：那是同一个语义的第二个名字（L1 **F1**），且只服务一个动作（A1）。

**词表纪律**（承 `06-plan` §4 同一条）：**每个态都必须有人 / agent 能维护**，且**不引入任何"引擎自动推进"的态**（L1 **B**）。

> **为什么 `handed` 不叫 `done`**：`inbox` 的终结动作是"**交给别人 / 别处**"，不是"做完了"—— 叫 `done` 会暗示条目本身是一件事（**它是念头**）。这正是 `06-plan` 把任务态钉在 `plan` 里的原因（L1 **F1**：一个概念一个名字）。

## 5. 承载与接入

**不新造机制** —— 完全走 `03-store` 已定的接入路径。`inbox` **只有一个 `kind`**：

| `kind`  | `scope`   | 形态         | 落点                      | schema（**包内**）                    | 模型所有者     |
| ------- | --------- | ---------- | ----------------------- | -------------------------------- | --------- |
| `inbox` | `project` | `snapshot` | `<项目>/.forge/inbox.json` | `forge/schemas/inbox.schema.json` | `07-inbox` |

**一个 `kind` 就够 —— 归档条目留在同一集合**（用 `status` 区分）：

| 候选                | 判断                                                                                     |
| ----------------- | -------------------------------------------------------------------------------------- |
| **单 `kind`**（取）   | 归档 = **一次状态变更**（改已有内容）→ 属 `snapshot`（`03-store` §5.1 判据）；集合文件与 `store` 自己的 `projects`、`plan` 的 `plans` **同形** |
| 拆 `inbox_archive` | 归档条目**不是只增不改**（它继承自 `items` 里同一条）→ 拆开 = **复制一份**，制造两个事实源（L1 **D1**）                      |
| 加 `inbox_log`     | 生命周期只有两步（§3.3）→ 轨迹是噪音（A1）。**`store` 的 `log` 形态已就绪，需要时纯加法接入，不必现在做**                              |

★ **合并也不新造 `kind`** —— 产物与源**都在同一个 `inbox.json` 里**（产 = 新增一条 `Item`；源 = 改 `status` / `target`）→ 一次 `merge` 仍是**对同一份文件的一次 `write`**（§6.3）。

**校验**（**结构层**，L1 B / **C3**）：类型 / 必填 / `status` 词表取值 / `id` 唯一 · `id` 前缀与递增格式 · **`status != open` 时 `target` 必填**（条件约束）。

> **`id` 唯一 + 递增的落地**：schema 管**单份文件的形状**（唯一性可用 `uniqueItems` 一族表达不了 id 字段，故由**用例**在写入前分配 **`max(已有) + 1`**）—— 与 `06-plan` 同理：**单条结构归 schema，跨记录归用例**（`03-store` §6.4 边界不破）。★ `merge` 的产物也走**同一条分配规则**。

**版本控制**：随 `.forge/` **整体入库**（`03-store` §5.4，S1 = B）→ `inbox.json` 天然可 diff、有历史。

**接入是"零改动"**：新模块只需**加一份 schema 文件**，`store` 读写逻辑不动（`03-store` §6.4）。

## 6. 接口

### 6.1 底层：只用 `store` 的三个原语

| 动作      | 怎么走                                             |
| ------- | ----------------------------------------------- |
| 读       | `store.read("inbox")`（缺文件 = **空数据**，不报错）         |
| 写       | 读 → 改 → `store.write("inbox", value)`（**校验后**落盘） |
| 查（按 id） | `store.query("inbox", "items", [{"id": …}])`    |

### 6.2 语义操作层（§2 的操作面，落在这里）

§2 的写动词**不是** `store` 的原语 —— 它们是 `inbox` 提供的**语义操作**，内部**组合** `store` 调用。**规则：一次写操作 = 一次 `read` + 一次 `write`（同一份文件）。**

```
inbox add "…"        ──▶  read("inbox") → 追加 Item（分配 id、status=open、created=今天）→ write("inbox")
inbox merge INB-001 INB-004 --text "…"
                     ──▶  read("inbox") → 新增 1 条 Item（id=max+1、status=open、text=…）
                          + 源 2 条 → status=handed、target="并入 INB-005"
                          → write("inbox")            ← ★ 一次写里同时完成"产 + 源"，原子
inbox hand INB-003 --to "…"  ──▶  read("inbox") → 找到 003 → status=handed、target=… → write("inbox")
inbox drop INB-003 --to "…"  ──▶  同上，status=dropped
inbox set INB-003 --tag 体验  ──▶  read("inbox") → 改非状态字段 → write("inbox")
```

| 要点              | 说明                                                                              |
| --------------- | ------------------------------------------------------------------------------- |
| **不新增写路径**      | 仍**全经 `store`**（L2 §1 规则 3 · §2.2 **W3**）；`inbox` 只是**组合**它                        |
| **一次 agent 调用** | 上面每一步对 agent 是**一次调用**（H3）—— agent 不需要知道"读一份、写一份"                                 |
| ★ **`merge` 的原子性** | N 条源的状态变更 **+** 1 条产物的新增，**在同一次 `write` 内**完成 → **不存在"改了一半"**（§6.3）              |
| **无旁路**         | `inbox` 是**人 + agent 共用**的（L0 §2）：人在 CLI 上改、agent 经 skill 改 —— 两者都**只经 `store`**  |
| **命令表面归入口层**    | 具体 `forge inbox …` 的拼法归**入口层**（§9 **T5**）；但**操作集由本模块定义**（H5：按完整流程设计）             |

### 6.3 失败语义

> ★ **读函数 = 对外表面**：本节 §6.2 的 `list_items()` / `show_item()` **不只在 `forge inbox` CLI 内部使用** ——
> 它们是 `inbox` 对**其他模块**的**公开读面**（现由 `workbench` 消费，L2 §4.2.1）。**改它们的签名 / 返回形状 = 改对外契约**。
> ★ 相应地：`workbench` **不 import 本模块内部实现、不读 `.forge/inbox.json`** —— 一律经这两个读函数。

**只有一次 `write`**（单份文件，原子替换）→ ★ **不存在 `06-plan` §6.3 / T7 那种"两次写一半成功"的问题**。
`inbox` 是本设计的**顺带收益**：`plan` 之所以有两次写，是因为它拆了 `plans`（状态）+ `plan_log`（轨迹）两个 `kind`；`inbox` 只有一份，天然免掉。

> ★ `merge` **不破坏**这条收益：它的"产 + 源"看似多步，实则**同属一份 `inbox.json`** → 仍是一次原子替换。**这是"只用一个 `kind`"换来的**（§5）。
> 仍然成立的一条：**缺文件 = 空数据**（首次使用即此状态）—— `inbox.json` 不存在时 `list` 给空、`add` / `merge` 正常创建。

| ★ **不加 `mergedInto` / `mergedFrom` / `group` 字段** | 溯源已在源条目的 `target` 里 → 反查即可（L1 **D2**：派生不落盘）。噪音大时再走 §9 **T9**                                       |

| **不做轨迹（`inbox_log`）**              | 生命周期只有两步（§3.3）→ 噪音（A1）。机制已就绪，需要时纯加法                                                           |
| **不做 `check` 命令**                 | `store` 的 schema 校验已覆盖（`03-store` §6.5）—— forge 的载体有 schema，写入即校验（L1 **B / C3**）                  |
| **不做优先级 / 排序 / 标签词表**             | 优先级是**读时判断**（§3.3）；标签**有意自由**（§4）                                                                          |
| **不做提醒 / 截止日 / 逾期**                | 治"记住不丢"，不治"到点提醒"（§3.3）                                                                                        |
| **不建到 aiwf 的外键**                   | L0 §4.1                                                                                                |
| **不落"收件箱报告"给人看**                   | 要给人看 → 渲染 `list` 视图（L1 **D2**：派生不落盘）                                                                        |

## 10. skill 文本约束（引擎不做的事 —— 落到入口层 skill）

> **为什么有这一节**：L1 约定 **B** —— 引擎只做确定性事项，**其余归 agent + skill**。
> 本模块的**判断类职责**（合并 / 去留 / 去向 / 时机）**全部**落在 skill 文本上（归**入口层**，§9 **T5**）。
> **本节只列"要约束什么"，不写 skill 正文** —— 正文在入口层，按**渐进披露**落 `skills/forge/references/inbox.md`。

| 引擎**不做** | skill 文本要写什么 | 依据 |
| --- | --- | --- |
| **合并判断**（哪几条是一件事） | 判据 + 例子（"同一主题 / 同一处体验问题 / 同一模块的相邻改进"）；★ **宁少合、不合错** | L1 **B** + §2.3 场景 C |
| **合并时机** | 两个节点：① **人明确要求**（"看看还欠什么" / "整理下 inbox"）② **提升为需求之前**；★ **不在 `add` 时合** | §2.1 纪律 5 |
| **不做聚类 / 分组** | 靠 agent 自己 `list --full` 判断；**引擎没有分组视图**（别去找 `--by-tag`） | §8 |
| **不做人门** | agent 判完**直接落盘**；主人只在「**提升为需求**」那步把关 | §8 |
| **不设撤销** | 合错就 `add` 一条正确的；★ **不要试图**改 `.forge/inbox.json`（不直读文件，§2.1 纪律 3） | §8 + §9 **T8** |
| **不做外键** | `--to` / `--source` 是**文本**，**不校验**目标是否存在 | L1 **E1** + §7 |
| **归属先分流** | 属当前在推的计划 → `plan add`；**只有不属于任何计划、或现在不做**的才进 inbox | §2.1 纪律 1 |

> ★ **skill 是"判断"的落点**（L1 B）；**引擎是"存储 + 结构校验"的落点**。两者**不重叠** —— 本节里没有一条能被写成确定性函数（否则它就该归引擎了）。
