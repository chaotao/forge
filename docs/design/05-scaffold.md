# forge · L3 模块设计 —— `scaffold`

> 层级：**L3**。上游 = **L2 概要架构与模块划分**（`02-architecture.md`）。
> 本文件写 `scaffold` 的**核心设计**；**实现以 `forge/scaffold.py` 为准**。

---

## 1. 职责与边界

**一句话**：`scaffold` 把**一份蓝图**落成一个**能开工的项目骨架**，并管住**后续往项目里加组件**（依赖管理）。

|         | 内容                                                                                                                                                                                                                                                            |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **做什么** | ① **蓝图**（库 / 模型 / 选择）② **落位**（`resolve` → `decide` → `apply` → 报账）—— 分**两类**：**自落**（`payload:`，自己写）· **委托**（`skill:` / `aiwf:`，交上游工具写）③ **依赖管理**（增量机制 → 入口层 `forge sync`，见 §5.4） |
| **不做**  | ① **不做代码生成**（L0 §4.3：「forge 是编排层，不是代码生成器」）—— 落的是**静态内容**，**不做变量渲染**<br />② 不写 `.forge/`（W3）<br />③ **不自己取件、不自己复制外部组件** —— 外部组件的安装一律**委托上游工具**（§4.2）<br />④ 不重管 aiwf 的 `.aiwf/installed.json`（那是 aiwf 的状态）<br />⑤ 不做语义判断（L1 约定 B）<br />⑥ 不解析上游 CLI 的文本输出（§4.3） |

### 1.1 两类落位（本模块的骨架）

蓝图的每个 `Item` 按 `from` 前缀落进**两类之一** —— 这两类的**判定、执行、报账全都不同**：

| 类别        | `from` 前缀             | 谁动手                                  | 落点谁定                | 判定谁做     | 进 lock 吗     |
| --------- | -------------------- | ------------------------------------ | ------------------- | -------- | ----------- |
| **自落**    | `payload:`           | **`scaffold` 自己写**                    | **蓝图声明**（`to`）      | `scaffold`（§3.4） | **进**（§3.6） |
| **委托**    | `skill:` · `aiwf:`   | **上游工具**（`skill install` / `aiwf wf install`） | **上游**（forge 不声明、也不知道） | **上游**   | **不进**（§3.6） |

> **「确保 skill 和 aiwf 都使用各个工具自己的能力去安装，不重复造轮子，蓝图只需要关联名字即可」**
> —— 动机是 L1 约定 **A1**（不重复造轮子 = 不自建一套「取件 + 复制 + 落点表」）与 **D**（一份数据一个权威来源：
> 组件怎么装、装哪去，权威在**上游**，forge 复述一份就是第二事实源）。
> **代价照实说**：forge 对委托结果**没有直接观测**（不入 lock）→ 见 §7 **T6**。

### 1.2 它写项目里的什么（L2 §4.3 的命名空间划分，本文件照用）

| 项目内路径                             | `scaffold` 做什么                                                            |
| --------------------------------- | ------------------------------------------------------------------------- |
| **`.forge/`**                     | **一个字节都不写** —— 归 `store`（L2 §2.2 **W3**）；lock 由它**委托** `store` 写                 |
| **`.aiwf/`**                      | **由 aiwf 自己写**（`scaffold` 委托 `aiwf wf install`，见 §4.2）；`scaffold` 不直接落笔 |
| **其余**（骨架 / 配置 / 脚本 / skill 落点 …） | **`payload:` 项由它写**；**`skill:` 项由 skill-library 写**；同一份产物只有一个写者（**W2**）     |

**与其它用例的界线**（L2 §2.2 **W1**「谁产出谁写」）：`scaffold` 只写**蓝图声明的那些 `payload`**；
别的用例将来往项目里落自己的产物（如 `plan` 落给人看的计划书），**不经 `scaffold`** ——
这正是 L2 删掉「项目业务内容的唯一写者」的动机（§2.2 原文：产物形态各异、无统一 schema 可约束）。

## 2. 蓝图

### 2.1 它是什么

**蓝图 = 一份有序的「落什么」清单 + 一份自带 payload。** 覆盖 L0 §3 列的四类内容 —— **两类自落、两类委托**：

| L0 §3 的类     | 蓝图里怎么表达                                  | 类别     |
| ------------ | ---------------------------------------- | ------ |
| **目录**       | `payload:` 指向一棵目录树                       | **自落** |
| **脚本**       | `payload:` 指向文件                          | **自落** |
| **Skills**   | `skill:<组件名>` —— **委托 skill-library 安装** | **委托** |
| **aiwf 工作流** | `aiwf:<组件名>` —— **委托 aiwf 安装**           | **委托** |

**它是声明，不是逻辑** —— 蓝图里没有条件、没有分支、没有代码。
依据：L0 §4.3（forge 不是代码生成器）+ L1 约定 **B**（引擎负责的是**确定性变换**：路径计算 / 复制）。

### 2.2 模型

```
Blueprint {
  version:     int          # schema 版本（L1 C4：模型变更须显式动作）
  id:          string       # 与所在目录名**一致**（§2.3）
  description: string?      # 一句话，给人看（将来的 `blueprint list` 用）
  items:       [Item]       # **有序** —— 顺序 = 落位顺序
}

Item {
  from: string              # 来源（§2.4，三路来源的前缀语法）
  to:   string?             # **目标项目内**的相对路径 —— **只属 `payload:` 项**（§2.4）
}
```

**`to` 为什么只属 `payload:` 项**：`to` 是**落点声明**。自落项的落点由蓝图定（forge 自己写，它必须知道写哪）；
委托项的落点**归上游**（§2.4）—— 蓝图在这里写一个 `to` 就是**替上游瞎猜**，而 forge 又不会去用（§3.4）。
故：**`payload:` 项必填 `to`；委托项不得有 `to`** —— 由 **schema 的 `allOf` / `if` / `then` 强制**（§2.5）。

**模型只有这两个字段，是刻意的**：

| 没写进去                       | 为什么                                                                 |
| --------------------------- | ------------------------------------------------------------------- |
| `op`（`write` / `copy_tree`） | **由来源形态推出**（取到的是一个文件还是一棵目录树），不需要人再声明一次（§3.2）                        |
| 渲染变量 / 条件                   | 暂不做：蓝图落**静态内容**，需要因地制宜的部分**由 agent 改**（L0 §2 人 + agent 分工）       |
| 落点（对委托项）                    | **归上游**（§2.4）；蓝图**只关联名字**                                           |
| 校验 / 判据                     | **归 agent**（L1 约定 B：**引擎不实现「判据核对器」**）                               |

### 2.3 蓝图库

```
forge/blueprints/                  # 蓝图库（**包内**，随 forge 发布）
  blueprint.schema.json            # 蓝图模型的 schema（§2.5）
  <id>/                            # 一个蓝图 = 一个目录
    blueprint.json                 # 清单（§2.2）
    payload/                       # 自带内容 —— `payload:` 的**寻址根**
```

**库在包内** —— 不落 `FORGE_HOME`、不落 `.forge/`。

| 依据                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `03-store` 的**同一条判据**：资产是**代码**、不是**数据**；放进数据目录会**制造第二个写者**，破 L2 §4.3「一个目录一个写者」                                                         |
| L2 §1 规则 3（**出口收敛**）：写 forge 自有状态只经 `store` —— 蓝图库若落在 `FORGE_HOME`，就得由 `store` 认领成一个 `kind`，那是给资产套数据的壳                                           |
| 同构既例：aiwf 的模板库在**仓库** `library/workflows/`（实测 `engine/aiwf/library.py:45–55`）；`skill-library` 的技能内容在**注册表** `skills/`（实测 `src/core/registry.ts`） |

**库位置可覆盖**：`FORGE_BLUEPRINTS_DIR` 环境变量，或 `--blueprints <dir>` 参数 —— **替换**语义（不叠加，A1）。
既例 = aiwf 的 `AIWF_LIBRARY_DIR` / `--library`。

**⚠ 覆盖只换「内容」，不换「模型」**：`--blueprints` 指向的库里**只要 `<id>/` 目录**；
蓝图**模型**的 schema **随 forge 发布**（包内 `forge/blueprints/blueprint.schema.json`），
**永远取自包内** —— 用户库**不必**带 schema，带了也**不生效**。
依据：L1 约定 **C2**（模型是唯一事实源）+ **D**（否则用户库就成了模型的第二事实源）。

**扫描只认子目录**：库根下的 `<id>/` 才是蓝图，`blueprint.schema.json` 之类的同级文件**天然被忽略**。
（aiwf 在这里踩过坑 —— 它的元信息文件**必须**另放 `meta/`，因为 `list_workflows` 会把目录下所有 `*.json` 当定义读，一旦被复制进项目就让 `validate` 失败。forge 取「只认目录」这条更省事的路。）

**「一个蓝图 = 一个目录」的三个好处**：① 清单可校验；② payload 是**普通文件**（人可读 / 可 diff / 可入库，L2 §5.1 Q3 约束②）；③ `id` 与目录名不两处维护（§2.5 校验其一致）。

### 2.4 来源：`from` 的语法

**格式 `<来源种类>:<组件名>`**，三个前缀 ↔ **两路来源 · 两类落位**：

| `from`               | 来源                    | 寻址根谁定                                | 形态             | 类别     |
| -------------------- | --------------------- | ------------------------------------ | -------------- | ------ |
| **`payload:<相对路径>`** | **蓝图自带**              | **本模块**（该蓝图目录下的 `payload/`）           | 按磁盘实际（文件 / 目录） | **自落** |
| **`skill:<组件名>`**    | **skill-library 注册表** | **上游**（skill-library 自己找注册表）           | 上游定（目录树）       | **委托** |
| **`aiwf:<组件名>`**     | **aiwf 库**            | **上游**（aiwf 自己找库 `library/workflows/`） | 上游定（单文件）       | **委托** |

**委托项的名字就是「喂给上游 CLI 的那个 id / 名字」** —— 蓝图**只负责关联名字**，不负责说明它在哪、落哪：
`from: "skill:skill-manager"` → `skill install skill-manager`；`from: "aiwf:std.review-check"` → `aiwf wf install std.review-check`。

**与 `lock.entries[].from` 的映射**（`03-store` §4.2 的模型；值对齐其 §3.2 已给的实例）：

| `Item.from` | 写进 lock 的 `from`                                  | 说明                       |
| ----------- | ------------------------------------------------- | ------------------------ |
| `payload:*` | **`blueprint:<蓝图 id>`** —— 自带 payload 的「组件」就是蓝图本身 | ✅ **进 lock**             |
| `skill:<名>` | ——                                                | ❌ **不入账**（§3.6；权威在 skill-library） |
| `aiwf:<名>`  | ——                                                | ❌ **不入账**（§3.6；权威在 aiwf）    |

> `payload:` 只是**库内寻址**，不是一种「来源种类」；lock 记的是**来源种类 + 组件**，
> 故 payload 项收敛到 `blueprint:<蓝图 id>` —— 与 `03-store` §3.2 实例里的 `"from": "blueprint:minimal"` 同值。

**为什么 forge 不读 skill-library 的 agent 表 / aiwf 的库根**：

| 判据                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------- |
| **落点归上游** —— 组件装哪去是上游自己的事（skill-library 按它的 agent 表、aiwf 按 `.aiwf/`）；forge 复述一份 = **第二事实源**（L1 约定 **D**）   |
| **A1** —— 读上游 config 会把 forge 绑在**它的配置形态**上（实测 `skill-library` 的 agent 表在 `~/.skill-library/config.json`，aiwf 的库根在 `AIWF_LIBRARY_DIR` / 仓库内） |
| **A1** —— 曾打算「蓝图声明落点 → 同一组件落多个 agent 目录要写多条 `Item`」；委托之后**这个问题连同它的简写需求一起消失**      |

### 2.5 蓝图 schema 与校验

**`forge/blueprints/blueprint.schema.json`** —— 与蓝图库**同级**，**不放 `forge/schemas/`**。

> ⚠ 为什么不去 `forge/schemas/`：那个目录是 **`store` 的 `kind` 目录** —— `03-store` §6.2 / §6.3 已定
> 「**`kind` 表由该目录派生**」。把蓝图 schema 放进去，`store` 会多认一个 `kind`（而蓝图不是它的数据）
> → 当场制造不一致（L1 约定 **D**）。
> **规则**：**`forge/schemas/` 只收 `store` 的 `kind`**；其它模块的模型 schema 与自己的资产放一起。

**`to` 的两条互斥规则由 schema 声明**（`allOf` / `if` / `then`）：

| `from` 前缀      | `to`          | 理由                        |
| ------------- | ------------- | ------------------------- |
| `payload:`    | **必填**        | 自落项必须知道写哪（§2.2）           |
| `skill:` / `aiwf:` | **不得出现**（`false`） | 委托项落点归上游，写了也是瞎猜、且不会被用（§3.4） |

**校验只到结构层**（L1 约定 **C3**：只到结构层 · **B**：不做语义）：

| ✅ 检查                                                                | ❌ 不检查                           |
| ------------------------------------------------------------------ | ------------------------------- |
| 合法 JSON · 类型 / 必填 · `id` **与目录名一致**                                 | 「这份蓝图适不适合这个项目」—— **归人 / agent** |
| `from` 前缀在词表内；**`payload:` 项引用的文件/目录在 `payload/` 内存在**             | 组件内容对不对（那是上游 / 人的事）             |
| **`payload:` 项**的 `to` 是**项目内相对路径**：不逃逸（无 `..`）、**不以 `.forge/` 开头**（W3） | 委托项引用的组件**是否存在**（归上游判定）          |
| **`payload:` 项**的 `to` **在同一蓝图内唯一**（**W2**：一份产物一个写者）                |                                 |
| **委托项**的组件名**非空**                                                    |                                 |

> **委托项为什么要「名字非空」** —— 它是唯一能传给上游的参数；空名字在 CLI 层就是错的，**当结构错误拦下**更省事。

## 3. 落位机制

### 3.1 四步

| 步           | 做什么                                                        | 约束                                        |
| ----------- | ---------------------------------------------------------- | ----------------------------------------- |
| ① `resolve` | 按 `Item.from` 去来源取件，回答「**有没有、形态是文件还是目录、内容在哪**」—— **只对 `payload:` 项** | **只读，绝不写盘**                               |
| ② `decide`  | **`payload:` 项**：查目标项目，定 `op`（§3.4 的 2×2）；**委托项**：直接定 `delegate` | **全流程唯一有分支的地方**                           |
| ③ `apply`   | **严格按序**执行：`payload:` 项自己写；`skill:` / `aiwf:` 项调上游 CLI（§4.2）   | 不做事务 / 回滚（§3.5）                           |
| ④ `report`  | **`payload:` 项**产出的 `Entry[]` 交 **`store`** 写 `.forge/lock.json` | `scaffold` **不落自有状态**（L2 §1 规则 3 + 不变量 1） |

**为什么 ①+② 合成一个纯函数**：让「**预演**」与「**执行**」**共用同一份逻辑** ——
同一段代码产出 `ChangeSet`：预演把它打印出来就结束，执行送给 `apply`。
这是「**停手呈交**」的载体，也直接决定接口只有两个原语（§5.1）。

### 3.2 `ChangeSet` 与 `op`

```
ChangeSet {
  version:   int            # schema 版本
  blueprint: string         # 蓝图 id（→ Lock.blueprint）
  actions:   [Action]       # **有序** = 执行顺序
}

Action {                    # **与蓝图的 Item 同形**
  op:     string            # "write" | "copy_tree" | "skip" | "refuse" | "delegate"
  from:   string            # = Item.from（来源标识）
  to:     string?           # = Item.to —— **只有自落项有**；`skip` / `refuse` / `delegate` 不记
}
```

| `op`            | 含义                              | 由谁定                | 作用于        |
| --------------- | ------------------------------- | ------------------ | ---------- |
| **`write`**     | 写**单个文件**                       | `decide`（落 / 不落）   | `payload:` |
| **`copy_tree`** | 复制**一棵目录树**                     | `decide`（落 / 不落）   | `payload:` |
| **`skip`**      | 目标已存在且**在 lock 里** → 不动它         | `decide`           | `payload:` |
| **`refuse`**    | 目标已存在且**不在 lock 里** → 拒绝，报给人   | `decide`           | `payload:` |
| **`delegate`**  | **交上游工具安装**（`skill install` / `aiwf wf install`） | `decide`（**无条件**） | `skill:` / `aiwf:` |

**`write` / `copy_tree` 不是判定结果** —— 由 `resolve` 给出的**来源形态**决定（§2.2）。
**`delegate` 也不是判定结果** —— 委托项**不进 2×2**（§3.4）；它的成功与否**在上游**。

> **模型里没有 `reason`**：人类可读的说明（「委托 `skill install X`」/「目标已存在且不在 lock」）
> **由入口层按 `op` 派生**，不占模型字段。依据：L1 约定 **B**（**引擎不出文案** —— 与 §5.1 同口径）
> + **A1**（字段必须有机器读者；`reason` 原文自注“机器不读”）。

### 3.3 `actions` 有序

`actions` **不是集合**：落了上级才落下级、先落配置再落脚本，**顺序是语义的一部分**。
顺序 = 蓝图 `items` 的**声明顺序**，**不另定排序规则**（A1）。

> ⚠ **委托项也占这个顺序** —— 如果蓝图里 `payload:` 与 `skill:` 混排，`apply` 就**按混排后的顺序**执行。
> 这条**不额外做拓扑排序**（A1）：需要「先建目录再装 skill」的蓝图，**自己把顺序写对**。

### 3.4 判定（2×2）—— **只作用于 `payload:` 项**

| 目标路径    | 在 lock 里？ | `op`                         | 要不要人介入                             |
| ------- | --------- | ---------------------------- | ---------------------------------- |
| **不存在** | —         | `write` / `copy_tree`（按来源形态） | 否                                  |
| **已存在** | **否**     | **`refuse`**                 | **是** —— 只报给人，`scaffold` **不自行处置** |
| **已存在** | **是**     | **`skip`**                   | 否                                  |

**「在 lock 里」怎么判**：该 `path` 是否出现在 `Lock.entries[].path` —— **不比对内容**
（`03-store` §4.2 已明确「不写内容哈希」，L2 §5.2 已把哈希与 `conflict` 列**推后**）。

→ **后果照实说**：既然不比对内容，「有 lock → `skip`」**不保护用户手改过的文件** —— 它会静默跳过。
这不是漏设计（`conflict` 与 `skip` **行为完全相同**，差别只在报不报），
故推后**不损失安全性，只损失可观测性**（L2 §5.2 的裁定原文）。

**为什么委托项没有这张表**（三条）：

| # | 理由                                                                                            |
| - | --------------------------------------------------------------------------------------------- |
| ① | **forge 不知道上游落点** —— `skill install` 落进「每个启用 agent 的项目目录」，具体几个、叫什么，由 skill-library 的 agent 表决定（§4.2 实测） |
| ② | **forge 无权判定** —— 目标是否存在、要不要覆盖，是**上游自己的策略**（如 aiwf 按 `.aiwf/installed.json` 判「是不是我装的」）           |
| ③ | **判定需要的信息在 lock 里**，而委托项**不入 lock**（§3.6）→ 想判也判不了                                                |

**`--force` 的作用范围**：① 把 `payload:` 项第 2 行的 `refuse` 改判为落，**其余两行不变**（A1：不做细粒度豁免机制）；
② 对委托项 = **透传给上游 `--force`**（`skill install --force` / `aiwf wf install --force`）—— forge 只转发，不解释。

**`refuse` 不是错误** —— 它是 `ChangeSet` 里的一种正常 `op`：预演时就能看见，给人决定「改路径 / 删目标 / 加 `--force`」。

### 3.5 执行与幂等

| 项  | 结论                                                                                                                             |
| -- | ------------------------------------------------------------------------------------------------------------------------------ |
| 写法 | `write` = 临时文件 → **原子替换**（同 `03-store` §5.3 的 snapshot 写法）；`copy_tree` = 逐文件按 `write` 落；`delegate` = 调上游 CLI，**CWD 显式设为目标项目根**（§4.2） |
| 顺序 | **严格按 `actions` 顺序**，不重排、不并行                                                                                                     |
| 失败 | **失败即停**（fail-fast）—— **不做回滚**                                                                                                   |
| 报账 | **失败之前已成功的项照常报账** → 账落在**实际落下的那些 payload 项**上                                                                                  |

**幂等从哪来**：

| 上次跑到哪 | 重跑时会发生什么                                        |
| ----- | ----------------------------------------------- |
| 全部成功  | `payload:` 项「已存在 + 在 lock 里」→ 全 `skip` → **一个字节都不写**；委托项**重跑上游命令**（它自己幂等） |
| 中途失败  | 已成功项 `skip`；失败项与未执行项仍是「不存在 / 无 lock」→ **接着往下落** |

→ **「逐项落账 + 重跑幂等」代替事务。没有回滚，也不需要回滚**（L2 §5.2 不做文件系统事务）。

> **委托项的幂等「不是 forge 的保证」** —— 上游命令**没有 `--dry-run`**（§4.3），forge 只能**照发**；
> 「重复装会不会有事」的权威答案在上游（`skill install` 覆盖同目录、`aiwf wf install` 按自己的账本判）。
> 这条**登记为代价**（§7 **T6**），不假装我们保证了。

### 3.6 报账（`report` → `Lock`）

`report` **不做设计** —— 它只是把执行结果**按 `store` 已定的模型**交出（`03-store` §4.2）：

| `ChangeSet` → `Lock`                      | 规则                                            |
| --------------------------------------- | --------------------------------------------- |
| `blueprint`                             | 原样 → `Lock.blueprint`                          |
| `op` = `write` / `copy_tree` **且执行成功**   | 各生成一条 `Entry { path, from: "blueprint:<id>" }` |
| `op` = `skip` / `refuse`                | **不生成**（`skip` 的项本来就在 lock 里）                  |
| **`op` = `delegate`**                   | **不生成**（§3.6.1）                               |
| 执行**失败**的项                              | **不生成** → 重跑时仍是「无 lock」，会**再试一次**（§3.5 靠这个成立） |

**与既有 lock 的合并**：`report` **按 `path` 归并**（新结果覆盖同 `path` 的旧条目）+ **排序**。
这不是「顺手做的」—— 它是 §3.5「中途失败后接着往下落」的**前提**：重跑时**不能丢掉上一轮的账**，
否则已成功的项在第二轮就变成「不在 lock 里」→ 被判 `refuse`。归并 + 排序同时满足 L1 约定 **G**（确定性可回归）。

#### 3.6.1 委托项为什么**不入账**

| # | 依据                                                                                                                            |
| - | ----------------------------------------------------------------------------------------------------------------------------- |
| ① | **权威在上游**（L1 约定 **D**）—— 装了哪些组件、装的什么版本，权威在 `skill-library` 的注册表 / aiwf 的 `installed.json`。forge 在 `lock.json` 复述一份就是**第二事实源** |
| ② | **记了无处用** —— `decide` 不判委托项（§3.4 三条理由）、`report` 不产委托条目，lock 里这一行**没有任何读者**                                                    |
| ③ | **`Entry.path` 是单值，填不出** —— `skill install` 会落进**多个** agent 目录（实测 4 个），而 `Entry` 只有**一个** `path` 字段 → 想记就得改 `store` 的模型（**C4：实现不得私自扩展模型**）  |

> **核过一遍**：`Lock { version, blueprint, entries[{path, from}] }` 对 `scaffold` **够用**，
> **不要求 `store` 扩充模型**（L1 约定 **C4**：实现不得私自扩展模型；**D**：写者 = 持久化权威）。
> 唯一已知的将来扩充点：`Lock.blueprint` 是**单值**，若将来一次落位含多个蓝图，需扩成列表 ——
> 那是 **A3 允许的向后兼容扩充**（字段 → 实体），登记 §7 **T2**。

## 4. 两类落位：自落 与 委托

### 4.1 自落（`payload:`）—— 一个只读接口

```
resolve(from) → (形态: file | tree, 内容位置) | None
```

- **自落目前只有一个实现**（`payload:` → `<蓝图目录>/payload/…`，本模块自定，§2.3）。
- **接一个「新的自落来源」 = 加一个实现 + 加一个 `from` 前缀** → `ChangeSet` 与 `lock` 的模型**都不动**
  —— L2 §2.5 的 L3 承接约束（用例读素材须经**自己的**来源适配器，接新来源不必动数据访问层构成）。
- 内容位置是**本机路径**；`apply` 只做「读它 / 复制它」。
- **接一个「新的委托来源」** = 在 §4.2 的表里**加一行**（命令 + 要清的环境变量），同样**不动任何模型**。

> ⚠ 委托之后 `skill:` / `aiwf:` **不再需要 forge 去解析** —— 注册表根、库根、落点全归上游，`resolve` 只剩 `payload:` 一个实现。
> **接口反而更瘦了**：这是 L1 约定 **A1**（最小可用）的正收益。

### 4.2 委托（`skill:` / `aiwf:`）—— 实测与三条约束

**实测结论（临时目录，未碰真实环境）**：

| # | 项               | 结论                                                                                                        |
| - | --------------- | --------------------------------------------------------------------------------------------------------- |
| 1 | **命令（skill）**   | `skill install <组件名>`                                                                                     |
| 2 | **命令（aiwf）**    | `aiwf wf install <组件名>`                                                                                   |
| 3 | **CWD（共同）**     | **必须显式设为目标项目根** —— 两个上游**都按 CWD 认项目**；不给 CWD 就落到**调用者的当前目录**                                                |
| 4 | **落点（skill）**   | 上游按**自己的 agent 表**，落进每个启用 agent 的**项目目录**（相对 CWD）→ 实测落出 **4 个**（`skill-manager` 在 4 个 agent 目录各落一份 `SKILL.md`） |
| 5 | **落点（aiwf）**    | `<项目>/.aiwf/workflows/<id>.json`（另维护 `.aiwf/installed.json`）                                              |
| 6 | **环境（aiwf）**    | 落点受 **`AIWF_HOME`** 影响（`Storage.root` = `AIWF_HOME` 或 `.aiwf`，相对 CWD）→ **必须清掉它**，否则整份 `.aiwf/` 会搬走          |
| 7 | **成功判据（共同）**    | **退出码** —— 两个上游**都没有 `--json`、没有 `--dry-run`**（实测）→ 预演做不出来、也不能解析文本                                           |

**→ 三条约束（写进实现）**：

| # | 约束                                                                                                                                                         | 依据                    |
| - | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| ① | **CWD 显式 = 目标项目根**（`subprocess` 的 `cwd=`，不用 `os.chdir` —— 不改进程状态）                                                                                           | 实测 3                  |
| ② | **清掉会整体改道的环境变量** —— 目前只清 **`AIWF_HOME`**；**保留** `SKILL_LIBRARY_*`（它们只影响**素材从哪读**，不改变**落点**）                                                                       | 实测 6 + L1 约定 **D**     |
| ③ | **成功判据 = 退出码**；失败时**只把上游输出的最后一行**当给人看的提示，**不做解析**                                                                                                           | 实测 7 + L1 约定 **B / G** |

**委托项在 `preview` 里长什么样**：`op = "delegate"`，`from` 原样，**无 `to`** —— 人类可读的「委托 `<程序>` 安装」**由入口层按 `op` 渲染**（§3.2）。
—— **预演能告诉你的只有「会调哪条命令」，不能告诉你「会落哪些文件」**。这条**登记**（§7 **T6**）。

### 4.3 明确不做

| 不做                                              | 为什么                                                                                                            |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **不自己取件 / 不自己复制外部组件**                           | **重复造轮子**还会造出第二事实源（L1 约定 **D**）—— 落点 / 判定 / 账本都在上游                                                       |
| 不重管 aiwf 的 `.aiwf/installed.json`               | 那是 aiwf 的状态；forge 侧**只记自己的 `lock.json`**（且只记 payload 项）                                                          |
| **不解析上游 CLI 的文本输出**                             | 两个上游**无 `--json`**（实测）；且 L1 约定 **G**（要能回归就得有确定结构，不是文本）                                                          |
| **不替上游做判定**（是否已装 / 要不要覆盖）                        | 判定需要的信息在**上游的账本**里（`installed.json` / 注册表），forge 拿不到也不该拿                                                      |
| **不在 lock 里记委托项**                               | §3.6.1 三条依据                                                                                                    |

> **一处已知摩擦（登记，不解决）**：`aiwf wf install` 这条路上，**forge 没有直接在 `.aiwf/` 落笔**（是 aiwf 自己落的），
> 所以 aiwf 认它是「自己装的」。但**两条账本仍各自独立、互不感知**（forge 的 `lock.json` 只管 payload；aiwf 的 `installed.json` 管它自己装的）——
> 这是 L1 约定 **D** 在跨工具场景下的**必然代价**，不是缺陷。

## 5. 接口

### 5.1 两个原语

| 原语            | 签名                                                                          | 写盘？                                            |
| ------------- | --------------------------------------------------------------------------- | ---------------------------------------------- |
| **`preview`** | `preview(blueprint_id, target_root, *, force=False, library=None) → ChangeSet` | **否** —— `resolve` + `decide`，**纯计算**        |
| **`apply`**   | `apply(changeset, target_root, *, force=False, library=None) → Result`（内含执行 + `report`） | payload 项写项目；**委托项调上游**；lock **委托** `store` 写 |

`Result` 最小形态：`{ applied: [Entry], skipped: [path], refused: [path], delegated: [from], failed: {from, to, error}? }`
—— **给人看的报告由入口层渲染**（本书不出文案，L1 约定 B）。

**`force` 为什么两个原语都要**：`preview` 用它算出「`refuse` 已改判为落」的 `ChangeSet`（预演与执行**必须一致**）；
`apply` 用它**透传给上游**（`delegate` 要加 `--force`）—— 同一份 `ChangeSet` 送给 `apply` 时，
预演用过的 `force` 若不一起带上，两次行为就**不一致**。故 `force` 是**两个原语共同的入参**，不是 `apply` 的私有开关。

**为什么叫 `preview` 而不叫 `plan`** —— **L1 约定 F2**：`plan` 是 forge 的**用例模块名**（`06-plan`），
这里再来一个就复制了 L1 §6 已登记的**第 ① 起撞名**。**冲突时改自己**的（**F1**：一个概念一个名字）。

**`ChangeSet` 不落盘**：预演的价值由**入口层输出**承载（打印 / JSON）。
若将来需要「跨会话审阅变更集」，那是**新的一份数据** → 须由 `store` 定一个 `kind`，
**不是 `scaffold` 私自落盘**（L2 §1 规则 3 出口收敛 + `03-store` §6.4 的接入机制）。

### 5.2 蓝图选择

| 项    | 结论                                                                                               |
| ---- | ------------------------------------------------------------------------------------------------ |
| 选择方式 | `forge new <路径> [--blueprint <id>]` —— **非交互**（L0 §2：入口两个，CLI 给人 / skill 给 agent；非交互才对 agent 可用） |
| 缺省   | **`minimal`**（包内必带的一个蓝图）                                                                         |
| 库列表  | 靠 `--blueprints` + 目录名即可；**不实现 `blueprint list` 命令**（归入口层）                              |
| 换蓝图  | `forge sync <路径> --blueprint <id>` —— **只增不删**；不是 `new` 的职责（§5.4）                        |

### 5.3 蓝图库内容

随包发布的产品蓝图（各自 `<id>/blueprint.json` + `payload/`，见 §2.3）：

| 蓝图          | 一句话                                       | payload（自落）                                                                                                        | 委托                                                       | 实测                                                                          |
| ----------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------- |
| **`minimal`** | 通用骨架：约定文件 + 忽略规则                            | **3 个文件**：`AGENTS.md` · `README.md` · `.gitignore`（**不含空目录**）                                                       | 0                                                        | ——                                                                          |
| **`novel`**   | 长篇小说创作项目：骨架文件 + 委托 aiwf 装上写作流程              | **4 个**：`AGENTS.md` · `README.md` · `.gitignore` · `novel/README.md`（`to` 带子路径，`novel/` 由 `_copy_file` 的 `makedirs` 建出） | **2 项**：`skill:aiwf` + `aiwf:std.novel-writing`            | `forge new <路径> --blueprint novel` → 写入 4 · 委托 2 · rc=0；lock 只含 4 条 payload     |
| **`drama`**   | AI 短剧创作项目：骨架文件 + 委托三个能力 skill              | **4 个**：`AGENTS.md` · `README.md` · `.gitignore` · `drama/README.md`（`drama/` 由 `_copy_file` 的 `makedirs` 建出）           | **3 项，全是 `skill:`、无 workflow 委托**：`skill:img-prompt` · `skill:comfy` · `skill:aiwf` | `forge new <路径> --blueprint drama` → 写入 4 · 委托 3 · rc=0；4 agent 各落 `img-prompt`(5) · `comfy`(29) · `aiwf`(28)；lock 只含 4 条 payload |
| **`godot`**   | Godot 4 游戏开发项目：工程骨架 + 约定文件 + Godot AI 插件 | **4 个文件 + 1 棵目录树**：`AGENTS.md` · `README.md` · `.gitignore` · `project.godot`，以及 `payload:addons/godot_ai` → `addons/godot_ai`（**`copy_tree`，247 文件 / ~2.0 MB**） | **0 项**（Godot 侧没有对应上游 CLI，插件只能作为 `payload:` 落）             | `forge new <路径> --blueprint godot` → 写入 5 · 委托 0 · rc=0；lock 5 条；插件 247 文件落齐；wheel 打包 **252 文件条目**（含 payload 点文件 `.gitignore` 与 122 个 `.uid`） |

**各蓝图的取舍**：

- **`minimal` 为什么不含目录树**：只需要一个能跑通闭环的骨架（A1）；空目录进 git 无意义，真需要时**由 agent 建**（L0 §2 人 + agent 分工）。
- **`novel` 是第一个含委托项的产品蓝图**：`minimal` 只覆盖「自落」，`novel` 把「payload 自落 + aiwf 委托」纳入产品库。
- **`drama` 是第一个「只有 skill 委托、没有 aiwf workflow」的产品蓝图**：
  - **为什么没有 workflow 委托**：短剧的创作链路（立项 → 剧本 → 分镜 → 提示词 → 出图 → 成片）目前只写在 `drama/AGENTS.md` 里、**由 agent 按链推进**，没有固化成 aiwf 工作流 —— 因为 **aiwf 库没有短剧流程**（现仅 `std.novel-writing` · `std.review-check` · `std.review-loop`），编一个出来属**越权**（形态选择，推不出来就不做）。要固化时用 `aiwf` skill 现建 —— 这也正是把 `aiwf` skill 装进项目的原因。
  - **为什么 `img-prompt` 与 `comfy` 拆两个 skill**：这不是本项目的设计，而是**上游既有分工** —— `comfy` 自己声明「提示词不在这里，由 `img-prompt` 产出」。forge 只**按名关联**，不重排上游（§2.4）。
  - **`img-prompt` 用连字符**：`skill-library` 注册表里的真名是 `img-prompt`（连字符）。下划线名从不存在，`skill install img_prompt` 会失败。
  - **⚠ 待拍板 —— `.gitignore` 的媒资策略**：默认挡 `drama/media/` + `*.mp4`。`img-prompt` 出词、`comfy` 出图与视频，**大文件**是这行的常态；几十上百 MB 的 `.mp4` 入 git 会让仓库迅速膨胀。若要留底，改走 Git LFS / 对象存储。
- **`godot`**：
  - **第一个「目录 payload（`copy_tree`）」蓝图** —— `minimal` / `novel` / `drama` 全是单文件；也是**第一个把第三方代码带进包**的蓝图。
  - **来源**：插件 = **Godot AI v3.1.2**（MIT，`github.com/hi-godot/godot-ai`），从 `mc-plus/addons/godot_ai` 整份复制入包；**随项目入库**（`.gitignore` 不忽略该目录）。
  - **为什么 payload 自带整份插件（而不是委托上游）**：Godot 插件不是 `skill:` / `aiwf:`，没有可委托的上游 CLI（§4.2 的委托路线以「有上游命令」为前提）；要「开箱即用」只能作为 `payload:` 由 forge 自己落。**代价**：包体 +2.0 MB 第三方代码，插件升级要人工跟上游。
  - **为什么插件随项目入库（而非照 `mc-plus` 忽略）**：`mc-plus` 的 `.gitignore` 忽略 `addons/godot_ai/`（注释称「由本地编辑器自行配置」）。**本蓝图不照抄** —— **入库**。三条理由：① **项目自洽可复现**：克隆下来插件就在，不必追问它从哪来；② 一旦忽略，`forge new` / `sync` **都补不回来**（§3.2 的判定是「`path` 在 lock 里 → `skip`」，**不看盘上在不在**）→ 忽略等于给每个新项目埋一个补不回的洞；③ 插件目录自带 `LICENSE`，入库后许可证随代码走，**无需**在库根另留副本。
  - **`plan/` · `inbox/` 为什么不进蓝图**：`mc-plus` 用 `plan/<计划名>/` + `inbox/` 两套目录记计划与念头 —— 这两件事**已归 `forge`**（`forge plan …` / `forge inbox …`）。蓝图**不落这两类目录**，`AGENTS.md` 明写「不要建 `plan/` · `inbox/`」，免得项目里长出第二套并行台账（L1 **D**）。

> **`AGENTS.md` 里 `forge plan` 的口径**（`minimal` / `novel` / `drama`）：以工作流 / 链路为主的**轻量级项目**设为「**默认不用（可选）**」—— 进度源是产物本身或 `.aiwf/runs/`；「计划 → 任务」账本留给**计划多、周期长的开发类项目**（`minimal` 相应标注「可选 · 开发类受用」）。

> ⚠ **一条已知妥协（不阻塞，未做）**：§3.2 的 `skip` 判定**不看存在性** —— 凡「在 lock 里、盘上却被删」的项，`new` / `sync` 都补不回来。改进方向：改为「在 lock 里**且存在**才 `skip`」；涉及 §3.4 的判定口径与 `skip` 语义。

### 5.4 依赖管理：`forge sync`

**增量入口只有一个命令** ——

```bash
forge sync <路径> [--blueprint <id>] [--blueprints <dir>] [--force] [--dry-run] [--json]
```

| 情形 | 行为 |
| --- | --- |
| 目标**未受管** | **拒绝**，提示 `forge new`（`sync` 只做增量） |
| 目标目录**不存在** | 拒绝 → **要人介入**（受管记录指向一个空位） |
| 已受管、`--blueprint` **未指定** | 用**登记值**对齐 |
| 已受管、`--blueprint` **指定且不同** | **换蓝图**（显式给出；`new` 对不一致的蓝图只拒绝并指到这里） |
| 落位 | 与 `new` **同一条链路**（`preview` → `apply` → 报账）→ **幂等** |
| 已落过的项 | `skip` —— **不覆盖**（§3.4 / §3.5） |
| 蓝图后补的项 | 落下来 |

**`add` 并入 `sync`**（不再有独立的 `add` 命令）：

| # | 依据 |
| - | --- |
| ① | 既然**只增不删**，「换成蓝图 B」与「再加上一份 B」在**文件层面是同一个操作**（都是"把 B 的项落进来、已有的不动"）→ 两个命令 = 一件事两个名字（L1 **A1**） |
| ② | `Lock` / `Project` 的 `blueprint` 是**单值** —— 真·多蓝图并存要改模型，属 §7 **T2**（A3 兼容扩充）。**不动模型**是当前能落地的边界 |

**为什么只增不删**（这是**成品判断**，不是疏漏）：

| # | 依据 |
| - | --- |
| ① | **删除是破坏性动作** —— 上层没给 `scaffold` 删项目文件的授权（L0 §4.1：forge 是编排层；§3.4 同一条精神：**不自行处置**） |
| ② | **对齐不是镜像同步** —— 蓝图去掉一项 ≠ 要删用户项目里的文件（那可能已被改过、被别处引用） |
| ③ | 要清理由**人**决定 —— `scaffold` **不代删**；本轮**也不报**「哪些项已不在蓝图里」 |

> **登记**：`Project.blueprint` 单值 = **已知妥协**（§7 **T2**）。完整来源**没丢** —— 每个 `Entry.from` 各自记着 `blueprint:<id>`（§3.6）。

## 6. `forge new` 走一遍

| # | 谁          | 做什么                                                                       |
| - | ---------- | ------------------------------------------------------------------------- |
| 1 | 入口层        | 校验目标路径；解析 `--blueprint`（缺省 `minimal`）                                       |
| 2 | `scaffold` | `preview(...)` → `ChangeSet`（**这一步就可以停手呈交**）                              |
| 3 | `scaffold` | `apply(...)`：① **自落** payload 项 → 落项目业务内容；② **委托** `skill:` / `aiwf:` 项 → 调上游 CLI |
| 4 | `store`    | 写 `<项目>/.forge/lock.json`（**只含 payload 项的 `Entry[]`** + 蓝图 id）；在 **global 域登记受管** |
| 5 | 失败         | **失败即停**；已成功项照常报账；**不登记受管**                                          |

**受管登记的时机**：**落位成功之后** —— 未建成的项目不进清单（避免清单里出现半成品）。

**重跑与已受管路径**：

| 情形 | 行为 |
| -- | -- |
| **未受管**（含中途失败后重跑） | 正常落位（§3.5：已成功项 `skip`） |
| **已受管 + 蓝图一致**（`--blueprint` 未指定时**取登记值**） | **幂等 no-op** —— 一个字节都不写 |
| **已受管 + 蓝图不一致** | **`refuse`** —— 报「已受管：蓝图 X ≠ 请求 Y」 |
| **对齐 / 增量** | 走 `forge sync` —— 与 `new` **同链路**：蓝图后补的项落下来，已落过的 `skip`（§5.4） |

依据：L1 **H3**（重试应可重复调用）· **H5**（不在完整流程里留死路）· **A1**（“换蓝图”不是 `new` 的职责，归 **§5.4** 的 `sync`）。

**实现范围**

| 做                                                   | 不做（登记 §7 / L2 §5.2）                                |
| --------------------------------------------------- | ------------------------------------------------- |
| 蓝图库（**包内**）+ **三路来源全通**：`payload:` 自落 · `skill:` / `aiwf:` 委托 | **多蓝图并存**（`add`）—— 要扩 `Lock` / `Project` 的单值字段，归 §7 **T2** |
| `preview` / `apply` / 报账（含委托）                        | 内容哈希 / `conflict` 列（L2 §5.2 推后）                  |
| `--force`（自落改判 + 委托透传）                               | 委托项的**可观测性**（§7 T6）                              |
| 一个 `minimal` 蓝图（示例内容）                                | 蓝图库的**其余内容**（随包发哪几个）—— 见 §5.3                        |

> **`aiwf:` 与 `skill:` 同构**（都是「调一条上游命令」），故**三路全通**。

## 7. 待定

| #      | 项                                             | 影响面                            | 归属                          | 状态                        |
| ------ | --------------------------------------------- | ------------------------------ | --------------------------- | ------------------------- |
| **T1** | lock 的内容哈希 + `decide` 第三列（`conflict`）           | 覆盖前的「本地已改」提示                   | 与 L2 §5.2 同一项，**推后**       | 待定                        |
| **T2** | `Lock.blueprint` 单值 → 多蓝图列表                     | 一次落位含多个蓝图                      | `store`（`03-store`）；A3 兼容扩充 | 待定                        |
| **T3** | `ChangeSet` 是否需要落盘（跨会话审阅）                     | 若需要，须由 `store` 新增 `kind`        | `store` + 入口层              | 待定                        |
| **T4** | 蓝图是否要**变量渲染**（如 `${project_name}`）            | 模板表达力                          | 本模块；暂不做                 | 待定                        |
| **T5** | 委托要求**上游 CLI 在 PATH 上**（缺则 `delegate` 失败）      | 使用门槛 —— forge 无法自带上游           | 环境 / 文档                     | 待定（**已知代价**，见下）           |
| **T6** | **委托项的可观测性** —— 不入 lock 后，forge 侧看不到「委托了什么 / 成没成」 | 预演只能报命令、报不了落点；重跑的幂等由上游兜底       | `store` + 入口层（若要做）          | 待定（**已知代价**）               |

**T5 的代价照实说**：委托路线把 forge 的**一组环境依赖**换成了**两个 CLI 依赖** ——
`forge new` 要跑通 `skill:` / `aiwf:` 项，机器上就得有 `skill` / `aiwf` 命令。
这是「不重复造轮子」的**直接代价**：**少一套代码，多一个前提**。

**T6 的代价照实说**：不入 lock 换来「没有第二事实源」，代价是**forge 对委托结果失明**。
若将来确实需要（比如 `workbench` 要展示「这个项目装了哪些 skill」），
那**必须重新走一遍 §3.6.1**：要么承认上游是唯一权威（去读上游的账本），
要么在 `lock` 里加一个**只记「我委托过」的弱记录**（并显式声明它**不是权威**）。**两条都不许静默做。**

## 8. agent 使用视角（L1 约定 **H6**）

> **一句话**：agent 用 `scaffold` **只有两个动作 —— `forge new`（立新项目）· `forge sync`（把已有项目对齐到蓝图）**；蓝图、payload、lock、委托的复杂度都收在这两个命令后面（H1 / H5）。
> 命令表面归**入口层**（§5.4），但它由本模块的**两个原语**决定：`preview`（纯计算）→ `apply`（执行 + 报账）。

### 8.1 三条使用纪律

| # | 纪律                                                                     | 依据                                                                |
| - | ---------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 1 | **agent 不直接调 `preview` / `apply`** —— 那是模块内原语；agent 面是**入口层命令** `forge new` | L1 **H1**（对外表面按 agent 设计）+ L2 §3.1（入口层两个面：CLI 给人 / skill 给 agent） |
| 2 | **先预演、再执行**（H2）—— 新建项目**先 `--dry-run` 看 `ChangeSet`**，由人点头后再真落（L0 §2：人是导演） | L1 **H2**（能强制的不靠约定）+ §3.1（预演 / 执行共用一份逻辑）                        |
| 3 | **agent 不直读 `.forge/lock.json`**（H4）—— 它看的是入口层渲染的报告；「要人介入」的信号（`refuse`）**必须从命令输出里读到** | L1 **H4** + `03-store` §9（同一条纪律）                                  |

### 8.2 完整流程（新建一个项目）

> 场景：agent 接到"帮我把 X 项目立起来"，蓝图已知（或由人指定）。

| 步 | agent 做什么                                  | **一次调用**                                    | 拿到什么                                              |
| - | ------------------------------------------ | ------------------------------------------- | ------------------------------------------------- |
| 0 | **知道有哪些蓝图可选**（无 `blueprint list`，§5.2 —— 靠目录名 / 人告知） | ——（`--blueprints <dir>` 指库；不指则用包内）           | 蓝图 id                                             |
| 1 | **预演** —— 先看会落什么、有没有冲突                     | `forge new <路径> --blueprint <id> --dry-run` | `ChangeSet`：逐条 `op` / `from` / `to`（**`refuse` 会显式出现**） |
| 2 | **（有 `refuse` 时）请示人** —— 不自行处置              | ——（把预演结果呈交）                                 | 人的决定：改路径 / 删目标 / 加 `--force`                       |
| 3 | **执行**                                     | `forge new <路径> --blueprint <id>`           | 落位结果 + 受管登记（`store` 写 `projects.json`）             |
| 4 | **收工看账**（第 3 步的输出即报告，无第二次调用）                | ——                                           | 落了哪些 payload / 委托了哪几项 / `refuse` 了哪些              |

**agent 全程不需要知道**：蓝图库在哪、`payload/` 怎么组织、lock 写成什么、`.aiwf/` 与各 agent 目录是谁写的。
**一次意图（把项目立起来）= 一次调用**（H3）—— 除了「预演」这一次**刻意**的中间呈交（H2）。

### 8.3 对齐 / 增量（`forge sync`）

> 场景：项目**已经建好**，但蓝图后补了项（或要换蓝图）—— 蓝图后来加了 `skill:aiwf`、项目里缺，就是实例。

| 步 | agent 做什么 | 一次调用 | 拿到什么 |
| - | --- | --- | --- |
| 1 | **预演** | `forge sync <路径> --dry-run` | 同样一份 `ChangeSet`（新项 `写入` · 已落过 `跳过` · 委托照发） |
| 2 | **（有 `refuse` 时）请示人** | —— | 人的决定（改路径 / 删目标 / `--force`） |
| 3 | **执行** | `forge sync <路径>` | 落位结果 —— **只增不删**，已落过的一个字节不动 |
| 4 | **换蓝图** | `forge sync <路径> --blueprint <id>` | 显式换蓝图（`new` 遇到不一致的蓝图只会拒绝并指到这里） |

**agent 必须知道的**：`sync` **不删任何东西** —— 蓝图里去掉的项**留在项目里**；清不清是**人**的决定。

### 8.4 两处 agent 必须知道的边界（照实说）

| 边界           | agent 要知道什么                                                                                 | 为什么                                                          |
| ------------ | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| **委托项失明**    | `delegate` **只报"会调哪条命令"（`skill install X` / `aiwf wf install Y`），不报"会落哪些文件"** —— agent **不能**据此断言"装好了" | forge 对委托结果**没有直接观测**（不入 lock，§3.6.1）；权威在**上游**（§4.2 / §7 **T6**） |
| **`refuse` 不是失败** | 它是**正常结果**，含义 = "目标已存在、且不是我落的" → **要人介入**                                                   | §3.4：`scaffold` **不自行处置**；这是「停手呈交」的落点                         |

> **与 `plan` 的差别**：`plan` 的 agent 面是**一组语义动词**（`claim` / `reject` / …，`06-plan` §2.3）；
> `scaffold` 的 agent 面是**两个动作**（`forge new` / `forge sync`）—— 它们都是**整体动作**：
> "立项目" / "对齐蓝图" 本身不可再分，没有可拆的语义动词（A1）。
> 两者的共同点（也是 H 的落点）：**agent 只面对语义动词 / 动作，不面对文件与原语。**
