# forge · L3 模块设计 —— `workbench`

> 层级：**L3**。上游 = **L2 概要架构与模块划分**（`02-architecture.md`）。
> 本文件写 `workbench` 的**核心设计**；**实现以 `forge/workbench.py` 为准**。
> **模块**：`workbench` —— **跨项目总览（分区聚合呈现）**（L2 §3.1）。它是**用例层**里的**视图**角色（**不是**数据访问层）。
> **术语约定**：本文的 **「分区」= 汇总单元**（`plan` / `inbox` / `aiwf` 三块内容），**与 `Plan` 的中文名「计划」无关**。
> **本文件只写 `workbench`**：`store` 见 `03-store.md`；`scaffold` 见 `05-scaffold.md`；`plan` 见 `06-plan.md`；`inbox` 见 `07-inbox.md`；`observer` 见 `04-observer.md`（本文 §7 给出对它的接口诉求）。

## 1. 职责与边界

**一句话**：`workbench` 管**「我手上这几个项目，各自到哪了、各自欠什么」** —— 它**自己一个字节都不存**，只是把**每个项目的三个分区内容**（`plan` / `inbox` / `aiwf`）**现读现算**成一张总览。

|         | 内容                                                                                                                                                                                                 |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **做什么** | ① **列清单**：读 global 受管清单 → 我有哪几个项目（`alias` / 路径 / 蓝图 / 注册时间）<br />② **分区汇总**：逐项目汇总 **`plan`**（计划与任务分布 + 在做 / 卡住）· **`inbox`**（念头分布 + 最近新增）· **`aiwf`**（工作流 / 运行 / 在等你）（**§4**）<br />③ 数据经**所有者读面**读（`store` 自有 kind 直读 · `plan` / `inbox` 经其**公开读面** · 外部经 `observer`），**不写**、**不旁路**（L2 §4.2.1） |
| **不做**  | ① **不写盘** —— **零写动词、零 `kind`、零 schema**（L2 §3.1 明写「不写」）<br />② ★ **不做「项目状态」归一** —— 不产出「这个项目处于某阶段」这类**单一值**（§4.0）<br />③ **不判断**「该不该介入 / 哪个分区重要」—— 判断归 agent 与人（L1 约定 **B**）；它只给**事实与计数**<br />④ **不碰外部系统** —— aiwf 运行状态**一律经 `observer`**（L2 §2.2 不变量 2：**没有旁路**，理由原文点名 `.aiwf/runs/`）<br />⑤ ★ **只调 `plan` / `inbox` 的公开读面**，**不 import 其内部实现、不读其落盘文件** —— L2 **§4.2.1**（读经所有者读面）；**写路径**仍零依赖（L2 §4.2）<br />⑥ **不承载明细** —— 计划 / 任务 / 条目的细节仍归 `forge plan show` · `forge inbox list`（§8） |

### 1.1 它回答三个问题

对齐 **L0 §3** 对 `workbench` 的定位（「哪几个项目在开展、各自什么阶段、哪些需要我介入」）与 **L0 §1** 的目的（「让人**对全部项目保有全局意识**」）：

| 问题                | 靠什么答                                            |
| ----------------- | ----------------------------------------------- |
| **我有哪几个项目**       | `forge workbench` —— 受管清单一行一个（`alias` / 蓝图 / 注册时间） |
| **各自到哪了**         | ★ **三个分区事实**（§4）—— **不用一个词**概括，摆出来让人自己合起来读；★ **「还在动吗」也在这里**：由 `latest_activity` / `oldest_open` 两个时间戳给（§4.4） |
| **各自欠什么**         | 同上：`在做 / 卡住` 的任务、`未处理` 的念头、`在等你` 的 run —— **全是数字与名字，不是结论** |

> ★ **第三条的边界（关键）**：L0 说「哪些**需要我介入**」—— 但「需不需要介入」是**判断**，归人（L1 约定 **B**）。
> 引擎只把**结构事实**摆出来：`卡住 1`（有 `blocked` 任务）、`未处理念头 15`（有 `open` 条目）、`⏳ 等 review`（aiwf run 停在人工门）。
> **不产出**「⚠ 需介入」这类结论性标记 —— 那是替人下判断。
> ★ **例外（合规的）**：`aiwf` 的「在等人工」**不是 forge 的判断** —— 它是 **aiwf 引擎自己**在 `runs show --view` 里给出的 `status: waiting` + `action.kind`（§4.3）。forge **透传**它，不加工。

### 1.2 边界（与谁无关）

| 对象               | 关系                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| `store`          | **经它只读**（L2 §4.2 边 **7**）—— 读 global 的 `projects` + 各项目的 `plans` / `inbox`；**不碰文件本身**（§6.1）           |
| `observer`       | **经它只读外部状态**（L2 §4.2 边 **8**）—— **只走 aiwf 一路**（§7）；**不自己旁路读 `.aiwf/`**                          |
| `plan` / `inbox` | ★ **只读它们的公开读面**（L2 **§4.2.1**）—— **不 import 其内部实现、不读其落盘文件**（§6.2）                        |
| `scaffold`       | **只读它的产出** —— 即 global 清单里的 `blueprint` / `registered_at`（`scaffold` 登记时写入）；不 import                   |
| 被管理项目            | **一个字节都不写**（L2 §3.1「写盘：**不写**」）—— 包括 `.forge/` 与项目业务内容                                           |
| `aiwf`           | **不感知 · 不挂钩**（L0 §4.1）—— ★ 读它的运行状态**只经 `observer`**，且**不给 forge 的模型加外键**（§4.3）                        |

## 2. agent 使用视角（L1 约定 **H6**）

### 2.1 五条使用纪律

| # | 纪律                                                                              | 为什么                                                                 |
| - | ------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 1 | **它是只读的** —— 没有写动词；`forge status` / `forge workbench` 跑多少次都不会改任何东西                                   | L2 §3.1「不写盘」；**别指望用它改状态**（改状态回项目里用 `forge plan` / `forge inbox`）      |
| 2 | ★ **CWD 依赖分两种** —— `forge workbench` **不依赖 CWD**（从任意目录跑都行）；`forge status` **项目根 = CWD**                                                    | 与 `plan` / `inbox`（项目根 = CWD）**相反**；它的输入是 global 清单（§6.1）—— 这正是「跨项目」的含义 |
| 3 | **要明细就别找它** —— 全局用 `forge workbench`，**本项目一眼**用 `forge status`；**计划 / 任务 / 念头明细**进那个项目用 `forge plan show` / `forge inbox list` | L1 **H4**：全局视图必须「一眼扫完」；明细视图已在 `06-plan` §2.6 / `07-inbox` §2.5 定过职责分工   |
| 4 | **别直读 `.forge/` 文件**                                                             | 同 `plan` / `inbox` 纪律；形态归 `store`（L2 §2.5），直读 = 绕过唯一读入口                |
| 5 | ★ **别指望它给「项目状态」** —— ★ **名字叫 `status` 的那个也不给**：它给的是**三个分区事实**，不是一句结论                                        | 项目开展内容多，**归不到一个状态**；要判断就自己读三个分区（§4.0）                     |

### 2.2 完整流程（一个新会话接手全局）

**场景**：主人开一个新会话问「我手上这几个项目都什么情况」。

| 步 | 动作                                 | 谁      | 得到                                                       |
| - | ---------------------------------- | ------ | -------------------------------------------------------- |
| 0 | `forge workbench`                  | agent | 清单 + 每项目三个分区：`plan`（计划与任务分布 / 在做 / 卡住）· `inbox`（分布 / 最近）· `aiwf`（运行 / 在等你） |
| 1 | （人看到某项目有「在做 / 卡住 / 在等你」）→ `cd <该项目>` | 人      | 进入那个项目                                                   |
| 2 | ★ `forge status`                   | agent | ★ **本项目**的同一份三分区视图（**一段**，与全局同形）—— 「这个项目什么情况」一眼答完                |
| 3 | `forge plan show`                  | agent | 该项目的计划列表（`06-plan` §2.4）                                   |
| 4 | `forge plan show <plan>.<task>`    | agent | 单任务交接包（含完整轨迹）—— 才知道**卡在哪**                                |
| 5 | `forge inbox list`                 | agent | 那些「现在不做、但别忘」的念头（`07-inbox` §2.4）                          |
| 6 | `aiwf runs show --view <run_id>`   | agent | **看到 `aiwf` 分区说「在等你」时**：拿 aiwf 自己给的下一步命令（§4.3）              |

> ★ **第 0 步是「全局意识」的落点**：一条命令看完所有项目，**不必逐个 cd**。
> 第 1–6 步是既有的「进入项目」动作（★ 第 2 步是**本项目一眼**） —— `workbench` **不重复造它们**（§8）。

### 2.3 命令总表

**读（2 个视图 —— 同一段渲染的两个出口）** —— 不吐 `projects.json` 原文；默认**结构化文本**、另给 `--json`：

| 读视图               | 返回                                                          | 过滤器 | **默认体量**                |
| ----------------- | ----------------------------------------------------------- | --- | ----------------------- |
| `forge workbench` | **跨项目总览**：一项目一段 —— 身份行 + **三个分区各一行**（`plan` / `inbox` / `aiwf`） | 无   | **全量**（有界：项目数 × 3；见 §9 **T2**） |
| ★ `forge status`  | ★ **本项目视图**（项目根 = **CWD**）：**一段** —— 与上方**逐字同形**（去身份行）          | 无   | **一段**（有界：3 行 + 动态项 ≤ 3 × 2） |

> **没有写动词、没有 `--dry-run`**（无落盘可言）、**没有 `--json` 之外的机器面**。
> **`--json` 给出与文本同一份视图**（H2 表面一致）—— **不是** global / project 域任何文件的原文（§3.1）。

### 2.4 token 纪律（H4）

| 视图                | 带轨迹 / 明细？ | 默认体量                          | 为什么                                              |
| ----------------- | --------- | ----------------------------- | ------------------------------------------------ |
| `forge workbench` | **❌ 都不带**   | 有界：`项目数 × (1 + 3)` 行 + 每个分区**最多 3 条**动态项 + **顶部「最近动态」≤ 6 行** | 全局只需「哪几个项目、三个分区各什么情况」；**展开全部任务会让 N 项目 × M 任务炸掉 token**（H4） |
| ★ `forge status`  | **❌ 都不带**   | 有界：**3 + ≤ 3 × 2** 行 + **「最近动态」≤ 6 行** | ★ **只有一个项目** ⇒ 与全局**同一条上限规则**（同一段渲染，L1 **D1**）；明细仍归 `forge plan show` / `forge inbox list`（§8-6） |

**四条规则**（沿用 `06-plan` §2.6 的同款思路）：

1. **一个分区一行摘要** —— `plan` / `inbox` / `aiwf` 各一行；**不展开计划名、不给 goal、不给轨迹**；★ **陈旧度（`latest_activity` / `oldest_open`）是本行里的标量字段，不新增行**（H4 不受影响）。
2. ★ **动态项给上限** —— 「在做 / 卡住的任务」「等待中的 run」最多列 **3** 条，超出只给 `⋯+K` 计数（H4：**有界**是硬要求，不是偏好）。★ **超限取哪 3 条**：`plan` 侧按 **`plan_log` 中该 task 最后一条事件的 `ts` 降序**（最近动的在前；**无事件**的排末尾；**同键**按地址升序 —— 全程**确定**，L1 **G**）；★ **排序键不显示**，只决定顺序。
3. ★ **「最近动态」也有界** —— 全局 / 本项目各 **≤ 6 行**（`RECENT_LIMIT`）；`inbox` 进时间线**每项目只 1 条**（§4.6），防止一个项目把别的挤掉。
4. **默认体量贴合各自的界** —— 项目数有界（人就管得过来几个），故给全量；若将来项目数膨胀，见 §9 **T2**。

## 3. 读侧模型（零落盘）

### 3.1 ★ `workbench` 没有落盘模型 —— 这是它最本质的特征

**先讲一个必须避免的坑**：`forge/schemas/` 目录 **= `store` 的 `kind` 表**（`03-store` §6.2：`kind` 由文件名**派生**，`store` 扫描该目录）。
→ **本文档的视图结构不得写成 `forge/schemas/*.schema.json`** —— 写进去 `store` 就会认为存在这个 `kind`，还会因为缺 `x-forge-scope` 而**报错**（`store._kinds()`）。

|          | `workbench` 的情形                                             | 依据                                       |
| -------- | ---------------------------------------------------------- | ---------------------------------------- |
| **kind** | **0 个** —— 不新增任何 `kind`，`store` 的 `kind` 表（`03-store` §6.2）**一行不动** | L2 §3.1（写盘：不写）+ L1 **A1**                |
| **schema** | **0 份** —— 视图结构只存在于**本文档**与**实现**里，不进 `forge/schemas/`                 | `03-store` §6.2（那个目录 = kind 表）           |
| **落盘**   | 无。**跑完即散**                                                   | L2 §2.3②（`observer` 同款性质）+ §3.1          |

> ★ **「不存」不是偷懒，是它的正确性来源** —— L2 §2.4 硬线 2：**`observer` 不存任何东西 → 工作台显示的是现读实况，永远不会读到过期副本**。`workbench` 同此。

### 3.2 视图结构（项目身份 + 三个分区）

**结构里的字段全部是「读时投影」**，不落盘、不进 schema 目录。

```
Workbench {                     # forge workbench 的输出（全局）
  focus:   string?              # 跨项目焦点 = 某个 alias；取自 projects.json 的 focus，未设置则缺省
  projects: [ProjectStatus]     # 顺序 = 焦点置顶，其余按 alias 升序（§3.3）
}
```

```
ProjectStatus {
  # —— 身份（来自 global 清单）——
  alias:          string        # projects.json 的 alias
  path:           string        # 目标项目绝对路径
  blueprint:      string        # 蓝图 id
  registered_at:  string        # ISO 8601
  focus:          bool          # 是否当前焦点

  # —— 三个分区（§4）——
  plan:  PlanSection
  inbox: InboxSection
  aiwf:  AiwfSection

  # —— 本项目「最近动态」（§4.6）——
  recent: [ActivityEntry]       # 带时间戳的事实，按时间降序、**截断到 RECENT_LIMIT(6)**

  error: string?                # 该项目 store 侧读不到时的原因（不静默吞错，§6.4）
}
```

> ★ **`recent` 只挂在 `ProjectStatus` 上，`Workbench` 顶层不另存一份** —— 全局视图的「最近动态」由 **`workbench.merge_recent(projects)` 读时合成**（各项目 `recent` 并起来 → 降序 → 截断）。若顶层再存一份，就是**同一份数据两处落**（L1 约定 **D** / **H4**）；入口层拿合成结果渲染即可（§4.6）。

> ★ **`forge status`（本项目视图）的输出 = 一个 `ProjectStatus`** —— ★ 与全局里的「一段」**逐字同形**（去掉 `alias` / `blueprint` / `registered_at` 那截身份信息）。
> **未受管的项目照常可用**：身份信息来自 global 清单，清单里没有该项目时退化为**路径** + 标注「未受管」，三个分区**照读**（都不依赖受管，§6.1）。

### 3.3 排序与去重

| 项     | 规则                              | 依据                                    |
| ----- | ------------------------------- | ------------------------------------- |
| 项目排序  | **焦点置顶**；其余按 **`alias` 升序**     | **确定性**（L1 **G**：可回归）；不按「重要度」——那是判断（L1 **B**） |
| `alias` | 唯一性由 `store` / `scaffold` 侧保证（`projects.json` 的 `alias` 全清单唯一） | `03-store` §4.1                       |

> ⚠ **`focus` 当前恒缺省** —— `projects.json` 的 schema 有该字段（`03-store` §4.1），但**没有任何命令能写它**（`cli.py` 只做读时透传）→ 排序规则**保留**、实际等价于纯 `alias` 升序。谁写它 → 登记 §9 **T3**。

## 4. ★ 分区汇总：各自什么信息有用（本文核心）

### 4.0 原则：只做分区汇总，**不做状态的归一**

**原则**：`workbench` **不产出「项目阶段」这类单一状态** —— **项目开展的内容很多，无法准确归一到单一状态来表达**。

**依据链**：
- L1 **B** —— 「这个项目现在算哪个阶段」是**语义判断**，引擎不做；
- L1 **A1** —— 能直接数出来的事实，别去造一个抽象；
- L1 **H4** —— 三个分区计数比「造一个准确的状态词」便宜得多，也更不该骗人（归错了比不归更糟）；
- L2 §3.1 —— `workbench` **不写盘** ⇒ 本来就没有字段能承载一个长期状态。

**三个分区的来源与读取路径**：

| 分区        | 内容                              | 来源                         | 经谁                |
| -------- | ------------------------------- | -------------------------- | ----------------- |
| `plan`   | 该项目的计划与任务 | `plan` 用例（kind `plans` + `plan_log`） | ★ **`plan.overview()`** —— 一次调用给全 |
| `inbox`  | 该项目的念头 | `inbox` 用例（kind `inbox`） | ★ **`inbox.list_items(show_all=True)`** —— 计数是平凡组装 |
| `aiwf`   | aiwf 的装了什么 / 跑没跑 / 在等谁          | `.aiwf/`（**aiwf 地盘**）       | ★ **`observer`**（§4.3） |

> ★★ **为什么 `aiwf` 分区不能自己读**：L2 §2.2 不变量 2 的理由**原文点名了 `.aiwf/runs/`** ——
> 「工作台的价值取决于『显示的与实际是否一致』，若**散落各处读 `.aiwf/runs/`、git**，迟早读出不同口径」。
> 故本分区**只能经 `observer`**（L2 §4.2 边 **8**）。这是**硬线**，不是风格问题。

### 4.1 `plan` 分区 —— 「有几份计划、做到哪、**现在在做什么**、卡在哪、**还在动吗**」

**来源**：逐项目调 **`plan.overview(path)`**（`06-plan` **§6.4**）—— **一次调用给全**：计数 / 分布 / `latest_activity` / `doing[]` / `blocked[]`（**含顺序**）。

```
PlanSection {
  # —— 以下 6 行 = `plan.overview()` **原样给**（`06-plan` §6.4；本模块不重算）——
  plans:        int             # 计划数；0 = 未记账
  plan_status:  {open, reached, dropped}   # ★ 计划状态的「分布」，不是归一
  tasks:        {total, done, doing, todo, blocked}   # 任务「分布」
  latest_activity: string?                # ★ `plan_log` **末条**事件的 ts（ISO）→ 「上次计划变动是什么时候」（§4.4）
  doing:        [{address, title}]        # ★ 在做的任务 —— **全量、已排序**（最近活动降序；§4.1 末）
  blocked:      [{address, title}]        # ★ 卡住的任务 —— 同 `doing` 的口径与顺序
  # —— 以下 2 行 = 本模块自己加的（呈现截断 + 容错）——
  truncated:    {doing: int, blocked: int}  # 呈现截断的余量（= 总数 − 列出的 3；无截断则 0）
  error:        string?                   # 读面抛 `StoreError` 时的原因（§6.4）
}
```

| 信息                               | 为什么有用                                        | 依据                 |
| -------------------------------- | -------------------------------------------- | ------------------ |
| **计划状态分布** `open / reached / dropped` | 「4 份计划里 3 份在开、1 份已达成」—— **分布**替掉了「单一状态」（§4.0） | L1 **D2**  |
| **任务分布** `total/done/doing/todo/blocked` | 一眼看出「活干到哪了」；`done/total` 是最省 token 的进度事实    | L1 **D2**          |
| ★ **`latest_activity`**        | ★ 「上次动这个项目的计划是什么时候」—— **陈旧度信号**：计数答不出「还在动吗」，一个时间戳就能答 | `plan_log` 末条 `ts`（§5.2；★ 只取末条，**不带轨迹**） |
| ★ **在做** `doing` 的任务（`<plan>.<task>` + 标题） | ★ **这就是「我现在在推哪个」的实况** —— 比任何阶段投影都准（它是引擎里的真值） | L0 §3「各自什么阶段」的**正确落点**（§4.0） |
| ★ **卡住** `blocked` 的任务          | ★ 结构事实（不是判断）：`06-plan` 里 `blocked` 是**agent 显式标注**的，不是 forge 推的 | L1 **B**（摆事实）+ §1.1 |
| **`plans == 0` → 显示「未记账」**        | 区分「**没记过账**」与「有账但全空」；前者是 scaffold 之后还没建 plan     | `03-store` §5.3（缺文件 = 空数据） |

**不做**：全列计划名 / `goal` / 判据 / 轨迹 / `owner` / 时间线。
**理由**：`goal` 与轨迹属明细（§8-6 / H4）；`owner` 只是分工不是状态。
> ★ **`latest_activity` 是「一个时间戳」，不是「时间线」** —— 它只取 `plan_log` 的**末条 `ts`**，**不列中间任何事件**（§5.2）；完整轨迹仍归 `forge plan show <plan>.<task>`（§8-7）。
> ★ **`doing` / `blocked` 的排序** = 按**该 task 轨迹末条事件的 `ts` 降序**（最近动的在前）；**没进过 `plan_log` 的 task 排末尾**；**同键**按**地址 `<plan>.<task>` 升序** —— ★ **由 `plan.overview()` 给**（`06-plan` §6.4）：规则只看数据、不看人（L1 **B** / **G**），**本模块不排序、只截断**。
> ★ **排序键不显示**（H4）—— **顺序本身就是信号**：越靠上 = 越近动过。

### 4.2 `inbox` 分区 —— 「欠着几个念头、最近还在往里记吗、**最老的挂了多久**」

**来源**：逐项目调 **`inbox.list_items(path, show_all=True)`**（`07-inbox` §2.4）—— **一次给全**；计数与 `min` / `max`（`latest_created` / `oldest_open`）是**平凡组装**，不涉语义（§6.2）。

```
InboxSection {
  total:          int           # 总条数
  status:         {open, handed, dropped}   # ★ 状态「分布」
  latest_created: string?       # 最新一条 Item.created（ISO）→ 「上次记念头是什么时候」
  oldest_open:    string?       # ★ 最老一条 open 的 Item.created（ISO）→ 「最老的欠账挂了多久」；无 open 则缺省（§4.4）
  recent:         [Item]        # ★ **最近加入的 3 条**（`created` 降序，同日按 `id` 降序）—— owner 读面的行（`id`/`text`/`status`，`text` 已按 60 宽截断）
  error:          string?       # §6.4
}
```

| 信息                              | 为什么有用                                            | 依据                    |
| ------------------------------- | ------------------------------------------------ | --------------------- |
| **状态分布** `open / handed / dropped` | 「15 条全 `open`」= 一个都没消化 —— 这是**欠账感**的事实来源        | L1 **D2**             |
| ★ **`latest_created`**         | ★ 「最近一次往 `inbox` 里记东西是什么时候」—— 判断**这个项目还活着没有**一路信号 | `Item.created` 是 `inbox` kind 内字段，**零额外来源**（`07-inbox` §4） |
| ★ **`oldest_open`**            | ★ 「最老的未处理念头挂了多久」—— **陈旧度信号**：`latest_created` 只说「最近记过」，这条说「**欠的债有多老**」 | 同 kind 内字段，取 `open` 条目里 `created` 最小者；无 `open` → 缺省 |
| ★ **`recent`（最近 3 条）**    | ★ 「**最近记进来的是什么**」——`latest_created` 只说「什么时候记的」，这条**把内容摆出来**：扫一眼就知道项目在关心什么 | `07-inbox` §2.4 的 `list_items(show_all=True)` 行（**同一份数据**，不额外读） |
| `total == 0` → 显示「0 条」        | 空就是空，不特殊渲染                                       | `03-store` §5.3        |

**不做**：列**全部**条目正文（明细归 `forge inbox list`，§8-6）；`tags` / `source` / `note` 的汇总（A1：没场景要它）—— ★ 只多给**最近 3 条**的短文本（截断到 60 宽），**不是**明细列表（H4）。
> ★ **`oldest_open` 只在有 `open` 时才有值** —— 全消化完（`open == 0`）就给缺省（**不是错误**，A1）；它与 `latest_created` **一老一新**，合起来才答得出「这个项目还活着没有 + 欠账积了多久」。

### 4.3 `aiwf` 分区 —— 「装了几个流程、有没有在跑、**在等谁**」

**来源**：★ **`observer`**（L2 §2.2 不变量 2 · §4.2 边 8）—— 它去读 aiwf 的 CLI：

| 读什么            | 命令                                 | 有 `--json`？ | 实测结论                        |
| -------------- | ---------------------------------- | ---------- | --------------------------- |
| 已装工作流          | `aiwf workflows --json`            | **有** ✅    | `{id, name}` 数组；空则 `[]`（§4.3.2 ②） |
| 运行清单           | `aiwf runs list --json`            | **有** ✅    | 一行一 run 的列对象（**field-per-column**，§下） |
| **单个 run 的业务视图** | `aiwf runs show --view --json <id>` | **有** ✅    | 结构化 stages（§下）               |

```
AiwfSection {
  workflows:   int              # 已装工作流数（aiwf workflows）
  runs_total:  int              # run 总数（aiwf runs list）
  running:     [AiwfRun]        # 运行中的 run（通常 0 或 1 个）
  last:        AiwfRun?         # 最近一次「已结束」的 run（completed / failed）
  error:       string?          # observer 这一路读不到时的原因（§6.4）
}

AiwfRun {
  run_id:        string
  workflow_id:   string
  title:         string         # ★ 实例名（`runs list` 的 title，aiwf `run_title()` 解析好）—— **永不为空**；旧 run = run_id
  status:        string         # ★ aiwf 的词，透传（running / completed / failed）
  started_at:    string
  ended_at:      string?
  stages_done:   int            # --view 里 status=done 的阶段数
  stages_total:  int            # 阶段总数
  current:       string?        # 当前阶段名（--view 里 status=waiting 的那个）
  wait:          string?        # ★ 有则 = 该阶段的 action.kind（如 review）→ 「在等你」
}
```

| 信息                                   | 为什么有用                                                            | 依据                              |
| ------------------------------------ | -------------------------------------------------------------- | ------------------------------- |
| **`workflows`（装了几个流程）**              | 区分「**没接流程**」(`0`) 与「**装了流程但没跑**」(`>0` 且 `runs_total==0`) —— 实测只能靠它区分（§4.3.2 事实③） | L0 §4.1（forge 读 aiwf）           |
| ★★ **`title`（实例名）**              | ★ 「**跑的是哪一个实例**」—— `workflow_id` 只是**模板名**（`std.novel-writing`），答不出「写的是哪部小说」；`title` **aiwf 已解析好**（起跑时 `--title` 给的实例名；工作流可选 `view.dynamic_title` 覆盖为产出名） | ★ **L1 F**：名字归 **aiwf / 工作流**所有，forge 只**透传** |
| **`running` + `current` + `stages_done/total`** | 「跑到第 3/9 个阶段、停在『角色设计』」—— 与 plan 分区同款的「到哪了」事实                     | L1 **D2**                       |
| ★★ **`wait`（在等谁）**                   | ★ **aiwf 引擎自己**在 `--view` 里给出 `status: waiting` + `action.kind` → 这是「哪些需要我介入」的**最精确事实** | ★ **L1 B**：**判断由 aiwf 做**，forge 只透传 |
| **`last`（最近结束的 run）**                | 「上次那轮跑完了 / 失败了」—— 与 `running` 一起构成「动静」                                     | L0 §3                           |

> ★ **`title` 从哪来**：aiwf 把**实例名**做成 **run 的一级字段**：`aiwf run … --title "…"` **起跑即给**（必填），并解析进 **`runs list --json`** —— `view.dynamic_title`（可选，工作流声明；产出后可**完全解析**则改名为产出名，如小说真名）→ `record.title`（起跑名）→ `run_id`，**永不为空**（`view.run_title()`）。
> ★ **`title` 从 `runs list` 取、不是 `--view`** —— 所以它**每条 run 都有**：`running` 与 `last` **一样**，**不再**是「只对 running 取」那组（§4.2 纪律的缺省字段**不含 `title`**）。**旧 run（跑在 `--title` 之前）没有起跑名** ⇒ aiwf 落到 **`run_id`**（`view.dynamic_title` 若可完全解析仍会先命中）；★ forge **不退回 `workflow_id`**（那是**模板名**、不是实例名）。
>
> ★ **边界**：**forge 不写 aiwf 的工作流定义 / run 快照**（`.aiwf/workflows/` · `.aiwf/runs/*/workflow.json`）—— 那是 **aiwf 的地盘**（L2 §4.3），**兼容 / 迁移归 aiwf**。**旧 run 显示 `run_id` 即终态**：**不为**「让旧 run 显示实例名」去改工作流 / 补快照。forge **只透传** `runs list` 给的 `title`。

> ★ **`wait` 的边界（重要）**：`workbench` **只透传 `action.kind`**（如 `review`），**不自己拼下一步命令**。
> aiwf 的 `--view` **文本**里本来就打印好了整条命令（实测：`-> aiwf review <run_id> --action <id> --verdict APPROVE|REJECT`），
> 但那属于**渲染细节、不是稳定结构**（`--view --json` 给的是 `action{kind,run_id,workflow_id,id}`）。
> **做法**：`workbench` 显示「⏳ 在等你：`review`」，并把**取命令的动作**交给 §2.2 第 5 步（agent 跑 `aiwf runs show --view <run_id>`）——
> 满足 **H3（一次动作一次调用）**，且**不造 aiwf 的命令**。

#### 4.3.1 词表归属：aiwf 的词，`workbench` 不翻译

| 谁       | 词表                                                       |
| ------- | -------------------------------------------------------- |
| aiwf    | `status`（`running`/`completed`/`failed`）· stage 状态（**`done`/`waiting`/`pending`**）· `action.kind` |
| forge   | **只透传**（`--json` 原样给），文本渲染时也**照 aiwf 的词**显示 —— **不自造中文态名**（L1 **F**：不占上游名） |
| **顺序**   | ★ **`running` / `last` 的顺序照 aiwf 给的原样**（**不重排**）—— 重排等于 forge 替 aiwf 决定「哪个要紧」（L1 **B**），也违背「只透传」的口径 |

> **理由**：这些词的**所有者是 aiwf**（L2 §4.1「forge 读运行状态」）—— `workbench` 若自己映射一套中文，就制造了**第二套词表**，将来 aiwf 改词就两边打架（L2 §2.2 不变量 2 防的正是这个）。

#### 4.3.2 ★ 四条实测事实（探针实跑）

> ⚠ **这四条是 `observer` 那一路的硬约束**，来自实测而非推断；`04-observer` 必须承接。

| #  | 实测                                                       | 结论（对设计的约束）                                              |
| -- | -------------------------------------------------------- | ------------------------------------------------------- |
| ①  | ★ **盘上的 `record.json` 不是当前状态** —— 某 run 目录里 `record.json` 的 mtime = run **创建那一刻**（内容 `phase: executing` / `next_node: start` / `node_runs: []`），而同目录 `record.log.jsonl` 是**次日**的，CLI `runs show` 现算为 `phase: awaiting_review` | ★★ **`aiwf` 分区不得直读 `record.json`** —— 它是**诞生快照**，读它就是**读到过期副本**（正面撞 L2 §2.4 硬线 2）。**必须走 CLI**。★ 这**修正**了 L2 §2.3②「没有 JSON 的直读文件」在**这一路**的应用 |
| ②  | `aiwf runs list` / `aiwf workflows` **都有 `--json`**（**field-per-column**）；`runs show --view --json` 本就有 | `observer` **三条全走 `--json`** —— 无文本 / 列位解析（`04-observer` §4.3） |
| ③  | 无 `.aiwf/` 的项目（`mc-plus`）与有 `.aiwf/` 但没跑过的项目（`drama_demo`）→ `aiwf runs list` **都返回 `(no runs)`、rc=0**，不报错 | 「**没接流程**」与「**流程没跑过**」**不能靠 list 报错区分** → 只能靠 **`workflows` 计数**区分（§4.3 表第一行）  |
| ④  | `aiwf` 读的是 **CWD**（在非项目目录跑 → `(no runs)`，不报错、静默当成空）                     | `observer` 必须**显式以 `cwd=<项目路径>` 调它**；且要**静默失败兜底**（路径写错也会返回「无」，不能当「真没有」） |

### 4.4 计数与词表的约定

| 项                              | 约定                                                              |
| ------------------------------ | --------------------------------------------------------------- |
| **计数**（`plans` / `tasks.*` / `inbox.*` / `workflows` / `runs_total` …） | **纯整数**，由读到的数据**直接数出来**，不带任何语义判断（§1.1 第三条）                     |
| **分布**（`plan_status` / `status`） | 给**各态计数**，**不给**「主导态」「综合态」——那就又是归一（§4.0）                          |
| **`plan` / `inbox` 的中文渲染**     | 沿用既有：落盘英文 token、渲染出中文（`06-plan` §4 · `07-inbox` §4 · `cli.py` 的 `_STATUS_LABEL`） |
| **`aiwf` 的渲染**                 | ★ **不翻译**（§4.3.1）—— 照 aiwf 的词显示                                 |
| **时间戳**（`latest_created` / `oldest_open` / `latest_activity` / `AiwfRun.*_at`） | **只给 ISO 8601 字符串**（原文值），**引擎不算「几天前」** —— 算相对时间要读「现在」，会引入**非确定性**（L1 **G**）；相对化归 agent / skill |
| **缺省语义**                 | 「数据里没有这个事实」→ **字段缺省**（不是 `0`、不是错误）：`latest_activity` = 从无 `plan_log` 事件 · `oldest_open` = 无 `open` 条目 |
| **`⋯+K` 的呈现**               | 截断只发生在 `plan`（`doing` / `blocked`）与 `aiwf`（`running`）。文本渲染给 `⋯ 还有 K 条`；★ **只对 forge 自家**的下一步给「去哪看」（`plan` → `forge plan show`）；★ **`aiwf` 侧不给命令**（§8-13 不自造上游命令 · §4.3 末） |

### 4.5 ★ 最终展示什么（信息清单 + 一个真样样本）

**一句话**：`forge workbench` = **一项目一段** —— **1 行身份 + 3 行分区**（`plan` / `inbox` / `aiwf`），分区下**最多再跟 2 行动态项**（`在做` / `卡住`）。体量有界：`项目数 × (1 + 3 + ≤2)`（§2.4）；★ `forge status` = **同一段、只有一个**（本项目，去身份行）。

**信息清单**（一个项目显示的全部事实）：

| 层 | 字段 | 来源 | 说明 |
| --- | --- | --- | --- |
| 身份 | `alias` · `blueprint` · `path` | `store.read("projects")` | 项目头一行 |
| 焦点 | `focus` | 同上 | 焦点项目置顶（当前恒缺省，§3.3） |
| `plan` | `plans` + `plan_status{open,reached,dropped}` | `plan.overview()` | 计划分布（§4.1） |
| `plan` | `tasks{total,done,doing,todo,blocked}` | `plan.overview()` | 任务分布 |
| `plan` | `latest_activity` | `plan.overview()` | ISO 原文；缺省 = 从无 `plan_log` |
| `plan` | `doing[]` / `blocked[]`（各 ≤3）· `⋯+K` | `plan.overview()` | 地址 + 标题；按最近活动降序（§4.1 末） |
| `inbox` | `total` + `status{open,handed,dropped}` | `inbox.list_items()` | 念头分布（§4.2） |
| `inbox` | `latest_created` · `oldest_open` | `inbox.list_items()` | ISO 原文；各自可缺省 |
| `aiwf` | `workflows` · `runs_total` · `running[]` · `last` | `observer`（aiwf 一路） | aiwf 的词，**透传**（§4.3.1） |
| `aiwf` | `AiwfRun{run_id, workflow_id, status, current, stages_done/total, wait}` | 同上 | `wait` = `action.kind`（`review` / `provide` …） |
| 容错 | `error`（逐分区） | 各读面 | 坏数据**显式显示**，不静默（§6.4） |

★ **`plan` 的那几行事实是「一次调用」拿来的**（`plan.overview()` → `06-plan` §6.4）：计数 / 分布 / `latest_activity` / `在做`·`卡住`（**连顺序**）都由**所有者**给 —— 本模块**不连事件、不拼地址、不排序**，只**截断到 3** 与**渲染**（§6.2）。

**渲染约定**：

1. **`plan` 分区恒 1 行摘要**（计数 + 分布 + `latest_activity`）；`在做` / `卡住` 行**仅非空时出现**（空则省 —— `tasks` 分布里已含 `blocked 0`）。
2. 动态项上限 **3**，超出给 `⋯ 还有 K 条`；★ **只对 `plan` 给「去哪看」**（`forge plan show`），`aiwf` 侧不给命令（§8-13）。
3. 时间戳一律给**原文 ISO**，引擎**不算「几天前」**（§4.4）。
4. `aiwf` 的词**原样**（§4.3.1），不翻译。
5. 分区为空照实说：`plan 0 份计划 —— 未记账` · `inbox 0 条` · `aiwf 流程 0 · 运行 0 —— 未接流程`。
6. 截断举例：若某项目 `doing` 有 7 个 → 第三项之后给 `⋯ 还有 4 条 → forge plan show`。
7. ★ **输出编码**：CLI 启动即把 `stdout` / `stderr` 钉成 **UTF-8**（`cli._configure_stdio`）—— 本视图含 `⏳` / `⋯` 等**非 GBK 字形**，否则 Windows 默认 cp936 下 `print` 直接 `UnicodeEncodeError`（实测）。

### 4.6 ★ 「最近动态」时间线

★ **要解决的问题**：§4.1–§4.3 的分区是**按来源分组**的 —— 一眼看全一个项目，但**跨项目「最近在发生什么、按时间排」答不出来**。而这恰好是「全局意识」最想要的那一问：**现在最该看的是什么**。

**做法**：把各分区里**已经带时间戳的事实**抽成 **`ActivityEntry`**，按 `ts` **降序**排一条；全局视图**置顶**（各项目 `recent` 由 `merge_recent()` 读时合成）。

```
ActivityEntry {
  ts:      string        # 时间戳（plan = ISO8601；inbox = 日期；aiwf = ISO8601）
  kind:    string        # "plan" | "inbox" | "aiwf"
  project: string?       # alias（全局视图下用来分辨是哪个项目）
  ...                    # 按 kind 各自带的字段（下）
}
```

| `kind`  | `ts` 来源                     | 其余字段                                                       |
| ------- | -------------------------- | ---------------------------------------------------------- |
| `plan`  | `plan.latest_activity`     | `doing[]` / `blocked[]`（**≤3 条**，owner 已排好）· `truncated` |
| `inbox` | **最近加入**那一条的 `created`     | `id` · `text`（截断）                                          |
| `aiwf`  | run 的 `started_at`         | `state`（`running` / `finished`）· `title` · `workflow_id` · `current` · `wait` · `stages_*` |

**排序与截断**：`ts` 降序（`None` → 排末尾）；同 `ts` 按 `kind` / 项目确定（L1 **G**）；全局**截断到 `RECENT_LIMIT = 6`**、本项目同样 6。

**三条口径**（★ 重要）：

1. **只挑「已经有时间戳」的** —— `plan` 的 `doing` 每条**没有**逐项时间戳（`overview()` 只给计数 + 排序后的列表），所以 `plan` 进时间线的是**一条**（`ts` = `latest_activity`，正文 = 在做 / 卡住摘要），**不臆造时间**（L1 **A1** / **D1**）。
2. **`inbox` 每项目只取最近 1 条** —— 分区里已经给了最近 3 条（§4.2），时间线再铺 3 条会把**别的项目挤掉**（H4）。
3. **全局时间线不落在 `Workbench` 上** —— `ProjectStatus.recent` 各带一份，全局由 `merge_recent()` 读时合成（§3.2 注）；否则同一份数据两处落（L1 **D** / **H4**）。

**渲染**（入口层，L1 **B**）—— 全局置顶的一段、本项目在身份行下的一段：

```
最近动态
  2026-10-10 14:35  drama_demo  ⏳ D01 · 第1集 在等你：review（S1 编剧 · 1/8）
  2026-10-09 21:04  mc-plus     在做 2 项：work-config-panels.TASK-006 自建双足编排演示…
  2026-10-09        mc-plus     记了念头 INB-015 把动力轴做成通用旋转输出，允许在轴上挂载非…
  2026-10-08 16:56  novel_demo  ⏳ 悬疑推理 · 名侦探柯南——单元案件驱动、主角聪… 在等你：review（角色设计 · 2/8）
```

**不做**：不按「重要度」重排（那是判断，L1 **B**）· 不给「跨项目动静汇总行」（§8-16 仍废）· 时间线**不替代**分区 —— 分区答「一个项目全貌」，时间线答「此刻最该看什么」。

## 5. 承载与接入

### 5.1 它**不**接入 `store` 的 `kind` 表

`03-store` §6.4 的接入公式是「**接入 = 加一份 schema 文件**」—— 对 `workbench` **不适用**：它**不产数据**，所以**不加 schema**。

| 步 | `plan` / `inbox`（写数据的用例）        | `workbench`（**视图**，只读）      |
| - | ------------------------------ | ---------------------- |
| ① | 定义模型 → 写 `schemas/<kind>.schema.json` | **无**（没有落盘模型）          |
| ② | 放进 `schemas/` → `store` 自动登记       | **无**                  |
| ③ | 用 `store.read` / `write`          | ★ **只用读**：`store.read`（自有 kind）+ `plan` / `inbox` 的**公开读面**（§6.2） |

> ★ 这说明 `03-store` §6.4 的公式**只覆盖「写数据的模块」** —— `workbench` 是**首个不写数据的模块**（`store` / `observer` 之外的第一个；L2 §3.1 的**视图**角色）。
> **`store` 的读写逻辑一行不动**（同 §6.4 的零改动承诺）。

### 5.2 它读什么（**所有者读面** + `observer` 一路）

| 数据 / 来源    | 所有者 | 怎么读 | 用来算 |
| -------------- | -------- | ------------------------------------------------ | ----------------- |
| `projects`     | `store`（**自有**） | `store.read("projects")`（**无 `project_root`**） | 清单 + `focus` + 身份 |
| `plans` / `plan_log` | 用例 `plan` | 逐项目调 **`plan.overview()`** —— ★ **一次调用给全**（计数 · 分布 · `latest_activity` · `doing`/`blocked` **连顺序**）；**不再**自己连事件 / 拼地址（`06-plan` §6.4） | `plan` 分区（§4.1） |
| `inbox`        | 用例 `inbox` | 逐项目调 **`inbox` 读面**：`list_items(show_all=True)` | `inbox` 分区（§4.2） |
| ★ 外部 aiwf   | **无人**（forge 之外） | 逐项目经 **`observer`**（**不自己读 `.aiwf/`**） | `aiwf` 分区（§4.3） |

**明确不读**（L1 **A1**：只要该场景需要的）：

| 不读                      | 为什么                                                              |
| ----------------------- | --------------------------------------------------------------- |
| `lock`                   | 三条问题用不到它；蓝图 id 已在 global 清单里（`05-scaffold` §3.6：lock 只记 payload 项） |
| **`.aiwf/` 的盘上文件**（含 `record.json`） | ★ **旁路**（L2 §2.2 不变量 2）+ 实测会读到**过期快照**（§4.3.2 ①）          |
| ★ **`plans.json` / `plan_log.jsonl` / `inbox.json` 本体** | ★ **旁路**：那是 `plan` / `inbox` 的**落盘文件**，不是它们的**读面**（L2 §4.2.1 **规则 1**：只经公开读面） |

> ★ **它知道 `plans` / `inbox` / `plan_log` 这几个 `kind` 名** —— 但只用来知道「这是谁的数据」；读一律**经所有者读面**（§6.2），**不 import 其内部实现、不读其落盘文件**。
> `kind` 名是**跨模块可见的表面**（L1 **F** 管的正是这个），已经在 `03-store` §6.2 的 kind 表里定过。

### 6.2 ★ 读经「所有者读面」（L2 §4.2.1）

**硬约束**：**不 import** `plan` / `inbox` 的**内部实现**、**不读**它们的**落盘文件**；读一律**经其公开读面**。

| 做法                                          | 允许？ | 依据                                                    |
| ------------------------------------------- | --- | ----------------------------------------------------- |
| ★ **`plan.overview(root)`**（`plan` 分区的一次调用）· `plan.list_plans` / `show_plan` / `read_events` · `inbox.list_items(root, show_all=True)` | ✅   | L2 **§4.2.1**：读数据经**所有者读面** |

| 直接打开 `<项目>/.forge/plans.json`               | ❌   | L2 **§4.2.1 规则 1**（不读对方**落盘文件**） |

### 6.3 与 `observer` 的接口（**只有 aiwf 一路**）

|         | 内容                                                                 |
| ------- | ------------------------------------------------------------------ |
| **方向**  | `workbench` → `observer`（**只读**）—— L2 §4.2 边 **8**                   |
| **要什么** | 逐项目的 **`AiwfSection`（§4.3）** —— 结构化值，**不落盘**                         |
| **谁实现** | `observer`（L2 §2.3②）—— **只做 aiwf 一路**（§7）；git / 文件系统**延后**         |
| **失败**  | 一路读不到 → 该分区 `error` + 其余照常（§6.4 / §7 ⑤）                             |
| **承诺**  | `observer` 落地后，这一路的信号**只进 `workbench`**，**不新增第二个消费者**（L2 §2.2 不变量 2 的理由）    |

### 6.4 失败语义

| 情形                                  | 行为                                                                                                     |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **global 清单缺文件**                     | `projects` 空 → 输出「还没有受管项目」＋提示 `forge new`（`store.read` 缺文件 = 空数据，`03-store` §5.3）                       |
| **某项目的 `plans` / `inbox` / `plan_log` 缺文件** | **不是错误** → 空数据（**读面按「缺文件 = 空数据」返回**，`03-store` §5.3）→ `plan.plans = 0`（显示「未记账」）· `inbox.total = 0` · `plan.latest_activity` 缺省（从无变动） |
| **某项目的数据不合 schema / JSON 损坏**        | 读面抛 `StoreError` → ★ **捕获它**，该项目的**那一分区** `error: <原因>`（其余分区照常），**其余项目照常输出**、命令 **rc=0**               |
| **`observer` 的 aiwf 路读不到**           | 该分区 `error: <原因>`；**其余两分区与其余项目照常**（§7 ⑤）                                                                   |
| ★ **aiwf 静默返回空**（路径写错 / 非 aiwf 项目）   | 实测 `aiwf` **不报错、rc=0、返回 `(no runs)`**（§4.3.2 ③④）→ ★ **不能当「真的没有」**：`observer` 须以 `cwd=<项目路径>` 显式调用，并把「项目路径不可达」与「真的没跑过」分开处置（§7 ①） |
| **`projects.json` 自身损坏**             | `StoreError` 冒泡 → **整条命令失败**（rc≠0）—— 它是唯一输入，坏了就没得算                                                         |

> ★ **第三条的关键**：**一个项目坏掉不能拖垮整张总览**，但也**不许静默吞掉** —— 必须把原因显示出来（`error` 字段 + 文本里一行 `读取失败：…`）。
> 依据：L1 **H2**（无歧义：坏就是坏）+ 本模块的存在意义就是「看清全局」，**藏错等于骗人**。

> **为什么有这一节**：L1 约定 **B** —— 引擎只做确定性事项，**其余归 agent + skill**。
> 本模块的**判断类职责**（要不要介入 / 哪个分区要紧 / 先干哪个）**全部**落在 skill 文本上（归**入口层**，`06-plan` §9 **T5** 同款）。
> **本节只列「要约束什么」，不写 skill 正文** —— 正文按**渐进披露**落 `skills/forge/references/`（`workbench` 面**尚未创建**）。

| 引擎**不做**        | skill 文本要写什么                                                                                | 依据                    |
| ------------------- | ------------------------------------------------------------------------------------------ | --------------------- |
| ★ **判断「要不要介入」**     | 怎么读三个分区的事实（`在做 / 卡住` 的任务 · 未处理念头 · **`在等你` 的 run**）→ 由 agent 与人**自己判断**；★ **别期待引擎给你结论** | L1 **B** + §1.1       |
| ★ **别找「项目状态」**      | `forge status` **不给**「这个项目处于某阶段」—— 它给**三个分区事实**；要判断就自己读三个分区（★ **名字叫 `status`，最容易误解**） | §4.0 + §8-3           |
| ★ **`aiwf` 的下一步怎么做** | 看到「⏳ 在等你：`review`」→ **跑 `aiwf runs show --view <run_id>`** 拿 aiwf 自己给的命令；**别猜命令格式**         | §4.3 + §8-13 + L1 **H3** |
| ★ **陈旧度怎么读**          | 引擎只给 **ISO 时间戳**（`latest_activity` / `oldest_open`）；**「几天前」由 agent 自己算** —— **别指望引擎给你「僵了 3 天」这种结论** | §4.4 + L1 **G**（引擎不算相对时间）+ **B** |
| **明细在哪看**           | 全局 `forge workbench`，本项目一眼 `forge status`；**明细**进项目用 `forge plan show` / `forge inbox list`（别在这找 `--verbose`）；★ **看到 `⋯ 还有 K 条` 就是截断提示**（§4.4） | §2.1 纪律 3 + §8-7 + §4.4 |
| **从任意目录跑**          | `forge workbench` **不需要** `cd`；`forge status` / `plan` / `inbox` **需要**（项目根 = CWD）—— 别混 | §2.1 纪律 2             |
| **别直读 `.forge/`**    | 同 `plan` / `inbox`：形态归 `store`，没有文件路径这回事                                                     | §2.1 纪律 4             |
| **别直读 `.aiwf/`**     | aiwf 运行状态**只经 `observer`→`workbench`**；尤其**别读 `record.json`**（它是旧快照）                            | §4.3.2 ① + L2 §2.2     |
| **别指望改状态**          | `workbench` **没有写动词**；改状态回项目里用 `forge plan` / `forge inbox`                                   | §2.1 纪律 1 + §8-1      |
| **坏数据要报**           | 看到 `读取失败：…` 就**如实转述**，别当「这个项目没东西」                                                            | §6.4 + L1 **H2**       |

> ★ **skill 是「判断」的落点**（L1 B）；**引擎是「读 + 确定性汇总 + 透传」的落点**。两者**不重叠**。
