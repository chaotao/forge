# forge · L0 定位与范围

> 层级：**L0（最高层）**。本文件不依赖任何下层文档。

---

## 1. 定位

> **forge 是面向 AI 协作项目的一站式工具（all-in-one）。**
> 把人与多个 AI 协作项目打交道时的各种痛点收在一处解决——
> 项目怎么立起来、计划怎么定、念头怎么记、手上几个项目分别到哪了；
> 目的是让人**对全部项目保有全局意识**，让项目**推进得更高效**。

**范围是开放的。** §3 列出的能力域是**当前已定的第一步，不是范围的边界**。
定位既然是"一站式解决 AI 协作项目的痛点"，**新增能力域是预期内的**；
但每加一个都要单独论证，不默认照单全收。

---

## 2. 服务对象与场景

| 项 | 内容 |
|---|---|
| 使用者 | **单人**（主人）+ 与之协作的多个 AI agent。**不是团队协作工具**——无多人、无权限、无审批流 |
| 协作形态 | 人做判断与决策，agent 做执行与记录；forge 是二者共用的记账本 |
| 项目数 | **多项目并行**（同时介入的项目会很多）→ 必须有跨项目视角 |
| 载体 | 同一台机器上的多个项目仓库；forge 自己不产出业务代码 |
| 入口 | **两个**：`forge` CLI（给人）+ forge skill（给 agent）。二者共用同一套内核 |

---

## 3. 范围之内：能力域

| 能力域 | 一句话 |
|---|---|
| `scaffold` | 一键初始化项目：目录 / Skills / aiwf 工作流 / 脚本 |
| `plan` | 定目标 → 定计划 → 执行追踪 |
| `inbox` | 需求捕获：把「现在不做但别忘」的念头记下来 |
| `workbench` | 跨项目总览：哪几个项目在开展、各自什么阶段、**哪些需要我介入** |

**核心命题**：这几件事原本散在「脚手架生成器」与「人脑记忆」两处；
forge 把它们收成**一个跨项目平台**，让人一处看全、一处介入。

> ⚠ 上表是**当前已定的部分**，不是完整范围（见 §1）。
> 粒度划分（「能力域」与「模块」的关系）归 **L2**，本层只确认：**这几件事在 forge 范围之内**。

---

## 4. 范围之外：边界

### 4.1 与 aiwf 的边界

**一句话：aiwf 只管「一次工作流运行的执行」，其余全归 forge。**

| 关注点 | 归属 |
|---|---|
| 工作流定义 / run / 执行记录 / 运行时队列 / 单 run 视图 / 模板库 | **aiwf** |
| 目标 / 计划 / 任务 / 依赖 / 焦点 / 收件箱 | **forge** |
| 项目身份 / 受管清单 / 项目阶段 / 跨项目总览 | **forge** |

三条已定的关系口径：

1. **forge 的 plan task 与 aiwf run 不挂钩**（甚至可能不知道 aiwf 存在）。
   task 是**通用任务**——可以指工作流、可以指一次 skill 直跑、**也可以什么引擎都不指**。
   任务描述里提一句「用工作流 X 跑」或存一个 link，是**文本 / 引用，不是外键**。
2. **aiwf 完全不知道 forge**；forge 可以读 aiwf（供工作台展示）。
3. **aiwf 不是全覆盖。** 简单任务走 skill / script 直跑，workflow 只留给需要
   状态持久化与人工 checkpoint 的长周期任务。→ 存在一类工作在文件系统里没有任何状态载体，
   工作台必须主动补齐这个洞。

### 4.2 与 skill-library 的边界

技能包的**注册与分发**归 skill-library；forge 只是**消费方**——在 scaffold 时按蓝图取技能落位。

### 4.3 明确不做

| 不做 | 理由 |
|---|---|
| 通用项目管理 SaaS / 团队协作工具 | 单人 + agent 场景，无人际协作与权限需求 |
| 一次工作流运行的执行 | 归 aiwf |
| 技能 / 工作流的注册与分发 | 归 skill-library / aiwf |
| 业务代码生成与实现 | forge 是编排层，不是代码生成器 |
| 绑定单一 agent | 必须跨 agent（`.trae / .workbuddy / .doubao / .qoder / .claude / .cursor`） |
| 项目的构建 / 测试 / 部署 | 属项目自身，forge 只记状态 |
