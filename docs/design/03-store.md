# forge · L3 模块设计 —— `store`

> 层级：**L3**。上游 = **L2 概要架构与模块划分**（`02-architecture.md`）。
> 本文件写 `store` 的**核心设计**；**实现以 `forge/store.py` 与 `forge/schemas/` 为准**。

---

## 1. 职责与边界

**一句话**：`store` 是 **forge 自有数据**的唯一读写者（L2 §2.2 不变量 2）。

|         | 内容                                                                                                                                         |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **做什么** | **读 / 写 / 查**（三个原语，L2 §2.3）                                                                                                                |
| **不做**  | ① **不做语义判断** —— "这条任务算不算完成"归 agent（L1 约定 B）<br />② 不读外部系统（归 `observer`）<br />③ 不写项目**业务内容**（由**产出它的用例**自行写，L2 §2.2）<br />④ **不暴露存储形态与存储位置**（L2 §2.5） |

**模型归属**（依 L1 约定 C「模型先行」）—— `store` 承载两类数据，但**只定义其中一类**：

| 数据                                                    | 模型由谁定义                                 | 本文件                      |
| ----------------------------------------------------- | -------------------------------------- | ------------------------ |
| **`store` 自有**：受管项目清单（global 域）· 落位记录 lock（project 域） | **本文件**（§4）                            | ✅ 定义                     |
| **用例数据**：plan · inbox ·（将来新增模块的数据）                   | **各自的用例模块 L3**（`06-plan` · `07-inbox`…） | ❌ 只给**承载与接入机制**（§3 / §6） |

> **依据**：L1 约定 D（单一事实源）—— 一份数据一个权威来源。`store` 是**写者**，不因此成为**模型所有者**；  
> 模型所有者 = "这份数据描述的是谁的事"。计划状态描述项目计划 → 归 `plan`。

## 2. 两个域与落点

| 域           | 落点                                          | 装什么                                         | 依据                  |
| ----------- | ------------------------------------------- | ------------------------------------------- | ------------------- |
| **global**  | **集中一处**：`<FORGE_HOME>/`，默认 **`~/.forge/`** | 受管项目清单 · 跨项目焦点                              | L2 §5.1 Q4 ①        |
| **project** | **`<目标项目>/.forge/`**                        | 计划状态 · inbox ledger · 焦点 · ad hoc 事项 · 落位记录 | L2 §5.1 Q4 ② · §4.3 |

**`FORGE_HOME` 环境变量**：默认 `~/.forge/`，可覆盖。  
依据 = **aiwf 的既有做法**（`AIWF_HOME`，默认 `.aiwf` —— 实读 `aiwf/engine/aiwf/storage.py:252`）。同类工具已有约定，不必另造。

> ⚠ **一处对 L2 §4.3 的精确化（不是改写）**：L2 说「退出 forge = 删 `.forge/` 一个目录」——  
> 那句说的是**项目内痕迹**。global 域另有一条登记，故完整动作 = **删 `.forge/` + 从 global 清单移除**。

## 3. 承载机制

### 3.1 目录与文件

**一个域一个目录 · 一份数据一个文件**：

```
~/.forge/                     # global 域（集中一处）
  projects.json               # 受管项目清单 + 跨项目焦点

<目标项目>/.forge/             # project 域
  lock.json                   # 落位记录：我装过哪几个
  plans.json                  # plan 用例数据（一项目多份计划）
  plan_log.jsonl              # plan 的过程事件（log 形态）
  inbox.json                  # inbox 用例数据
```

| 文件                           | 放什么            | **模型定义在哪**          | `store` 的角色      |
| ---------------------------- | -------------- | ------------------- | ---------------- |
| `<FORGE_HOME>/projects.json` | 受管项目清单 · 跨项目焦点 | **本文件**（§4.1）       | 定义模型 + 读写        |
| `<项目>/.forge/lock.json`      | 落位记录           | **本文件**（§4.2）       | 定义模型 + 读写        |
| `<项目>/.forge/plans.json`      | plan 用例数据（计划集合）     | `06-plan`（**已接入**）  | 只提供**承载与校验**（§6） |
| `<项目>/.forge/plan_log.jsonl` | plan 的过程事件（`log`）  | `06-plan`（**已接入**）  | 只提供**承载与校验**（§6） |
| `<项目>/.forge/inbox.json`     | inbox 用例数据    | `07-inbox`（**已接入**） | 只提供**承载与校验**（§6） |

> **⚠ 上表是"当前已知的"文件，不是封闭集。**  
> 文件由 `kind` 决定（§6.2），`kind` 由用例定义（§6.4）—— **一个用例可以定义多个 `kind`，就落多个文件**。  
> 例如 inbox 若要另放一份只增不改的历史记录，那是它的**第二个 `kind`**，在这里多一行而已，**`store` 零改动**。  
> 命名与切分规则见 **§3.4**。

### 3.2 文件实例

`~/.forge/projects.json`：

```json
{
  "version": 1,
  "projects": [
    {
      "path": "D:/proj/my_aigc",
      "alias": "my_aigc",
      "blueprint": "minimal",
      "stage": "scaffolded",
      "registered_at": "2026-10-08T11:20:00+08:00"
    }
  ],
  "focus": "my_aigc"
}
```

`<目标项目>/.forge/lock.json`：

```json
{
  "version": 1,
  "blueprint": "minimal",
  "entries": [
    { "path": "AGENTS.md",  "from": "blueprint:minimal" },
    { "path": ".gitignore", "from": "blueprint:minimal" }
  ]
}
```

> **lock 只记 `payload` 项**（= forge **自己落的**）。委托上游安装的组件（`skill:` / `aiwf:`）**不入账** ——
> 依据：组件装没装，权威在**上游**（`skill-library` 扫目录 / `aiwf` 的 `installed.json`），forge 再记一份 = 第二个事实源（L1 约定 **D**）。
> 详见 `05-scaffold` **§3.6**（含"要看时谁去读上游"）。

### 3.3 为什么拆文件而不是合成一份

| 理由         | 说明                                                   |
| ---------- | ---------------------------------------------------- |
| **可 diff** | 一份数据变更只动一个文件 → diff 小、合并冲突少（L2 §5.1 Q3 约束②）          |
| **归属可见**   | 文件名 = 数据所属模块 → 「**一个目录一个写者**」（L2 §4.3）在**文件粒度**上也看得见 |
| **接得住后补**  | `06-plan` / `07-inbox` 写自己的文件，**不必回来改 `03-store`**   |

### 3.4 命名与切分规则

**命名：文件名 = `kind` 名 + 形态后缀。**

| 情形                | `kind` 名    | 文件                  |
| ----------------- | ----------- | ------------------- |
| 模块的**主数据**        | `<模块>`      | `<模块>.json`         |
| 模块的**附属数据**（第二份起） | `<模块>_<角色>` | `<模块>_<角色>.json(l)` |

例：`inbox` 的主 ledger → kind `inbox` → `inbox.json`；若 inbox 另有一份历史流水（假设角色名 `events`）→ kind `inbox_events` → `inbox_events.jsonl`。

**为什么附属用 `_` 而不是 `.`**：`kind` 由 **schema 文件名派生**（§6.2 / §6.3），而 schema 文件是 `<kind>.schema.json`。  
若 `kind` 里带 `.`（如 `inbox.events`），文件名成 `inbox.events.schema.json` → **无法唯一切出 `kind`**（`.` 既当分隔符、又当扩展名的一部分）。  
用 `_` 时，"剥掉尾部 `.schema.json`"这一步是唯一的。

**切分：变更模式不同就拆成两个 `kind`**（判据见 §5.1）——  
**当前状态**（可原地改）与**只增不改的记录**（只往后加）**不共用一份文件**。

**命名约束**：`.forge/` 下的文件名 = **数据所属模块的名字**（`lock` 属 `store`；`plan` / `inbox` 属用例）。

## 4. 模型（`store` 自有部分）

依 **L1 约定 C**：模型先行；模型是唯一事实源；实现不得绕过、不得私自扩展。  
落盘形态 = **语言中立的 JSON Schema 文件**（`forge/schemas/projects.schema.json` · `lock.schema.json`，见 §6.3）。

### 4.1 `projects` —— 受管项目清单（global 域）

字段取自 L2 §2.3 的既有结论（路径 / 别名 / 蓝图 id / 阶段 / 注册时间 + 跨项目焦点），未新增语义：

```
Projects {
  version:   int           # schema 版本（模型变更须显式动作，C4）
  projects:  [Project]
  focus:     string?       # 跨项目焦点 = 某个 Project 的 alias；未设置则缺省
}

Project {
  path:          string    # 目标项目绝对路径
  alias:         string    # 短名，**全清单唯一** —— 它即"身份"，focus 等引用它
  blueprint:     string    # 蓝图 id
  stage:         string    # 阶段 —— 词表未定（S3）
  registered_at: string    # ISO 8601
}
```

### 4.2 `lock` —— 落位记录（project 域）

**只记 forge 自己落下的那些**（= `payload` 项）。**委托上游安装的组件（`skill:` / `aiwf:`）不入账** —— 见 §3.2 末。  
（L2 §5.2：**哈希与 `conflict` 列推后**。）

```
Lock {
  version:   int
  blueprint: string          # 本次落位用的蓝图 id
  entries:   [Entry]
}

Entry {
  path:   string             # 相对项目根的路径
  from:   string             # 来源（哪路来源 / 哪个组件）
}
```

**明确不写**（推后，L2 §5.2）：内容哈希 · 组件版本 · `conflict` 判定所需的比对字段。

**模型归属说明**：lock 是 `scaffold` 的**落位记录**，但它是 **forge 自有状态** → 落盘模型由本文件（写者 `store`）定义；  
`05-scaffold` 的落位步**按此模型产出**。若 `05` 发现不够用 → 不自行扩展（**C4**）。

## 5. 存储形态与写入（Q3，L2 下推）

**L2 给的约束**：① 数据访问层对外**只暴露结构语义**，不暴露形态（L2 §2.5）；② 形态须 **人可读 · 可 diff · 可入库**（L2 §5.1）。

### 5.1 形态是 `kind` 的属性，不是 `store` 的全局选择

L2 §2.5 已把数据访问层接口与存储形态**解耦** —— 形态属 `store` 的内部实现。**但它不能是单一全局值**：

| 判据                             | 说明                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------ |
| **不同数据的变更模式不同**                | `projects` / `plans` 是"读一份、改一处、写回"；**只增不改的记录**（历史 / 事件）是"只往后加"。用一个全局形态，等于让前者的模式替后者做决定 |
| **§6.4 已定"新模块接入 `store` 零改动"** | 形态若是全局单值，将来出现追加型数据就得回来改 `store` → **破掉那条承诺**                                         |

→ **形态由 schema 声明**（与 `scope` 同处，§6.2 / §6.3），**调用方不传**。

**选择判据：只看变更模式，不看数据量。**

| 形态                 | 落盘             | 写入                | 判据                     |
| ------------------ | -------------- | ----------------- | ---------------------- |
| **`snapshot`**（快照） | `.json`        | 整份读写 + 原子替换（§5.3） | 变更 = **改已有内容**（当前状态）   |
| **`log`**（流水）      | `.jsonl`（一行一条） | **追加一行**（§5.3）    | 变更 = **只往后加**（历史 / 事件） |

**一份数据只能有一种形态。** 混用会同时丢掉两边的优点 ——  
把历史记录塞进 `inbox.json` 的一个数组里，则每追加一条都要**读全量 + 重写全量**（追加不再廉价），  
且状态与流水共用一次 diff（流水的噪音污染状态的变更）。

**为什么 `log` 值得现在就定性**：它不是"以后可能要用"，而是 **§6.4 那条零改动承诺的承重点** ——  
承诺要对**任意形状、任意变更模式**的数据成立，形态就不能是单值。

### 5.2 候选与取舍

| 候选        | 人可读 | 可 diff | 可入库 | 判断                                         |
| --------- | --- | ------ | --- | ------------------------------------------ |
| **JSON**  | ✅   | ✅（行级）  | ✅   | **取它** —— 对应 `snapshot`                    |
| **JSONL** | ✅   | ✅      | ✅   | **取它** —— 对应 `log`；**不能原地改**，故只用于只增不改的数据   |
| Markdown  | ✅   | ✅      | ✅   | **结构有歧义** —— 要自己定义并解析，等于造一套格式 → 违 L1 约定 A1 |
| SQLite    | ✗   | ✗      | ✗   | 二进制，**直接违反 L2 约束②**                        |

**"只用 JSON 够不够"** —— 分两问答：

| 问                    | 答                                                                                                                          |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **快照型数据**（当前状态）      | **够** —— `snapshot` 形态不必换。规模到几十 ~ 几千条时整份重写的开销可忽略（几 KB ~ 几百 KB）                                                             |
| **追加密集的数据**（历史 / 事件） | **不够** —— JSON 数组的短板正在**追加**上：① 追加要**读全份 + 重写全份**（非 O(1)）；② 旧记录与当前状态混在一份文件里，**append-only 的账本语义丢失**；③ 流式读 / "看最近几条"都要先解析整份 |

JSONL 的代价（也是它只用于 `log` 的原因）：**不能原地改** —— 改一条要么重写整份，要么留墓碑。

### 5.3 写入方式

| 形态         | 写法                        | 为什么读者不会被卡住                        |
| ---------- | ------------------------- | --------------------------------- |
| `snapshot` | **原子替换**：写临时文件 → `rename` | 读者**永远**看到完整的一份，不会读到半截 JSON       |
| `log`      | **追加一行** + 行尾换行           | 追加**不重写**已有内容；最坏情况是最末一行不完整 → 跳过即可 |

**并发**：`store` 是**单一写者**（不变量 2）→ 两种形态都**不需要**行级并发控制。

**缺文件 = 空数据**（不报错）：`projects.json` 不存在 → 受管清单为空（首次使用即此状态）。

**实现范围**：`snapshot` 与 `log` 两种形态**均已实现**。  
`log` 的 `read` 读全部记录（缺文件 = `[]`；**末行不完整 → 跳过**，中间行损坏则报错）· `write` **追加一行**（校验单条）· `query` 对 `log` 允许省略容器前缀。**首个 `log` 形态的 `kind` 是 `plan_log`**。

**仍未定的候选是 `07-inbox` 的历史流水**（是否需要 / 叫什么 / 装什么由 **`07-inbox`** 定）—— 但它要的 `log` 机制**已就绪**，落地时不必再动 `store`。

### 5.4 版本控制

**`.forge/` 整个纳入版本控制** —— 该目录下**全部文件**（`projects.json` / `lock.json` / `plans.json` / `plan_log.jsonl` / `inbox.json`，以及将来新增的任意 `kind`）一律入库，**不加任何忽略规则**。

| 依据   | 说明                                                                  |
| ---- | ------------------------------------------------------------------- |
| 面向独立开发者 | 暂不需要更细的版本控制，版本冲突少                                                   |
| 附带好处 | `lock.json` 随仓库走 → **换机后 `scaffold` 重跑行为一致**（有 lock = 我装过 → `skip`） |
| 一条实操 | `.forge/` 里**不生成 `.gitignore`** —— 无需分治，也就没有"谁有权写忽略规则"的问题           |

## 6. 接口与扩展机制

### 6.1 三个原语

| 原语                               | 做什么                                        |
| -------------------------------- | ------------------------------------------ |
| `read(kind)`                     | 读一份数据（缺 → **空数据**，不报错）                     |
| `write(kind, value)`             | **校验后**落盘（校验范围见 §6.5；写法按该 `kind` 的形态，§5.3） |
| `query(kind, field_path, value)` | 按字段取值在数据内查找（如按 `path` / `alias` 找受管项目）     |

**边界**：**不暴露**文件路径、JSON 结构、分片方式、**存储形态** —— 用例只面对"字段与值"。  
这使 Q3 换形态（若将来变）时，**用例接口不变**（L2 §2.5）。

### 6.2 `kind` 表（由 `schemas/` 目录派生）

| `kind`     | `scope`   | **`形态`**   | 落点                           | 模型所有者       | 状态        |
| ---------- | --------- | ---------- | ---------------------------- | ----------- | --------- |
| `projects` | `global`  | `snapshot` | `<FORGE_HOME>/projects.json` | **`store`** | ✅ 已定义     |
| `lock`     | `project` | `snapshot` | `<项目>/.forge/lock.json`      | **`store`** | ✅ 已定义     |
| `plans`    | `project` | `snapshot` | `<项目>/.forge/plans.json`     | `06-plan`   | ✅ 已定义 |
| `plan_log` | `project` | **`log`**  | `<项目>/.forge/plan_log.jsonl` | `06-plan`   | ✅ 已定义（**首个 `log` 形态 `kind`**） |
| `inbox`    | `project` | `snapshot` | `<项目>/.forge/inbox.json`     | `07-inbox`  | ✅ 已定义 |


**`scope` 与 `形态` 都不由调用方传** —— 它们是 `kind` 的属性，记在表里。重复传会制造不一致。

> 本表只登记**已定义 / 已声明**的 `kind`。★ `06-plan` 已声明**两个**（`plans` + `plan_log`）—— 「一个用例可定义多个 `kind`」的**首个实际例子**；inbox 是否需要第二个 `kind`（历史流水，形态 `log`）由 `07-inbox` 定，  
> 到时本表加一行即可，**`store` 的读写逻辑不动**（§6.4）。

### 6.3 schema 从哪来：包内静态资源

**`forge/schemas/<kind>.schema.json`** —— 语言中立的 JSON Schema，**随 forge 发布**。

| 点                      | 说明                                                  |
| ---------------------- | --------------------------------------------------- |
| **它是模型的唯一事实源**         | 依 L1 约定 **C2**：校验 / 序列化 / CLI 表面 / 展示，一律从它派生        |
| **它声明 `scope` 与 `形态`** | `kind` 表（§6.2）由这些文件**派生**，不另立一份手工表 → 避免两处事实源（约定 D）  |
| **它不落 `.forge/`**      | 它是**代码**，不是数据。放进数据目录会制造第二个写者 → 破「一个目录一个写者」（L2 §4.3） |
| **沿用相邻工具做法**           | `aiwf/schemas/*.schema.json`（实测），forge 同构           |

### 6.4 新模块如何接入（= "适配后续不同模型"的答案）

**接入 = 加一份 schema 文件，`store` 的读写逻辑零改动。**

| 步 | 做什么                                                                | 谁做               |
| - | ------------------------------------------------------------------ | ---------------- |
| ① | 定义模型 → 写 `forge/schemas/<kind>.schema.json`（**声明 `scope` 与 `形态`**） | 新模块（**C1 模型先行**） |
| ② | 把文件放进 `forge/schemas/` —— `kind` 由文件名派生，`store` 自动登记               | 新模块              |
| ③ | 之后用 `store.read(kind)` / `write(kind, …)`                          | 新模块              |

**为什么这样就够了**：`store` **不假设数据的形状，也不假设它的变更模式** ——  
它按注册的 schema 校验、按声明的形态落盘，**不解释字段含义**。

| 模块          | 数据形状                                              | 变更模式  | 形态         | 对 `store` 的差别 |
| ----------- | ------------------------------------------------- | ----- | ---------- | ------------- |
| `plans`     | 一组计划（`plans[]`；每份计划 = 目标 / 判据 / 状态 + `tasks[]`） | 改已有内容 | `snapshot` | 无             |
| `plan_log`  | 只增不改的一行一事件                                      | 只往后加  | `log`      | 无             |
| `inbox`     | 一组事项 + 状态（ledger）                                 | 改已有内容 | `snapshot` | 无             |
| （例）某模块的历史流水（如 `plan_log`） | 只增不改的行                                            | 只往后加  | `log`      | 无             |
| 将来某模块       | 嵌套树 / 多份分片                                        | ——    | 按需         | 无             |

**唯二会触碰 `store` 的情况**（都不是"接入"）：

| 情况                                             | 性质                            | 走什么                   |
| ---------------------------------------------- | ----------------------------- | --------------------- |
| 需要一个新的 **`scope`**（= 出现 L2 §2.4.4 说的"新的数据所有者"） | **L2 级**增长                    | 须回到 L2 层处理         |
| 需要**第三种形态**（如随机读写 → SQLite）                    | 只加一个**落盘后端**；用例接口不变（L2 §2.5） | `store` **内部扩展** + 登记 |

### 6.5 校验的执行与语义的分界

`store` **执行**校验，但**不理解**校验的含义（L1 §2：C 管结构、B 管语义）：

|   | 检查什么                                     | 例子                                   |
| - | ---------------------------------------- | ------------------------------------ |
| ✅ | 合法 JSON / JSONL · 类型 / 必填 · 词表取值 · 引用完整性 | `stage` 是否是 schema 允许的取值             |
| ❌ | **语义判断**                                 | "这个任务算不算完成" —— 归 agent（约定 B）         |
| ❌ | **对 schema 内容的解释**                       | "`stage = scaffolded` 意味着什么" —— 归用例 |

校验所需的 schema 由 **§6.2 的 kind 表**提供 —— 只要是登记过的 `kind`，`store` 就能校验它，而**仍不需要理解它的语义**。

## 8. agent 使用视角（L1 约定 **H6**）

> **本节结论一句话：`store` 对 agent 没有直接面。** agent **永不**直接调用它，也**永不**直接读写 `.forge/` 下的文件。
> 这不是遗漏，是设计 —— 理由见 §8.1 / §8.3。

### 8.1 三条使用纪律

| # | 纪律                                                                                          | 依据                                                          |
| - | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 1 | **agent 不直接调 `store`** —— 三个原语（`read` / `write` / `query`）**只对用例开放**，不对 agent 开放                 | L2 §1 规则 3（出口收敛）+ L1 约定 **B**（语义归 agent + skill，引擎不做）       |
| 2 | **agent 不直读 `.forge/` 下的文件**（H4）—— 它看的是**用例渲染的视图**（如 `plan show`）；`.forge/` 是**引擎的存储**，不是 agent 的接口 | L1 约定 **H4** + §6.1（原语不暴露路径 / 结构 / 形态）                      |
| 3 | **agent 要写 forge 数据，一律经某个用例的命令**（`forge new` / `forge plan …`）；它**不需要知道**数据落在哪个文件、什么形态      | L1 约定 **H3**（一次意图 = 一次调用）+ **D3**（单一写者）                     |

> ⚠ 纪律 2 的现实风险与 `06-plan` §2.1 同源：`.forge/*.json` 是仓库里的**普通文件**，agent **天然会直接 `Read` 它** ——
> 该纪律必须写进 forge skill 明说（`06-plan` §9 **T8**）。**靠 agent"自觉"不算数。**

### 8.2 agent 眼里的 `store`：一条都不需要知道

| agent 想做的事     | 它调用                                 | 内部谁经 `store`                                    | agent 需要知道 `store` 吗 |
| -------------- | ----------------------------------- | ----------------------------------------------- | ------------------- |
| 新建项目并纳入受管      | `forge new <路径>`                    | `scaffold`（写 lock）+ `store`（登记 `projects`）       | **不需要**             |
| 看某个项目的计划       | `forge plan show …`                 | `plan` 读 `plans.json`                            | **不需要**             |
| 记一次任务状态变更      | `forge plan claim` / `done` / …     | `plan` 写 `plans.json` + 追加 `plan_log.jsonl`（一次调用） | **不需要**             |
| 看全局有哪些受管项目     | `forge` 的项目视图（归 `workbench`，**待写**）  | 读 `projects.json`                               | **不需要**             |

→ **对 agent 而言 `store` 是不可见的** —— 这正是数据访问层的正确状态（L2 §2.5：数据访问层对外只暴露结构语义，不暴露形态 / 位置）。

### 8.3 那谁"用" `store`（三个面，**都不是 agent 面**）

| 面            | 谁                                          | 怎么用                                                       | 依据                        |
| ------------ | ------------------------------------------ | --------------------------------------------------------- | ------------------------- |
| **用例**（程序内） | `scaffold` / `plan` / `inbox` / `workbench` | 调 `read` / `write` / `query` 三原语                            | L2 §2.2 不变量 2 + §4.2 边 5  |
| **人**（开发者）   | 开发者                                        | 把 `.forge/*.json` 当**普通文本文件**看 / diff / 手改（改完 `store` 下次读即是新值） | L2 §5.1（人可读 · 可 diff · 可入库） |
| **新模块作者**     | 未来的用例                                     | 加一份 `forge/schemas/<kind>.schema.json` 即接入，`store` **零改动** | §6.4                      |

> **为什么"agent 面留空"是对的、不是缺的**：给 agent 一个能直接写 `.forge/` 的口，会同时破坏三条上层约定 ——
> **D3**（单一写者：agent 会绕过用例，成为 `.forge/` 的第二个写者）、
> **B**（语义判断会以"原语调用"的形式挤回引擎侧）、
> **H3**（"一次意图 = 一次调用"要求入口是**语义动词**；`read` / `write` 是**无语义原语** —— 它们**不是**给 agent 用的表面）。
> 故本节在此的产出 = **明确"没有"，并说明为什么不该有**（H6 要求"写清怎么用"，对数据访问层模块，"怎么写清"就是这句）。
