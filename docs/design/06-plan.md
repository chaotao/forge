# forge · L3 模块设计 —— `plan`

> 层级：**L3**。上游 = **L2 概要架构与模块划分**（`02-architecture.md`）。
> 本文件写 `plan` 的**核心设计**；**实现以 `forge/plan.py` 为准**。

---

## 1. 职责与边界

**一句话**：`plan` 管**一个项目里的若干份计划**（一份计划 = 一个模块 / 一个 demo / 一个交付物）—— 每份计划的**目标 · 判据 · 状态** + 它的**任务**与**过程记录**。

|         | 内容 |
| ------- | ---- |
| **做什么** | ① **计划** `plans[]`：`title`（显示短名）· `goal`（目标陈述）· `criteria`（判据）· `status`（`open` / `reached` / `dropped`）<br />② **任务** `tasks[]`（可验收的最小执行单元）<br />③ **过程记录** `plan_log`（事件轨迹 —— 任务"当前上下文" = 其轨迹**末条 note**）<br />读写**经 `store`** |
| **不做**  | ① **不判"完成"** —— 判定归 agent（L1 约定 **B**）<br />② **不自行落盘**（经 `store`；`.forge/` 归它独占，L2 §2.2 **W3**）<br />③ **不建 aiwf 外键**（L0 §4.1）<br />④ **不落"计划书"**<br />⑤ **不做**甘特 / 关键路径 / EVM / 工时估算（§8）<br />⑥ ★ **不管"项目"本身** —— 受管项目条目归 `store` 的 **global 域**（`projects` kind，`~/.forge/projects.json`）；`plan` 只在**项目内**写自己的数据 |

### 1.1 它回答三个问题

| 问题               | 靠什么答                                                            |
| ---------------- | --------------------------------------------------------------- |
| 为什么做 · **成了没**   | `Plan.goal` + `criteria` + `status`（`reached` / `dropped`） |
| **有几份计划在推** · 走到哪了 | `plans[]` 列表 —— 每份计划的 `status` + 任务完成度                            |
| 谁在做 · 做完没        | `tasks[]`（`status` · `owner` · `done_when`）+ `plan_log`（过程）     |

### 1.2 边界（与谁无关）

| 对象          | 关系                                                                                        |
| ----------- | ----------------------------------------------------------------------------------------- |
| `store`     | **经它读写**（L2 §4.2 边 5）—— `plan` 不碰文件                                                       |
| `observer`  | **不依赖** —— 外部运行状态归它                                                                       |
| `workbench` | **只被读、不反向依赖** —— `workbench` 经本模块的**公开读面**读（L2 §4.2 边 **7b** · **§4.2.1**）；本模块**不**依赖它（**写路径零依赖**，L2 §4.2）。聚合细节归 `08-workbench` |
| `scaffold`  | **不依赖** —— 它立项目骨架 + 登记受管；`plan` 只管**自己项目里**的计划                                             |
| `aiwf`      | **不挂钩**（§7）—— task 与 aiwf run **无外键**，最多文本引用                                              |
| 项目文件        | **本轮零产物** —— 不落计划书；将来若要落，按 **W1** 由 `plan` 自己写、且**必须是对 `store` 的投影**（L2 §4.4 条款 3）        |

## 2. agent 使用视角（L1 约定 **H6**）

> **本节为什么排在这里**：L1 约定 **H1** 已定「**首要使用方是 agent**」—— 对外表面先按 agent 的易用性设计。  
> 故本文件把「**agent 怎么用**」提到模型之前（H5：**按完整流程设计，不按单命令设计**）。  
> 本节描述**使用叙事 + 契约**；命令的**机制与失败语义**在 §6。

### 2.1 五条使用纪律

| # | 纪律                                                                                             | 依据               |
| - | ---------------------------------------------------------------------------------------------- | ---------------- |
| 1 | **一次意图 = 一次调用**（H3）—— 认领 / 打回 / 完成 / 放弃都是**一个动词**，不由 agent 自己拼两步                               | L1 **H3**        |
| 2 | **不直读原始文件**（H4）—— `plans.json` / `plan_log.jsonl` 是**引擎的存储**，agent 只看 `show` / `log` 的**过滤视图** | L1 **H4**        |
| 3 | **优先走捷径**（H2）—— 认领 / 打回 / 完成 / 放弃**先找同名动词**，不退回 `set …`；`set` 只兜其余                             | L1 **H2 / H3**   |
| 4 | **判定由 agent 做，引擎只存**（L1 **B**）—— "这任务算不算完成""这份计划成了没"是 agent 的判断，写入即落盘                            | L1 **B**         |
| 5 | ★ **地址带计划**（H2）—— 指一个任务**必须写全** `<plan>.<task>`（如 `login.T3`）；**不存在"不带计划的 task id"**（**例外**：`--deps` 另**宽容**计划内裸 id —— 见 §2.4 注）             | L1 **H2** + §2.2 |

> ⚠ 纪律 2 的现实风险：`plans.json` 是仓库里的**普通文件**，agent **天然会直接 `Read` 它**。  
> ⚠ 纪律 3 的现实风险：`set --status` 照样能到 `done`（§2.5.1），agent **可能偷懒全用 `set`** → 轨迹全 `op:"set"`、**丢掉"打回 vs 完成 vs 放弃"的区分**。  
> **两条都只能靠 skill 明说约束** —— 靠 agent"自觉"不算数。见 `skills/forge/references/plan.md`「始终遵守」。

### 2.2 地址规则（N 份的前提）

```
login            ← 一个「计划」（plan）—— 项目内唯一
login.T3         ← 该计划里的任务（task）—— 计划内唯一，计划间可重名
```

- **计划标识 = slug**（`login` / `demo` / `worldbuilding`）—— **项目内唯一**。
- **任务标识 = 短名或序号**（`T3` / `login-flow`）—— **只在计划内唯一**（跨计划 `T1` 可以重复）。
- **`done` 对两级通用**：「这实体成了」= task → `done`、计划 → `reached` —— **一条表达**（H2）。
- **无隐式解析**：`plan done T3` **不存在**（没有计划 → 无法定位）→ 引擎直接拒 → 无歧义（H2）。

### 2.3 完整流程（一个新会话接手项目）

> 场景：**新会话的 agent** 接手项目，主人只说一句"继续推进"。

| 步 | agent 做什么           | **一次调用**                                | 拿到什么（H4：只要该场景需要的）                                                   |
| - | ------------------- | --------------------------------------- | ------------------------------------------------------------------- |
| 0 | **看全局** —— 有几份计划、各到哪了 | `forge plan show`                       | **plans 列表**：每份计划 `id` / `title` / `status` / **任务完成度**（**不含 goal / 轨迹**） |
| 1 | **挑一份计划**             | `forge plan show login`                 | 该计划：`title` / `goal` / `criteria` / `status` + **任务列表**（**不含轨迹**）         |
| 2 | **挑一个任务**           | `forge plan show login.T3`              | **交接包**：T3 当前状态 + **完整轨迹**（末条 note = 现在基于什么情况）                      |
| 3 | **认领**              | `forge plan claim login.T3`             | 状态 `todo → doing`，owner = `agent`                                   |
| 4 | **干完交付**            | `forge plan done login.T3 --note "…"`   | 状态 `→ done` + **轨迹自动追一行**                                           |
| 5 | **（验收方）打回**         | `forge plan reject login.T3 --note "…"` | `→ doing` + 轨迹追一行（**`--note` 必填** = 打回原因）                           |
| 6 | **（遇阻）要人介入**        | `forge plan block login.T3 --note "…"`  | `→ blocked` + 轨迹追一行                                                 |
| 7 | ★ **这份计划成了**          | `forge plan done login`                 | 计划 `→ reached` + 轨迹追一行                                               |
| 8 | ★ **这份计划不做了**         | `forge plan drop login --note "…"`      | 计划 `→ dropped` + 轨迹追一行                                               |
| 9 | **回看**（跨计划"最近发生了什么"） | `forge plan log`                        | 全项目时间线**尾部 20 行**（默认，§2.4）                                          |

**agent 从头到尾没"另外写日志"** —— 轨迹是操作的**副产品**（H3），自己长出来。  
**任务的"当前上下文"没有单独字段**：它就是 `plan show <plan>.<task>` 里轨迹的**末条 note**。

★ **另有汇总读面 `plan.overview()`（§6.4）** —— 它不是 agent 的**步骤**，是**程序读面**：视图型用例 `workbench` 用它，**不经 CLI**。

### 2.4 命令总表

**写（7 个动词 / 5 个捷径）** —— 一个意图一个动词：

| 写动词                                                                | 用途                                                | 强制              |
| ------------------------------------------------------------------ | ------------------------------------------------- | --------------- |
| `plan add <plan> --title "…" --goal "…" [--criteria "…" …]`               | 新建**一份计划**                                          | `--title` · `--goal` |
| `plan add <plan>.<task> --title "…" [--done-when "…"] [--owner …] [--deps …]` | 新建**一个任务**                                        | `--title`       |
| `plan set <id> [--status][--owner][--note][--goal][--title]`           | **兜底** —— 其余一切改动（只改 note / 改 goal / 改 title / 转 owner） | 至少给一项           |
| `plan claim <plan>.<task>`                                         | **认领**（`→ doing` + `owner`）                       | —               |
| `plan block <plan>.<task> --note "…"`                              | **卡住**（`→ blocked`）                               | `--note`        |
| `plan reject <plan>.<task> --note "…"`                             | **打回**（`→ doing`）                                 | **`--note` 必填** |
| `plan done <id>`                                                   | **完成** —— task → `done`；**计划 → `reached`**         | —               |
| `plan drop <plan> --note "…"`                                      | **放弃一份计划**（`→ dropped`）                             | `--note`        |

> `add` / `set` 是**通用**（一建一改）；`claim` / `block` / `reject` / `done` / `drop` 是**语义捷径**（各映射到一次 `set`）。  
> 上表 8 行 = **7 个动词**（`add` / `set` / `claim` / `block` / `reject` / `done` / `drop`），其中 `add` 与 `set` 之外是 **5 个捷径**。
>
> `--deps` 的**入参形态**：收 **全地址** `<plan>.<task>`（**规范**，§2.1 纪律 5）**或**计划内裸 id（`T1`，宽容 —— `deps` 是计划内引用）；**存盘统一为计划内裸 id**（§3）。计划部分与本计划不一致 → **拒**（跨计划依赖本轮不做，§8 / §9 **T12**）。

**读（4 个视图）** —— 都不吐 `plans.json` 原始文件；输出默认**结构化文本**、另给 `--json` 机器可读；**默认体量按"有没有界"分**：

| 读视图                       | 返回                                                | 过滤器                                 | **默认体量**                        |
| ------------------------- | ------------------------------------------------- | ----------------------------------- | ------------------------------- |
| `plan show`               | **plans 列表**：每份计划 `id` / `title` / `status` + 任务完成度（**不含 goal / 轨迹**）        | `--status <s>`                      | **全量**（有界：计划数）                   |
| `plan show <plan>`        | **单份计划**：`title` / `goal` / `criteria` / `status` + 任务列表 | —                                   | **全量**（有界：单份计划任务数）                |
| `plan show <plan>.<task>` | **单任务交接包**：状态 + **完整轨迹**                          | `--tail N`                          | **全量**（有界：单任务轨迹）—— 交接要完整        |
| `plan log`                | **跨计划时间线**（含 note）                                 | `--tail N` · `--all` · `--plan <p>` | **`--tail 20`**（**无界**：随项目寿命增长） |

> **为什么不用同一个默认值**：三条视图**有界**（计划数 / 单份计划任务数 / 单任务轨迹），截断只会**伤交接**；  
> `log` 跨计划、随项目寿命**无界增长**，不给默认截断就**会炸 token**（H4）。  
> → **默认值贴合各自的界**（H4 + H5）。

> **输出契约（4 个视图一致，H2）**：默认渲染**结构化文本**（表格 / 分组，人眼可读）；加 `--json` 输出**同一过滤视图**的机器可读结构  
> （脚本 / 程序消费；**不是 `plans.json` 原文** —— 过滤与默认体量规则照旧生效）。  
> **为什么一致**：① 入口层**已有** `--json`（`forge/cli.py`，如 `forge new --json`）—— 读侧不给会出现"**有的命令有、有的没有**"的**表面不一致**（违 **H2**）；  
> ② `--json` 只是**对同一模型的另一种序列化**，不新增语义、不新增事实源（L1 **C / D** 无碍），边际成本仅一次序列化。


### 2.5 一个意图 = 一次调用（映射）

**捷径与 `set` 等价** —— 捷径让高频 / 语义重的动作**零歧义**（H2），`set` 保证表面**封闭不失控**：

| 捷径                                 | 等价于 `set`                                        | 要点                                  |
| ---------------------------------- | ------------------------------------------------ | ----------------------------------- |
| `plan claim <plan>.<task>`         | `set <plan>.<task> --status doing --owner agent` | 认领                                  |
| `plan block <plan>.<task> --note`  | `set <plan>.<task> --status blocked --note`      | 卡住                                  |
| `plan reject <plan>.<task> --note` | `set <plan>.<task> --status doing --note`        | **打回**（`op` 与 `claim` 不同 —— §2.5.1） |
| `plan done <plan>.<task>`          | `set <plan>.<task> --status done`                | 任务完成                                |
| ★ `plan done <plan>`               | `set <plan> --status reached`                    | **宣告这份计划达成**                          |
| ★ `plan drop <plan> --note`        | `set <plan> --status dropped --note`             | **宣告这份计划放弃**                          |
| `plan set …`                       | ——（它就是兜底）                                        | 其余一切                                |

> **为什么捷径是 5 个**：★ **计划的达成 / 放弃**是**语义重且必须留痕**的动作 ——  
> 它决定"**这个项目里哪份计划停了**"（`workbench` 要答的问题之一）。让 agent 自己拼 `set --status dropped`  
> 会**丢掉"放弃"这个意图**（轨迹里只剩 `op:"set"`）。其余改动仍走 `set`，**不再加第 6 个捷径**（L1 **A1**）。

#### 2.5.1 `op` 双轨与"优先走捷径"

`set --status` **与**捷径并存 ⟹ 同一状态有**两条到达路**。**不收紧**：

| 到达路              | `Event.op` 记什么 | 例                                                                           |
| ---------------- | -------------- | --------------------------------------------------------------------------- |
| 走捷径              | **捷径名**        | `plan reject login.T3` → `{op:"reject", from:"doing", to:"doing"}`          |
| 走 `set --status` | `"set"`        | `plan set login.T3 --status doing` → `{op:"set", from:"doing", to:"doing"}` |

**要点**：`op` 记的是 **agent 实际用的动词** —— 它自描述"agent 意图是什么"，不由引擎从 `(from,to)` 反推。  
（**反推不可行**：`claim` 与 `reject` 的 `(from,to)` 都是 `*→doing`，推不出。）

**残留风险（明说）**：agent 若全走 `set`，轨迹会全是 `op:"set"`、**丢掉"打回 vs 完成 vs 放弃"的区分**。  
**对策 = 纪律，不是砍接口**：在 **skill** 里写「**先找同名动词，找不到再 `set`**」（§2.1 纪律 3）—— 见 `skills/forge/references/plan.md`。  
→ 与 `plans.json` 不直读那一条**同源**：**agent 的读 / 写习惯都靠 skill 约束**，不靠把接口砍到只剩一条路。  
**唯一反悔点**：若将来要 `op` **绝对单一**，再收紧为"状态变更必走名词动词"（那需补一个回到 `todo` 的动词，登记 §9 **T10**）。

### 2.6 token 纪律（视图分工，H4）

| 视图                        | 带轨迹？                | 默认体量                | 为什么                                      |
| ------------------------- | ------------------- | ------------------- | ---------------------------------------- |
| `plan show`（列表）           | **❌ 不带**            | 全量（有界）              | N 份计划 × M 任务 × 轨迹 → **必炸**；全局只需知道"哪份计划到哪了"   |
| `plan show <plan>`        | **❌ 不带**            | 全量（有界）              | N 任务 × 轨迹 → **必炸**；计划视图只需"这份计划有哪些任务、各自什么状态" |
| `plan show <plan>.<task>` | **✅ 带**（可 `--tail`） | **全量**（有界）          | 单任务，轨迹有限；这就是"**交接包**"，截断会丢上下文            |
| `plan log`                | **✅ 带**（可 `--tail`） | **`--tail 20`**（无界） | 跨计划时间线随项目寿命增长 → 默认必须封顶（H4）                |

**两条规则**：

1. **轨迹（含 note）只跟随「单任务」或「显式 `log`」视图；列表视图与计划视图都不带轨迹、也不带 note。**
2. **默认体量贴合各自的界**：有界的给全量，无界的给封顶。
3. **计划级字段按视图分**：`goal` / `criteria` **只在单份计划视图**（步 1）；列表视图（步 0）只给 `id` / `title` / `status` / 完成度 —— 列表要"一眼扫完"（H4）。

> 这条同时**反证**了「不落计划书」：要给人 / agent 看，就渲染一份**带过滤的视图**（`show` / `log`），**别让它啃 `plans.json` 原文**。

## 3. 模型

依 **L1 约定 C**（模型先行）。落盘形态 = 语言中立的 JSON Schema（`forge/schemas/plans.schema.json` / `plan_log.schema.json`，§5）。

### 3.1 计划集合（`kind` `plans` · snapshot）

```
Plans {
  version: int             # schema 版本（变更须显式动作，C4）
  plans:   [Plan]
}

Plan {
  id:        string        # 计划标识（slug）—— 项目内唯一（机器地址）
  title:     string        # 显示短名（名词短语）—— 全局列表用
  goal:      string        # 目标陈述（一句话）—— 单份计划视图用，也是 criteria 的语境（原 Objective.statement）
  criteria:  [Criterion]   # 判据 —— ≥1 条
  status:    string        # open | reached | dropped
  tasks:     [Task]
}

Criterion {
  text:  string            # 一条可核对的断言
  check: string?           # 给 agent 的提示（"这条可以这样核"）；引擎只存不执行（L1 B）
}

Task {
  id:        string        # 计划内唯一
  title:     string
  status:    string        # todo | doing | done | blocked
  deps:      [string]?     # 前置任务 id（**同一份计划内** · **计划内裸 id**，如 `T1`）；无依赖不写
  owner:     string?       # human | agent（L0 §2 人机分工）
  done_when: string?       # 验收条件（一句话）
}
```

**`Plan` 的两个文本字段分工**：`title` = **标签**（名词短语，如"登录模块"）—— 全局列表用它；`goal` = **目标陈述**（动词导向，如"让用户能安全注册 / 登录 / 找回密码"）—— 单份计划视图用它，也是 `criteria` 的语境。**两个都必填**。

**`Task` 上没有 `objective` 字段**：task 住在 `Plan.tasks` 里 —— **父级即结构**，不需要字段。  
**`Task` 上没有 `note` 字段**：`note` 只存在于 `plan_log` 的事件上；任务「当前上下文」= 其轨迹的**末条 note**（读时取，§3.2）。

### 3.2 过程事件（`kind` `plan_log` · **`log`**）

```
Event {
  ts:   string             # ISO 8601
  plan: string             # ★ 哪一份计划（计划标识）—— N 份的前提
  id:   string             # 被改实体的 id（计划事件 = 计划 id；任务事件 = 任务 id）
  op:   string             # add | set | claim | block | reject | done | drop（= 写动词集，§4）
  from: string?            # 变更前的 status
  to:   string?            # 变更后的 status
  note: string?            # 本次附带的一句话（打回原因 / 完成说明 / 放弃原因…）
}
```

一行 = 一次写操作的**事实**（`plan` 写盘时**自动**追加，agent 不单独记，§2.1 纪律 1）。  
`op` 记 **agent 实际所用的动词**（§2.5.1）—— 走捷径记捷径名、走 `set` 记 `set`。

★ **`plan` 维度是 N 份的前提**：没有它，事件分不清属于哪份计划。

**`Event` 是「源」，不是「派生」**：它是 agent 写入的操作事实 —— **必须落盘**。  
**`note` 只有这一个家**：任务不另存 note 字段，"当前上下文" = 该任务轨迹里**最后一条带 note 的事件**。  
→ **一份数据一个权威来源**（L1 **D1**），**零重复**。

### 3.3 四个"没有"是刻意的

不为"以后可能需要"预留结构（L1 **A1**）：

| 没写进去                          | 为什么                                                                                                                      |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **`Plans.status`**（项目级状态）     | "这个**项目**到哪了" = 它的**计划**的聚合（几份计划 `open` / `reached` / `dropped`）—— **读时派生**（L1 **D2**）；落盘即第二事实源。**归 `workbench` 算** |
| **`Task.note`**               | 「当前上下文」= `plan_log` 轨迹末条 note（**读时取**）—— 另存字段与最后一条事件**恒等**，是重复（L1 **D1**）                                                |
| **`plans` / `tasks` 的顺序字段**   | 数组顺序即顺序（A1）；计划的"当前阶段"由各自 `status` 与任务完成度定，不由序号定                                                                           |
| **`Task.objective` / 任何跨计划关联** | 层级**封顶 3 层**（项目 → plan → task）；task 的父级由**结构**（住在谁里）决定 —— 不需要字段                                                  |

**为什么"判定落盘、聚合派生"**：判定（"这**计划**成了没 / 不做了"）是**语义**，归 agent（L1 B）→ **必须落盘**（`Plan.status`，它是源）；聚合（"这个**项目**到哪了"）是**确定性的**，归引擎 / 读侧 → **不落盘**（L1 D2）。

## 4. 词表

**三张封闭**词表（由 schema 枚举约束，L1 **C3**：校验只到结构层）。取值用**英文 token**（与 `store` 的 `stage` 同风格）。

| 实体      | 字段       | 取值                                                             | 说明                                                                                 |
| ------- | -------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `Plan`  | `status` | `open` · `reached` · `dropped`                                 | `reached` = 达成（agent 判定）· `dropped` = **显式放弃** —— "这份计划不做了"的合法出路（否则被弃的计划把项目永远钉在未完成）   |
| `Task`  | `status` | `todo` · `doing` · `done` · `blocked`                          | **4 态**。`blocked` 是「哪些需要我介入」最干净的**任务级**信号                                          |
| `Event` | `op`     | `add` · `set` · `claim` · `block` · `reject` · `done` · `drop` | **枚举 = 写动词集**（§2.4）；`op` 记 **agent 实际所用动词**（捷径名 / `set`），非由 `(from,to)` 反推（§2.5.1） |

**词表纪律**：**每个态都必须有人 / agent 能维护**。所以词表**短**，且**不引入任何"引擎自动推进"的态**（L1 B）。

> ⚠ 注：`op` 枚举里的 `set` 不是"第 6 条捷径"，而是**通用兜底的留痕**；`status` 词表（`Plan` 3 态 / `Task` 4 态）**不因 `op` 有 7 值而变**。

## 5. 承载与接入

**不新造机制** —— 完全走 `03-store` 已定的接入路径。`plan` 有**两个 `kind`**（一个用例可有多个，`03-store` §6.4）：

| `kind`     | `scope`   | 形态         | 落点                           | schema（**包内**）                       |
| ---------- | --------- | ---------- | ---------------------------- | ------------------------------------ |
| `plans`    | `project` | `snapshot` | `<项目>/.forge/plans.json`     | `forge/schemas/plans.schema.json`    |
| `plan_log` | `project` | **`log`**  | `<项目>/.forge/plan_log.jsonl` | `forge/schemas/plan_log.schema.json` |

**校验**（**结构层**，L1 B / **C3**）：类型 / 必填 / 词表取值 / **引用完整性**（`Event.plan` 指向存在的计划 · `deps` 经**归一化**后指向**同计划内**存在的任务 —— 全地址 `login.T1` 与计划内裸 id `T1` 都收、跨计划拒）/ `deps` **无环**。

> ★ **`plans` 是一个「集合文件」，不是"每份计划一个文件"** —— 理由：`03-store` §6.2「**一个 `kind` 一个文件**；kind 表由 `schemas/` 目录派生」；  
> "每份计划一个文件"要求 `store` 支持**多文件 kind** = 新机制（违 L1 **A1**）。集合文件与 `store` 自己的 `projects`（`{ projects: [...] }`）**同形**。

**版本控制**：随 `.forge/` **整体入库**（`03-store` §5.4，S1 = B）→ `plans.json` 天然可 diff、有历史。

**接入是"零改动"**：新模块只需**加 schema 文件**，`store` 读写逻辑不动（`03-store` §6.4）。

## 6. 接口

### 6.1 底层：只用 `store` 的三个原语

| 动作      | 怎么走                                             |
| ------- | ----------------------------------------------- |
| 读       | `store.read(<kind>)`（缺文件 = **空数据**，不报错）         |
| 写       | 读 → 改 → `store.write(<kind>, value)`（**校验后**落盘） |
| 查（按 id） | `store.query(<kind>, field_path, value)`        |

**语义判定不在引擎里**（L1 B）："这任务算不算做完""这份计划成了没"归 **agent**（由 forge skill 约束其行为）。引擎只做 **结构校验 + 存储**。

### 6.2 语义操作层（§2 的操作面，落在这里）

§2 的写动词**不是** `store` 的原语 —— 它们是 `plan` 提供的**语义操作**，内部**组合** `store` 调用。  
**规则：每次写操作必定追加一条 `plan_log`（note 的唯一归宿）；仅当 `status` / `owner` 变时才改 `plans.json`。**

```
plan done login.T3 --note "…"  ──▶  ① store.write("plan_log", 追加 {plan:"login", id:"T3", op:"done", from:"doing", to:"done", note})
                                    ② store.read("plans") → 改 T3.status → store.write("plans", …)      ← 仅当状态变
plan set login.T1 --note "…"   ──▶  ① store.write("plan_log", 追加 {plan:"login", id:"T1", op:"set", note})   ← 只改 note → 只动 log
plan drop login --note "…"     ──▶  ① store.write("plan_log", 追加 {plan:"login", id:"login", op:"drop", from:"open", to:"dropped", note})
                                    ② store.read("plans") → 改 login.status → store.write("plans", …)
```

| 要点              | 说明                                                                              |
| --------------- | ------------------------------------------------------------------------------- |
| **不新增写路径**      | 仍**全经 `store`**（L2 §1 规则 3 · §2.2 **W3**）；`plan` 只是**组合**它                      |
| **一次 agent 调用** | 上面两步对 agent 是**一次调用**（H3）—— agent 不需要知道有两个文件、两次 `store` 写                       |
| **无旁路**         | `plan` 是**人 + agent 共用**的（L0 §2）：人在 CLI 上改、agent 经 skill 改 —— 两者都**只经 `store`** |
| **命令表面归入口层**    | 具体 `forge plan …` 的拼法归**入口层**；但**操作集由本模块定义**（H5：按完整流程设计）             |


### 6.3 失败语义（登记 §9 **T7**）

> ★ **读函数 = 对外表面**：本节 §6.2 的四个**读视图**（`list_plans` / `show_plan` / `show_task` / `timeline`）· `read_events()` 与 §6.4 的 **`overview()`** **不只在 `forge plan` CLI 内部使用** ——
> 它们是 `plan` 对**其他模块**的**公开读面**（现由 `workbench` 消费，L2 §4.2.1）。**改它们的签名 / 返回形状 = 改对外契约**。
> ★ 相应地：`workbench` **不 import 本模块内部实现、不读 `.forge/plans.json`** —— 一律经这些读函数（含 §6.4 的 `overview()`）。

`set` / 捷径内部是**最多两次 `store` 写**（`plan_log` **总写**；`plans` **条件写**）。**两写之间失败怎么办**（先写哪个、一半成功要不要回滚）**不定**，登记 **T7**。  
倾向（未定）：**先写 `plan_log` 再写 `plans`** —— 轨迹是"事实"，宁可多一条孤立事件，不可丢一次状态变更；但需在 T7 里正式裁。

### 6.4 汇总读面 `overview()`（**程序接口** —— 无 CLI 出口）

**为什么加它**：`workbench` 的 `plan` 分区要的是**四个派生事实** —— 计数 / 分布 / 最近活动 / 在做·卡住清单。
只给「按计划」与「按事件」两种原始读面，消费方就得自己**把事件按 `(plan, id)` 连到任务**、自己**拼 `<plan>.<task>` 地址**、自己**定「最近活动」的取法**
—— 那是**重算语义**：同一份知识两处实现（违 L1 **D1**），且本模块改词表 / 改地址规则时**静默出错**（这正是 L2 **§4.2.1** 要防的）。

**签名**：`overview(project_root) -> dict`（**一次调用给全**；**不设上限** —— 上限归呈现，见口径 2）

| 字段                  | 类型                                    | 说明                                                                                |
| ------------------- | ------------------------------------- | --------------------------------------------------------------------------------- |
| `plans`             | `int`                                 | 计划数；`0` = **未记账**（消费方照此渲染）                                                        |
| `plan_status`       | `{open, reached, dropped}`            | 计划状态**分布**（恒含三键，为零也给）                                                             |
| `tasks`             | `{total, done, doing, todo, blocked}` | 任务**分布**；`total` = 四态之和                                                          |
| `latest_activity`   | `string?`                             | `plan_log` **末条**事件的 `ts`（ISO）；**从无事件 → 缺省**（同 `08-workbench` §4.4）                  |
| `doing` / `blocked` | `[{address, title}]`                  | **全量、已排序**：按该 task 轨迹**末条事件的 `ts` 降序**；**无事件排末尾**；**同键按地址升序**（L1 **G**）             |

**三条口径**：

1. **排序键不返回** —— 「顺序本身就是信号」（`08-workbench` §4.1）；返回里只留 `address` + `title`。
2. **不截断** —— `doing` / `blocked` 给**全量**；「最多 3 条 + `⋯+K`」是**呈现**约定，归消费方（L1 **H4** 落在视图层）。
3. **缺文件 = 空数据** —— 同其它读面（§6.1）：给零值，不报错。

**为什么无 CLI 出口**（L1 **A1**）：它不是给 agent 的**步骤视图**（§2.3 的 0–9 步已覆盖人的用法），唯一消费者是**视图型用例** `workbench`（其**本项目出口** `forge status` 即调它）。将来若人要单看，再议。

★ **它是公开读面** —— **改签名 / 返回形状 = 改对外契约**（同 §6.3 的注）。

## 8. 明确不做（由模型决定，不是遗漏）

| 不做                       | 为什么                                                                                                             |
| ------------------------ | --------------------------------------------------------------------------------------------------------------- |
| 甘特图 / 关键路径 / 时间轴         | 无强依赖场景 —— 单人 + 多项目并行                                                                                            |
| EVM / KPI / 燃尽图 / 工时估算   | 个人项目不适用；到这个粒度估算误差已大于管理收益                                                                                        |
| 风险登记表                    | 阻塞已是 `Task.status` 的一个态，风险写在任务上即可                                                                               |
| WIP 限制 / 迭代 / 看板         | 属**执行层**，归 aiwf run                                                                                             |
| RACI 四角色                 | 单人场景无区分意义 → 简化为单一 `owner`                                                                                       |
| **多层分解**（task 之下再分层）     | 封顶 **3 层**（项目 → plan → task），再往下是负收益                                                                     |
| **里程碑实体**（`Milestone`）   | **取消**：无论建不建 task 链都站不住 —— **不建链** = 无动词的死字段；**建链** = 派生不落盘，只剩分组标签。计划的"下一道门"由**一个 `done_when` 可验收的 task** 表达 |
| **`Objective` 实体**       | **压平**：降为 `Plan.title` + `goal` + `criteria` + `status` 四个字段；三样都**没有别的家**，故不是省概念而是换形态                            |
| **跨计划依赖**（`deps` 指到别的计划）   | 本轮**不做** —— `deps` 限**同计划内**；跨计划关系属"计划与计划之间"的事，超出本轮（登记 §9 T12）                                                      |
| **管理"项目"层**（受管清单 / 增删项目） | 归 `store` 的 global 域（`projects`）+ `scaffold` / `workbench`；`plan` 不碰                                            |
| **全量审计日志**（可回溯到任意时点的账本）  | `plan_log` 是"**过程上下文**"，不是审计账本；要审计归 **git**（`.forge/` 入库）                                                       |
| **diff / 评论线程 / 富文本反馈**  | 反馈全文归**执行侧**（aiwf run）或任务描述**文本引用**；forge 不持有执行史                                                                |
| **把 `set --status` 收紧掉** | 不收紧：`op` 双轨靠 **skill 纪律**约束，不靠砍接口（§2.5.1）                                                     |
| **`overview()` 的截断 / 渲染** | 那是**呈现**（归视图型用例 `workbench`）—— 本模块只给**全量与顺序**（§6.4 口径 2）                                                                  |
