# forge · L1 设计原则

> 层级：**L1**。上游 = **L0 定位与范围**（`00-positioning.md`）。
> 装**全项目通用**原则 —— 逐条须过 §0 门槛。

---

## 0. 收录门槛

一条原则要进 L1，必须**同时**满足：

| # | 门槛 |
|---|---|
| T1 | 对**所有模块**成立 —— 不是某个模块的设计决策 |
| T2 | **不定就会返工** —— 它是"方向性"的，不是"做法偏好" |
| T3 | **不是从已有原则推导出来的** —— 不重复、不冗余 |

**机制**：L1 的构成**按需增长**（当前 **8 条**，见 §1–§8）；追加是一次**显式动作**，
须说明它防的是哪一类返工（T2）；不满足 T1 / T3 的一律放 L2 或 L3。

## 1. 约定 A —— 简单优先，先基础后扩充

| # | 规则 |
|---|---|
| A1 | 模型 / 接口取**最小可用形态**，不为"以后可能需要"预留结构 |
| A2 | 遇到**当前想不清**的问题，默认**不做**并登记为待定项，而不是先设计一套通用机制 |
| A3 | 扩充必须**向后兼容**（字段 → 实体可以；先建树再拆下来不行） |
| A4 | **不追溯否定已拍板的决定** —— 本约定约束**未定项**与**未来的新增** |

> 主人原话："架构、模型简单优先，可以先做基础功能，再扩充完善，**很多不是一上来就能想清楚的**。"

---

## 2. 约定 B —— 引擎只做确定性事项，其余靠 agent + skill

| | 内容 |
|---|---|
| **引擎负责** | 模型定义 · 存储读写 · 确定性变换（模板渲染 / 路径计算 / 复制）· **结构与引用的合法性**检查（词表取值、id 存在性、依赖环检测） |
| **引擎不负责** | 判断 · 语义核验 · **完成判定** · 度量 —— 及一切需要"理解"的事 |
| **这些归谁** | **agent**，并用 **skill 约束**其行为（渐进披露；低摩擦入口） |

**B 有两条判据，两条都过，才归引擎：**

| | 判据 | 回答的问题 | 不过怎么办 |
|---|---|---|---|
| **判据一** | **能否写成确定性函数** | **能不能**交给引擎 | 不能 → 归 agent + skill |
| **判据二** | **长期是否适合引擎**（§2.1） | **该不该**交给引擎 | 不该 → 归 agent + skill |

**关键推论**：**引擎不实现「判据核对器」。** 判据的**表达**可以留在模型里，
但"这条判据过了没有"是语义判断 —— 归 agent（或主人），**不归引擎**。

> 主人原话："引擎做基础的确定性事项（比如模型、存储等），**其余靠 agent**，
> 可以用 **skill 去约束 agent** 来实现能力。"
> 另："**校验感觉也不是机器可以判定的强卡点**。"

### 2.1 判据二 —— 长期适合

**归入约定 B 本体**（不独立成约定）。

判据一只回答"**能不能**交给引擎"，**没回答"该不该"**。补上缺失的那一半（原话）：

> "引擎和 agent(skill) 的边界 —— **如果 agent 很强大，理论上没有引擎也可以 run 得很好**；
> **AI agent 还在持续进步，现在做得不好，不代表未来不能胜任**。
> 所以**引擎不能想着做很多、做很重**，而是想清楚**哪些是长期适合引擎做的、哪些是适合 agent 做的**。"

据此三条：

| # | 规则 | 防哪类返工 |
|---|---|---|
| **B5** | **长期判据**：划界标准是「**长期是否适合引擎**」，**不是「当前 agent 是否做得到」**。反例（要避免）：因为 agent 现在做不好 X，就把 X 放进引擎 | 引擎被**临时能力缺口**撑肥 → agent 一升级就得拆 |
| **B6** | **引擎取薄**：引擎只保留**别处必须依赖的确定性基础**（模型 · 存储 · 确定性变换 · 结构校验）。自检问句：「**把它拿掉，会有别的部分没法工作吗？**」不能 → 说明它可以归 agent | 引擎功能膨胀 → 成为变更瓶颈 |
| **B7** | **边界调整是显式动作**：agent 能力进步导致某项归属需要重判时，走一次**显式修订**（登记 + 裁定），**不静默挪动** | 与 A4 同源的"静默改写"病 |

**边界是双向的，别读成"引擎越薄越好"**：
B5 / B6 防的是**引擎被当前 agent 的弱点撑肥**；反过来，**已归引擎的确定性基础也不因"agent 也能做"而外移**
—— 那会破坏**约定 G**（可回归）与**约定 D**（单一事实源）。

## 3. 约定 C —— schema 驱动：先定义模型结构，再基于模型实现功能

> "基于 **schema 驱动**，先定义模型结构，基于模型实现功能。"

| # | 规则 |
|---|---|
| C1 | **模型先行**：任何功能**先有模型定义（schema），再写实现**；不允许"先写代码再补模型" |
| C2 | **模型是唯一事实源**：校验、序列化、CLI 表面、展示，一律**从模型派生或对模型校验**，不各自另写一套 |
| C3 | **实现不得绕过模型**：任何写入都必须过模型的合法性检查 |
| C4 | **模型变更是显式动作**：改结构先改模型，实现跟随；实现**不得私自扩展模型** |

**与约定 B 的分工（重要，别混）**：

| | 管什么 |
|---|---|
| **约定 C** | 模型**长什么样**、**谁**校验**结构**（词表取值 / id 存在性 / 引用完整性） |
| **约定 B** | 引擎**不**做**语义**判断；判断类的事归 agent |

即：C3 的"合法性检查"**只到结构层**，**不到语义层**。"这条判据过了没有"这类问题仍归 agent（约定 B）。

**约定 C 顺带覆盖的两件事**（原草案里的 M1 / M2 已并入本条，不再单列）：
- 模型与**载体解耦**（schema 定义结构，Markdown / JSON / SQLite 只是载体）；
- 载体须**可机读** —— 因为要让模型去校验它。

## 4. 约定 D —— 单一事实源

| # | 规则 |
|---|---|
| D1 | 每份数据**只有一个权威来源**；其余一律是**投影**（读时算）或**引用**（指向权威源） |
| D2 | 派生的那一份**不落盘**；若为性能落盘，也必须**可随时重建**、不得被独立维护 |
| D3 | **单一写者**：谁拥有某份数据，就**只由它写**；别处只能读或提请求 |

**与约定 C2 的分工（两条都叫"唯一事实源"，管的不是一回事）**：

| | 管什么 | 例子 |
|---|---|---|
| **约定 C2** | **结构定义**的派生关系（写代码时的规则） | 校验 / 序列化 / CLI 表面从 schema 派生，不各写一套 |
| **约定 D** | **运行期数据**的权威归属（跑起来之后的规则） | 计划"完成"由 objectives 聚合，不另存一份 status |

**已发生的三起返工**：① plan task 状态曾有两份来源（文档 vs run record）→ drift；
② 视图若自存状态会与引擎分裂；③ 技能包有两份副本（源 + 注册表），改完必须 `register --force` 才生效。

---

## 5. 约定 E —— 依赖单向

| # | 规则 |
|---|---|
| E1 | 模块 / 工具之间的依赖方向**固定且单向**；**下游不得反向感知上游**（不 import、不反查） |
| E2 | 依赖图**显式维护**（写进 L2），不靠"顺手 import" |

**已发生的事故**：forge ↔ aiwf 先定"挂钩"、后改为"不挂钩"，模型已推翻过一次。
**L0 已落定的实例**：forge **读** aiwf 的产物；**aiwf 不感知 forge**。

---

## 6. 约定 F —— 命名唯一与避让

| # | 规则 |
|---|---|
| F1 | 一个概念**全链只有一个名字**（模型 / 字段 / 命令 / 文档用同一个词） |
| F2 | **不占用上游工具已用的名字**；冲突时**改自己**的 |

**已发生的三起**：
① `forge plan` 命令撞 `plan` 用例模块；
② forge 的「事项」差点叫 `item`，撞 aiwf 的运行时队列 `items` → 改叫 `task`；
③ 落位机制的决策结果 `Plan` 撞 `plan` 用例模块 → 改叫 **`ChangeSet`**。

**F 的适用范围** ——

F1 / F2 管的是**对使用方（agent 与人）直接可见的表面**：**用例模块名 · CLI 命令名 · `kind` 名 · 跨模块共用的模型**。
**单模块 schema 内部的子模型**（JSON Schema 的 `$defs/*`）**各有文件作用域** —— 引用带 `#` 前缀、在本文件内解析 → **允许重名，不属 F 的管辖**。

**判据一句话**：**这个名字会不会脱离文件上下文、与另一个同名者出现在同一处？**
会 → **要唯一**；不会 → **可以重名**。

**实例**：`07-inbox` 的子模型 `Item` 与 `05-scaffold` 的蓝图子模型 `Item` 同名 → 分属两份 schema、`$defs` 作用域隔离、永不同现一处 → **保留 `Item`**。

## 7. 约定 G —— 确定性可回归

| # | 规则 |
|---|---|
| G1 | 引擎的确定性行为**必须有可重复的自动化验证**（测试 / golden），**不接受"应该没问题"** |

**为什么它算 L1 而不是实现细节**：它是**约定 B 的后半句** ——
B 说"确定性的活归引擎"，G 说"**因此归引擎的部分必须可测**"。两者天然配对，缺一半则 B 落不了地。

**已发生的返工**：改一处崩三处 —— 这是**实现环节最大的返工源**。

---

## 8. 约定 H —— 面向使用方 agent 的易用性优先

> 主人原话："需要**优先考虑对于使用方 agent 的易用性**（**不要有歧义、易用错，减少工具调用次数**），
> 以及 **token 成本**等。设计功能模块时**先从实际项目中完整使用流程的角度**去考虑合理性，
> 而**不仅是单一命令的易用性**；产出的模块设计文档**也要包含 agent 视角如何使用这个功能和流程**。"

| # | 规则 |
|---|---|
| H1 | **首要使用方是 agent**：forge 对外表面（命令 · 参数 · 输出 · 模型字段）**首先按 agent 的易用性设计**，其次才是人 |
| H2 | **无歧义 · 不易误用**：一个意图只对应一种表达；**能强制的不靠约定**；不留"两种写法都行、语义却不同"的坑 |
| H3 | **一次动作 = 一次调用**：能一次返回的**不要拆两次**；**副产品随主操作自动落**，不要求 agent 记得额外记一笔 |
| H4 | **token 是一等约束**：读取**按需过滤 / 渲染视图**，不逼 agent 吞整份原文；输出**只给该场景需要的** |
| H5 | **按完整流程设计，不按单命令设计**：先站在**实际项目里 agent 的完整使用流程**判断合理性；**单条命令好用不构成理由** |
| H6 | **L3 文档必须含「agent 使用视角」**：写清 agent 在**什么场景、按什么步骤、调用哪些命令**用这个模块（完整流程），而不只有模型与接口定义 |

**防哪类返工（§0 门槛 T2）**：接口不趁手 → agent **绕路 / 误用 / 反复调用** → 事后推翻重设计。

**与相邻约定的分工（别混）**：

| | 管什么 |
|---|---|
| **约定 B** | **边界** —— 某一职责归**引擎**还是归 **agent** |
| **约定 H** | **表面质量** —— 同样归 agent 的事，**对外好不好用**（歧义 / 调用次数 / token / 流程视角） |
