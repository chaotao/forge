# forge · L2 概要架构与模块划分

> 层级：**L2**。上游 = **L0 定位与范围** · **L1 设计原则**。
> 只写"概要架构与模块划分"。模块**内部**的设计（模型 / 字段 / 词表 / 接口实现）归 **L3**。

---

## 1. 分层

```
入口层      forge CLI                          forge skill
                │                                  │
                ↓                                  ↓
用例层      scaffold │ plan │ inbox │ workbench        ← 可插拔，各自独立成包
                │           └ workbench = 只读视图（无自有数据）
                ├──────→  目标项目（业务内容）
                │          └ 谁产出谁写
                ↓
数据访问层  store   ·   observer
              │             ↑
              ↓             │
          forge 自有      外部系统
          （读写）        （只读）
```

**三条层间规则**（依 L1 约定 E1「依赖单向」）：

| # | 规则 |
| - | --- |
| 1 | 依赖**只向下**：用例不得被数据访问层感知；数据访问层不得被外部工具感知 |
| 2 | **数据访问层不含业务语义**：只有"模型 / 存储 / 确定性变换 / 结构校验"（L1 约定 B）；**也不含存储实现**（见 §2.5） |
| 3 | **出口收敛**：写 **forge 自有状态**只经 `store`；读**外部运行状态**只经 `observer`。**写项目业务内容不收敛** —— 由**产出它的用例**自己写（§2.2 写约束） |

★ **层名**：`数据访问层` / `用例层` ——
`store` 与 `observer` 的共性是**无语义的数据访问**（"内核"一词易被读成"更重要"，而 `observer` 只是**只读适配器**，不担此分量）；`workbench` 则是**视图**、不是"能力域"。
L0 §3 的「能力域」= 本层的「用例」；模块**分三类角色**（数据访问 / 数据型用例 / 视图），见 §3.1。

图中**两个箭头** = 数据访问层两件套的划分依据（§2.1）：
`store` 守 **forge 自有** · `observer` 守 **外部系统**（只读）。

`store` 的**自有数据**分两处落点：**global 域**（跨项目数据）**集中在一处**；
**project 域落目标项目内的 `.forge/`** —— 与 aiwf 用 `.aiwf/` 同理（见 §4.3）。

图中**没有**「数据访问层 → 外部系统」的写箭头 —— 对外部只有读，「写外部系统」是当前**唯一的空缺格**（§2.5）。

## 2. 数据访问层

### 2.1 两件套

数据访问层的划分依据是「**谁的数据**」（数据所有者），**不是**"数据放在哪"：

| 数据所有者 | 模块 | 访问 | 职责 |
| --- | --- | --- | --- |
| forge **自己** | `store` | 读写 | 受管项目清单 · **计划（一项目多份）** / 收件箱 / 焦点 · **落位记录（lock）** |
| **外部系统** | `observer` | **只读** | 从 aiwf / git / 文件采集并归一化成视图 |

**数据访问层 = 两个无语义的口子** —— 不是"更重要的内核"。
划分依据取「数据所有者」，因为它**不随功能增减而变**（所有者不因用例增多而增多）—— 这是它能跟上用例拓展的前提（§2.5）。
★ 两者**分量不同**：`store` 是 forge 自有状态的**唯一写者**；`observer` **只读、不存**，是**外部数据的适配器**（§2.3②）。

**命名**

| 模块 | 名字含义 | 说明 |
| --- | --- | --- |
| `store` | forge 自己的**账本** | 含 global 域（跨项目，集中一处）与 project 域（落目标项目内 `.forge/`） |
| `observer` | 往里**看**的那只眼 —— **外部数据的适配器**（只看不碰） | 与 `store` **分量不同**：只读、不存；是外部运行状态的**唯一读口**（§2.3②） |

数据访问层只管**两块数据**：forge 自己的、以及来自外部的。
「**目标项目**」**不是**数据访问层守卫的数据域 —— 见 §2.2 的写约束。

### 2.2 不变量与写约束

**不变量（两条）**

| # | 不变量 | 域 |
| --- | --- | --- |
| 1 | `store` 是唯一写 **forge 自有状态**者（**含目标项目内 `.forge/`**） | forge 自己 |
| 2 | **读外部**分两个物种：`observer` 读**运行状态**（只读、不存）· **素材 / 组件**由**需要它的用例**自己读 | aiwf · git · 文件系统 · skill-library |

第 2 条的理由：工作台的价值取决于"显示的与实际是否一致"，若散落各处读 `.aiwf/runs/`、git，迟早读出不同口径。
（**素材**不是"显示口径"问题 —— 它是落位的**输入**，谁用谁读。）

**写约束 —— 对「项目业务内容」**

| # | 约束 | 说明 |
| --- | --- | --- |
| W1 | **谁产出谁写** | 项目业务内容由**产出它的用例**写；数据访问层不代写、也**不设统一出口** |
| W2 | **同一份产物只有一个写者** | L1 约定 D3（单一写者）在用例层的落地 —— 按**内容**划分，不按目录 |
| W3 | **`.forge/` 仍归 `store` 独占** | forge 自有状态（含 lock）不受 W1 影响 —— 这是"一个目录一个写者"仅存的**唯一**硬约束 |

**为什么项目业务内容不设"唯一写者"**：

> 项目产物的**形态各异**（骨架 / 配置 / 脚本 / 给人看的计划书…），**没有统一 schema 可约束**。
> 用"单一写入出口 + 一套变更机制"覆盖全部项目写入，前提是"所有写入都能用同一个模型表达" ——
> **该前提不成立** → 是过度设计（L1 约定 A1：简单优先）。

⇒ 落位机制**不用作架构级约束**，它归 `scaffold` **内部**（设计见 L3 `05-scaffold`）。

W2 与 **L1 约定 D（单一事实源）** 一致：它是 D3 在用例层的落地；不变量 1 是 D3 在数据访问层的落地。

### 2.3 职责明细（做 / 不做）

**① `store` —— forge 自己的账本**

| | 内容 |
| --- | --- |
| **存什么** | **global 域**（集中一处）：受管项目清单（路径 / 别名 / 蓝图 id / 阶段 / 注册时间）· 跨项目焦点（"我现在在推哪个"）<br />**project 域**（落 `<目标项目>/.forge/`）：**计划（一项目多份；每份 = 目标 / 判据 + `tasks[]`）** · inbox ledger（`未处理` / `已交接` / `丢弃`） · ad hoc 事项 · **落位记录（lock，由 `scaffold` 交来）** |
| **做什么** | 读 / 写 / 查 |
| **不做** | ① **不做语义判断** —— "这个任务算不算完成"归 agent（L1 约定 B）；② 不读外部系统；③ 不写项目里的**业务内容**（它只写 `.forge/` 专区） |

**② `observer` —— 外部数据的适配器**

| | 内容 |
| --- | --- |
| **做什么** | 把 aiwf / git / 文件系统读成**统一视图**（`ProjectStatus` 等） |
| **采集差异** | aiwf 的 `--json` **覆盖不均**（`wf *` 等仍无）→ ★ **一律经 CLI**：有 `--json` 用 JSON、暂无的**按文本解析**；**不直读其运行时文件**（快照会过期） |
| **关键性质** | **什么都不存** —— 它是 L1 约定 D2「读时投影」的实现者；这解释了它为何没有"更新"这个概念 |
| **不做** | **一个字节都不写** |
| ★ **为什么独立存在** | 它是**外部运行状态的唯一读口**。若不独立，每个消费方（如 `workbench`）都得自己应付 aiwf 的**采集差异**（`--json` **覆盖不均** · `(no runs)` **静默空返回** · **CWD 依赖**）—— 同一份知识的**多处拷贝**（与 §4.2.1「读经所有者读面」是同一条原则）。留**多数据源**扩展点（git / 文件系统） |

**一句话记法：`store` 是自己的账本，`observer` 是外部数据的那只（只读）适配器。**

### 2.4 典型操作触达谁

| 操作 | store | observer | 写项目的用例 |
| --- | --- | --- | --- |
| 看全局（`forge workbench`） | 读 | 读 | — |
| 记一个念头（`forge inbox add`） | **写** | — | — |
| 立一个新项目（`forge new`） | **写**（登记受管 + 落账） | — | **`scaffold`** 写骨架 |
| 同步已有项目（`forge sync`） | **写**（落 lock） | — | **`scaffold`** 写增量 |

**这张表的意义 = 三条硬线**：

1. 写 **forge 自有状态**只有 `store` 一个出口；读**外部运行状态**只有 `observer` 一个入口 —— 没有旁路。读 **forge 自有**的数据则一律经**该 `kind` 模型所有者的读面**（§4.2.1）。
2. **`observer` 不存任何东西** → 工作台显示的是现读实况，永远不会读到过期副本。
3. **项目业务内容由用例分头写**（W1）—— 靠 **W2（一份产物一个写者）** 保证不重叠，故第 3 / 4 行的"写"同时发生也不冲突。

### 2.5 增长边界

**判据：数据访问层按「数据所有者」增长，不按「用例」增长。**

| | 按什么划分 | 拓展时 |
| --- | --- | --- |
| **用例层** | 用例 / 流程 —— 把数据访问层原语组合成一个完整用例 | 新增用例 → **数据访问层不变** |
| **数据访问层** | **数据所有者** —— 谁的数据、哪个方向 | 只有**出现新的所有者**才需要它增长 |

**抽象性来自划分依据的稳定性，不是来自"抽象得更多"。** 所有者不因功能增减而变。

**完备性：数据所有者 × 方向**

| 数据所有者 \ 方向 | 读 | 写 |
| --- | --- | --- |
| forge 自己 | `store` | `store` |
| 外部系统 | `observer`（**仅运行状态**）· **各用例**（**仅素材**） | **空缺** |
| 人 | 经入口层 | 经入口层（不直连数据访问层） |

**「目标项目」不在本矩阵里** —— 它**不是**数据访问层守卫的数据域（由用例按 W1 直接写，§2.2）。

**六个格子只有一个空缺 —— 「写外部系统」**（如回写 aiwf、写 git commit）。
它空着**不是设计漏了**，是 L0 §4.1 主动定的（"forge 读 aiwf；**aiwf 完全不知道 forge**"）。
→ 对**当前已声明的一切**，数据访问层的两个原语是**穷尽的**。

空缺格记为**已知的潜在第四边界** —— 不是"永远不做"，是"现在不做"（L1 约定 A2）。
将来若需要，走一次**显式修订**（登记 + 裁定），不静默新增。

**未来拓展的四种落点**

| 情形 | 落在哪 | 是否动数据访问层 |
| --- | --- | --- |
| **新增用例** | **用例层**（如 `review`） | 否 |
| **新增动作或字段** | **现有模块内部**（如 `scaffold` 的落位增加"删除""移动"） | 否（模块构成不变） |
| **新增数据源或目标** | **适配器**（`observer` 内部 · **各用例的来源适配器**） | 否（模块构成不变） |
| **出现新的数据所有者** | **数据访问层本体**（如需要写外部系统） | **是**（需过门槛） |

**数据访问层增长的唯一触发条件 = 出现新的数据所有者**，它比"用例增多"稀有得多。

随之而来两条约束（**L3 承接**）：

- `observer` 须留**适配器扩展点**（多数据源）；用例读素材同样经**自己的**来源适配器 → 接新来源**不必动数据访问层构成**；
- 数据访问层**新增动作**属现有模块内部扩展，**不构成数据访问层增长**。

**与存储形态解耦**

数据访问层对外只暴露**结构语义**（读 / 写 / 查），**不暴露存储形态**。无论取 Markdown / JSON / SQLite，用例看到的接口不变。

→ 这是 §1 层间规则 2「数据访问层不含业务语义」的后半句 —— **也不含存储实现**。
→ 存储形态的选择**只影响 `store` 一个模块内部**，正是 L3 的射程（见 §5.1）。

## 3. 模块划分

### 3.1 模块清单

**forge = 6 个模块**（数据访问 2 + 用例 4，**平级**）；按**角色**分三类：

| 层 | 角色 | 模块 | 一句话职责 | 写盘 |
| --- | --- | --- | --- | --- |
| 数据访问 | **账本** | `store` | forge **自有数据**（global 受管清单 / project 计划状态 · 焦点 · inbox ledger · 落位记录） | 写（自有） |
| 数据访问 | **适配器** | `observer` | **外部运行状态的唯一读口**，产出**读时投影** | **不写** |
| 用例 | 数据型 | `scaffold` | **立项目与依赖管理**：蓝图与选择 → **自己落位**（写项目业务内容） | **写（项目）** + 经 `store` |
| 用例 | 数据型 | `plan` | **项目内计划（一项目多份）** —— 目标 / 判据 / 任务（**可落自己的项目产物**） | 经 `store`；可写项目 |
| 用例 | 数据型 | `inbox` | 念头捕获与交接 | 经 `store` |
| 用例 | **视图** | `workbench` | 跨项目总览与介入（**聚合呈现**） | **不写** |

- **两个模块不写盘**：`observer`（现读现算）与 `workbench`（聚合呈现）—— 这不是缺陷，它们靠"不存"来保证"看到的即实况"。★ 二者**同属"不写"、角色不同**：`observer` 是**数据访问**（外部），`workbench` 是**视图**（聚合）。
- **用例与模块一一对应**：L0 §3 的四个「能力域」即本层的四个用例模块（术语映射见 §1）。
- **模块数不是封闭集**（L0 §1 范围开放性）：上表是"当前已定的部分"；新增用例 = 新增模块，但每个都要单独论证。**数据访问层的增长条件严格得多**（§2.5）。
- **L3 文档与模块一一对应**：`03-store` · `04-observer` · `05-scaffold` · `06-plan` · `07-inbox` · `08-workbench`。

### 3.2 `WorkUnit`：暂缓

`WorkUnit` **不是模块** —— 它没有自己的数据域，因此不是数据所有者、也**不写盘**。
这条是**护栏**：防止将来把它当作数据所有者或写者接进来（那会破掉 §2.2 的不变量）。

它的**定义与规格暂缓**（「没想清楚，先不做」；判据 = L1 约定 A2）：
不进 L2 正文、不建独立 L3 文档、**不作为下游设计的前提**。

**将来若要启用**：属**新增**（不是"恢复"）—— 需重新过 L1 §0 门槛与 L2 的模块判据。

## 4. 接口方向与边界

### 4.1 对外方向

| 对象 | 方向 | 说明 |
| --- | --- | --- |
| **aiwf** | forge **读**运行状态 / **调用 CLI**（**不读**其库）；**aiwf 完全不知道 forge** | 读状态经 `observer`；`scaffold` 装工作流走 `aiwf wf install <id>` |
| **skill-library** | forge **调用 CLI**（**不读**注册表 / 库根） | 由**需要组件的模块**（如 `scaffold`）**经 CLI 委托**安装；注册与分发**不归 forge** |
| **git** | forge **只读** | 状态信号（未提交 / 冲突），经 `observer` |
| **被管理项目** | forge **写**项目业务内容 | 由**产出它的用例**写（W1）；边界见 §4.3 |
| **`aiwf/sim/plan-task`** | **只作设计参考，不是依赖** | 边界见 §4.4 |

### 4.2 模块间的依赖图

**显式边表**（L1 约定 E2 要求"依赖图显式维护"）：

| # | 从 | 到 | 说明 |
| --- | --- | --- | --- |
| 1 | 入口层（CLI · skill） | 用例 | 人是**唯一入口**；数据访问层不直接面向人 |
| 2 | 用例（各） | 目标项目 | **写自己的项目产物**（W1） |
| 3 | 用例 `scaffold` | 数据访问层 `store` | 登记受管（global 域）· 落位落账（project 域）· 读回 lock |
| 4 | 用例 `scaffold` | 外部组件（skill-library / aiwf） | **调用其 CLI** 委托安装（**不读**其库根 / 注册表）；蓝图 payload 为**包内资产**（不经此边） |
| 5 | 用例 `plan` | 数据访问层 `store` | 计划状态读写（project 域） |
| 6 | 用例 `inbox` | 数据访问层 `store` | 念头读写（project 域） |
| 7 | 用例 `workbench` | 数据访问层 `store` | 读 **`store` 自有**的 kind（`projects` / `lock`）—— **只读** |
| **7b** | 用例 `workbench` | 用例 `plan` / `inbox` | ★ **读它们的公开读面** —— **只读**（§4.2.1） |
| 8 | 用例 `workbench` | 数据访问层 `observer` | 读外部运行状态（**只读**） |
| 9 | 数据访问层 `observer` | 外部系统 | **只读运行状态**，现读不存 |
| 10 | 数据访问层 `store` | forge 自有数据 | 唯一写者（global 集中一处 / project 落 `.forge/`） |

**零反向边**（L1 约定 E1 的可检验表达）：

- 数据访问层**不引用**任何用例；
- **写路径：用例之间零依赖** —— 各自只经 `store` 写自己的数据、互不写；**各用例各写自己的项目产物、互不依赖**（W2 保证不重叠）；
- **读路径：数据经「所有者读面」** —— 见 **§4.2.1**；
- 外部工具**不感知** forge。

**跨用例的复合动作**（如"立项目 + 初始化计划"）**由入口层组合**，不靠用例互相调用 ——
否则会引入一条"用例 → 用例"的**写**边，破掉 E1。

**数据访问层内部依赖：无。**
两件套**互不依赖**（`store` 不感知 `observer`，反之亦然）。
`store` 的两个域（global / project）共用一套读写原语 —— 那是**内部实现取舍，不是模块间依赖**。

### 4.2.1 ★ 读取原则：一切读取经「所有者读面」

数据都有**所有者**。**读一份数据，一律经它的所有者公开的读面** —— 不旁路、不重算语义。

| 数据 | 所有者 | 读法 |
| --- | --- | --- |
| `plans` / `plan_log` | 用例 `plan` | `plan` 的**公开读面**（`list_plans` / `show_plan` / `read_events`） |
| `inbox` | 用例 `inbox` | `inbox` 的**公开读面**（`list_items` / `show_item`） |
| `projects` / `lock` | 数据访问层 `store`（**自有**） | `store.read` |
| 外部运行状态（aiwf / git / 文件系统） | **无人**（forge 之外） | **`observer`** —— 唯一适配器（§2.3②） |

**规则**

1. **只经公开读面**：不得 import 对方的**内部实现**、不得读对方的**落盘文件**；
2. **读路径单向、无环**：**视图型**用例（`workbench`）可**只读**引用**数据型**用例的读面；**反向不许**；
3. **写路径仍零依赖**（§2.2 W1–W3）。

**为什么放开这条读边**：视图模块若不读所有者读面，就**必须自己重算一遍语义**（数据形状 + 状态词表）——
那是**同一份知识的两处事实源**（违 L1 约定 **D**），且所有者改词表时**静默出错**。
「用例之间零依赖」若读成"**不许调对方公开读面**"，就与本节冲突；正确的拆法是：
**不许依赖对方实现 / 写路径**（保留），**允许调对方公开读面**（本条）。

### 4.3 与「被管理项目」的边界

forge 对目标项目**只做两件事**：

| # | 做什么 | 经谁 |
| --- | --- | --- |
| 1 | 往项目里**落自己产出的内容**（骨架 / 产物…）；**外部组件**由上游工具落 | **产出它的用例**（组件：**调上游 CLI**） |
| 2 | **读**项目的状态用于总览（git 状态 · 文件存在性等） | `observer` |

**项目内的命名空间划分**（谁写哪里，一眼看清）

| 项目内路径 | 放什么 | 谁写 |
| --- | --- | --- |
| **`.forge/`** | **forge 自有状态**的 project 域：计划状态 · inbox ledger · 焦点 · ad hoc 事项 · 落位记录（lock） | **`store`** —— 唯一写 forge 自有状态者（§2.2 不变量 1） |
| **`.aiwf/`** | aiwf 的地盘：引擎记录（`installed.json` · `runs/`） | **aiwf 自己**（forge 只**调** `aiwf wf install`，**不代它取件 / 落位**），**不放自有状态** |
| **其余**（代码 / 配置 / 文档 / skill / payload …） | 项目**业务内容** | **产出它的用例**（W1）—— **同一份产物只有一个写者**（W2） |

**一份产物一个写者** —— 按**内容**划分，不按目录：
多个用例可以在**同一个目录**里各写自己的产物，但**同一个文件只能有一个写者**。
`.forge/` 是唯一仍按目录独占的地方（W3）。

**明确不做**：

| 不做 | 依据 |
| --- | --- |
| 不代管项目代码（不重构 / 不实现业务） | §3.1 清单里无此模块 |
| 不做构建 / 测试 / 部署 | 同上 |
| 不替项目做技术决策 | L1 约定 B（引擎只做确定性事项；判断归 agent） |
| 不改写**非自己产出**的项目文件 | W1 / W2 只授权"写自己产出的"，未授权"接管" |

**退出 forge 的完整含义**：删 `.forge/` ＋ 从 global 清单移除 ＋ **自行处置各用例落下的产物** ——
用例落的产物（骨架 / 计划书…）留在项目里，`.forge/` **不是**唯一痕迹。

### 4.4 与 `aiwf/sim/plan-task/` 的边界

> 事实核对（实读 `aiwf/sim/plan-task/README.md`）：它是 aiwf 仓库 `sim/` 下的**一份仿真**，
> 验证"工作流能否自己产出计划（任务清单）→ 逐条执行 → 整体验收 → 交付完成态计划"。
> 两条关键前提：① **plan 不是人的输入，而是工作流的第一个产出**；
> ② **任务清单不是文件，而是引擎持有的运行时队列**（`aiwf items add` / `seal`，无人写队列文件）。

| 维度 | `aiwf/sim/plan-task/` | forge `plan` |
| --- | --- | --- |
| 是什么 | aiwf 仓库里的**仿真**（验证引擎 + `view` 能力） | forge 的**用例模块**（产品） |
| 范围 | **一次 run** 的计划 | **一份计划**（**一项目多份**；每份 = 目标 / 判据 / 任务） |
| 状态谁持有 | **aiwf 引擎**（运行时队列，`seal` 封口） | **`store`**（唯一写者，§2.2 不变量 1） |
| 产物落在哪 | `plan/<name>/*.md` + `.aiwf/runs/`（引擎记录） | `store` 的 project 域（`.forge/`）；**若 `plan` 另落给人看的产物，那是它自己写的项目文件**（W1） |

**边界条款**

| # | 条款 | 依据 |
| --- | --- | --- |
| 1 | forge 与 `sim/plan-task` **无结构性挂钩**：不建外键、不做专用接口；forge 读 aiwf 只经 `observer` 读**运行状态** | L0 §4.1；既有硬口径（forge plan 的 task 与 aiwf run 无外键） |
| 2 | `sim/plan-task` 对 forge 是**设计参考，不是依赖** —— forge 不 import 它、不读它的 `plan/` 产物 | L1 约定 E1（单向）；plan **重设计**，不照搬 aiwf 代码 |
| 3 | **同一份计划不得有两处事实源**：`plan/<name>/plan.md` 是 sim 的业务产物，**不构成 forge plan 的事实源**；若将来 forge 要在目标项目里落"计划书"，那是 **`plan` 用例**的项目产物（W1），且必须是对 `store` 的**投影** | L1 约定 D（单一事实源 / 派生不落盘） |

**一处潜在张力（不在 L2 解决）**：
sim 的定位是「plan 是工作流的产出，不是人的输入」；forge 的定位是「plan 是人 + agent 协作维护的项目状态，`store` 为唯一写者」。
两者**当前不冲突**（范围不同：一次 run vs 项目内一份计划）；但若将来要让 aiwf workflow **执行 forge 的 plan**，
这两种定位会撞车（**谁写 plan state？**）→ 留一次**显式裁定**，不静默处理。

## 5. 留给 L3 的约束与暂缓事项

### 5.1 下推 L3（L2 已给约束，形态选择归模块设计）

| # | 项 | L2 保留的约束 | 下推到 |
| --- | --- | --- | --- |
| **Q3** | 存储形态（Markdown / JSON / SQLite） | ① 数据访问层对外只暴露**结构语义**，不暴露存储形态（§2.5）；<br />② 形态须满足 **人可读 · 可 diff · 可入库** | **L3-store** |
| **Q4** | 存放位置 | ① **global 域必须集中** —— 它是**跨项目**数据，项目内文件装不下；<br />② **project 域落目标项目内的 `.forge/` 专区** —— 与 aiwf 用 `.aiwf/` 同理，它是 `store` 的**专属命名空间**，与其余项目内容**分属不同写者**（§4.3）；<br />③ **`.aiwf/` 不放 forge 自有状态**（素材交付允许） | **L3-store**（`.forge/` 下的具体文件与结构 / 是否纳入版本控制） |
| **Q5** | 工作台呈现形态（CLI 文本 / JSON / HTML） | ① `workbench` **不写盘**（§3.1）；② 只从数据访问层读；③ **L2 定接口、L3 定实现** | **L3-workbench** |
| **Q6** | 用例写项目产物的**边界约定** | ① **谁产出谁写**（W1）；② **同一份产物一个写者**（W2）；③ 各用例自行声明自己写哪些产物，**不越界代写** | **L3 各用例**（`scaffold` / `plan` …） |

> **Q3 约束 ② 的来源**：候选 **N6（状态可迁移）**。
> 依据链：L0 §2「人做判断与决策，agent 做执行与记录；forge 是二者共用的**记账本**」+ 主人既有工作方式（版本控制 / diff / 校验）。
> **Q3 能下推的理由**：§2.5 已把数据访问层接口与存储形态**解耦** → 形态选择只影响 `store` 一个模块内部，正是 L3 的射程。
